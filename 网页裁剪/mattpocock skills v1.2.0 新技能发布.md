### Wait What 技能（提升清晰度）

**2:49** · 它用一些非常怪异的大语言模型(LLM)用语，我就是觉得非常非常难以阅读，很多人都有同感。

**2:55** · "The honest options are to accept it and reword the AC or to persist the digest along the export. So a resumed unchanged publish can skip the read to flagging rather than picking."（诚实的选项是接受它并改写验收标准(AC)，或者在导出时一并保留摘要。这样恢复未变更的发布就可以跳过阅读标记，而不是做出选择。）这是什么意思？但它确实承载着实际含义。正因如此你才知道它重要。我试过各种办法来修复这个问题，比如输出样式(output styles)，或者在 agent.md 里加东西。但我意识到，我真正需要的是一个能说"等等，你刚才说什么？"的技能。于是这个技能就叫 wait what。这是一个非常非常简单的技能，只做两件事。

**3:22** · 首先，它说："使用这种特定的标准 ASD STE-100 简化技术英语(simplified technical English)"——这本质上是给智能体(agent)一个引导词，让它使用非常简单的语言。

**3:34** · "用清晰、陈述性的句子表达。"

**3:36** · 其次，它还会告诉智能体要扎根于 context.md 中的通用语言(ubiquitous language)。对付啰嗦真正的解药，并不是让它用简单语言——虽然我们也做了一点这个——而是让它用你的语言，也就是你在 Grill with Docs 里梳理出来的那套词汇。当智能体(agent)造出一些莫名其妙的垃圾、而你完全不知道它刚说了什么时，就用这个技能。你只需说"Wait, what?"，它就会给出一个清晰得多的版本。下一个变化相当大。它是对我最受欢迎的技能(skills)——Grill Me——的一次更新。

### Grill Me（多问题轮次）

**4:06** · 此前，Grill Me 一次只盘问你一个问题。也就是说，你会收到一个问题，然后作答，然后再来一个问题，再作答。所以每一轮一个问题。

**4:18** · 然而，这种方式有一个糟糕的失败模式：当你走到一次盘问会话的尾声、大部分难题已经搞定之后，剩下的就只是一堆简单问题，一轮一个，你基本上只是在说"嗯，听起来不错。嗯，那个也不错。"这极其令人沮丧，感觉慢得要死。所以一段时间以来，我一直想找个办法加快这一过程。对我来说最合理的做法是，每一轮放多个问题。这样如果有许多简单题，你就可以一口气说"是、是、是、是、是"。

**4:46** · 但如果第三个问题的答案依赖于第一个问题的答案，那会怎样？以前你不会有这个问题，因为你是一个一个答的。如果某个问题依赖于更早的问题，那更早的问题早就答过了。但在这个新设置下，这岂不是更令人困惑？因为你正在回答一些有误的、或时机不对的、或本该先于其它问题回答的问题。这要怎么行得通呢？嗯，如果你仔细想想，这些问题其实就像一张图(graph)。

**5:14** · 可能在最开头有那么一个关键问题需要先回答，它打开了一大批其它问题，而那些问题也许又各自引出更多问题。

**5:24** · 所以现在，Grill Me 被设计成跟随这张图，只回答当前可回答的问题，但以轮次(rounds)的方式来提问。于是你先收到第一轮问题，可能少到只有一个关键问题。然后你进入下一轮——由上一轮打开的那批新问题，它始终以尽可能快的速度把问题边界(frontier)向前推进。它看起来是这样的。你可以看到我在这里处于第一轮，有 Q1。然后我们得到这个小建议。我决定用——我知道你们大概不喜欢，但我很喜欢——

**5:57** · 用 emoji 来增加一点色彩。

**5:59** · 这让用眼睛导航变得超级容易。我能一眼看到，哦，这是 Q1，然后看到推荐答案。Q2，看到推荐答案。

**6:08** · 而且因为我在用口述，我就可以一口气刷出来："好的，Q1，我同意。Q2，我同意。Q3，那里需要改一下。Q4，那里要改。"

**6:17** · 再往下，我们可以看到第二轮问题进来了，布局完全一样。所以我们回答了第一轮问题，然后又得到新一轮问题，就这样不断把边界向前推。下一个大变化是，我改造了我的 writing great skills 技能，因为我发现自己把它用在技能以外的事情上。我用它处理任何供智能体(agent)阅读的内容，以让智能体表现更好、让文档更精炼、让输出更可预测。

### Writing for agents 技能

**6:44** · 于是现在我们有了 writing for agents，你可以用它来修改 agent.md 或 claude.md，或者在创建、编辑技能(skills)时使用，并且它在这个参考文件里钉装了一些额外的技能机制。所以你既可以用它来写技能，更关键的是，也可以用它把你那份 agent.md 抽取成多个技能，从而终结那种可怕的前置堆砌(frontloading)。总体而言，每当我需要写任何智能体配置并希望它读起来顺口时，我都会非常频繁地使用这个技能。我希望智能体用它时表现良好。

**7:14** · writing for agents 就是正确的选择。而且它也是可被模型调用的(model-invocable)。这里的描述非常干净。所以每当你修改 agent.md 时，它应该都会被自动引入，这非常好。下一个是一个新技能，我把它藏着掖了一阵子。这就是 wizard 技能。

### Wizard 技能（用于配置/开通）

**7:33** · 最近我发现自己不得不开通(provision)一堆基础设施，并走完一堆 AWS 的流程，我对此深恶痛绝，于是我想，智能体(agent)肯定有办法在这里帮上我。所以我做了这个 wizard 技能，它生成一个交互式的 bash 向导，引导人类一步步完成只有他们自己才能执行的步骤。换句话说，我本可以让智能体去——好吧，去 AWS 用 computer use 之类的开通那些东西，但那样感觉很糟糕。我想掌控全部过程，但我又希望它尽可能简单。这就是一个向导的样子。

**8:04** · 这个我想是用来迁移到一个远程主机环境的。

**8:09** · 所以你只需启动它，然后说"准备好开始了？是的，请开始。"然后它把我直接送到我需要去的那一页。顺带一提，那一步打开了脚本，我什么都没做。它送我过去，让我登录，让我改掉正好需要改的东西。然后我可以粘贴我的 API 密钥。请记住，这是一个确定性脚本，所以这里没有任何东西经过智能体。它不会把内容发到 Anthropic 或别处。所以我在这里粘贴，它把它存到需要存的文件里。它甚至会在需要时把它们存进 GitHub secrets。

**8:35** · 它就这样和我一起走完这些独立阶段，一路维持着这个漂亮的小界面，直到我们得到所需的结果。我发现这把开通服务从极其痛苦变成了出奇地愉悦，因为我清楚地知道以前那要花我多长时间。所以 wizard 已经成了我技能集里不可或缺的一部分。我把它放在 in-progress 状态好几个月了，现在我想，好吧，是时候让你们看看它了。

### To Questionnaire 技能（用于协作）

**8:58** · 下一个绝对是我产出过的最无聊的技能名，但我发现自己真的非常需要它，而且我意识到它的用途会超出我当初用它做的那些事。它叫 to questionnaire，用途是把一次盘问(grilling)会话中的那些决策抽取出来，整理成一份你可以拿去和别人一起过一遍的文档。我当时在做一次 wayfinder 会话，想在后院建一个花园办公室。

**9:23** · 我意识到智能体(agent)在盘问我，但我真正需要与之商量的人是我太太，因为显然她也会使用这个空间。所以我们要一起设计它。于是，我让智能体把它本来要问的问题整理成一份 Markdown 文档。然后我把它放进一个 Google Doc，发给我太太，我们一起过一遍，再把答案拉回智能体里。

**9:46** · 这是一个我希望有朝一日能删除的技能，因为它某种意义上是一种补丁，弥补了目前智能体(agent)不太容易与之协作这一事实。有些团队的配置——我认为是相当好的配置——是他们把智能体放在 Slack 里，于是他们可以在这些对话中 @ 智能体。这样他们就能一起协作、一起回答问题，尤其是和利益相关者(stakeholders)一起。然后智能体就能真正地介入并说："好的，我根据这些去实现。"

**10:13** · 但很多人目前并不在那个世界里。很多人还不是 AI 原生的(AI native)。他们可能连 Slack 或 Microsoft Teams 之类的东西都没有。

**10:21** · 所以，能抽出一份文档，交给某人，他们可以在 Google Docs 或别的什么上面评论，这其实非常有用。那么各位，基本就是这样了。我们带来了一批新技能(skills)。我尤其期待你们对 wait what 的反应，因为我认为当 Opus 在做怪异举动时，它确实能救你几次。
