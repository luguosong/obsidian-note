## 1. 数据结构与证书↔印章关系（主题一）

电子印章的核心是"印章数据结构 + 证书绑定"。本节回答：一枚印章在数据层如何与持章人、制章者证书绑定，绑定媒介是什么。

### 1.1 SESeal 印章数据结构概览

GB/T 38540-2020 §6.1 定义电子印章 SESeal 的顶层结构（关键字段）：

```
SES_SealInfo ::= SEQUENCE {
    eSealInfo       TBS_ESeal,     -- 印章信息（待签内容）
    cert            Certificate,   -- 制章者证书（§6.1.3）
    signatureAlgID  OBJECT IDENTIFIER,  -- 签名算法标识
    signedValue     BIT STRING     -- 制章者对印章信息的签名值（§6.1.5）
}
```

- `eSealInfo`（类型 `TBS_ESeal`）是印章的"待签信息"，含印章头、印章属性信息（`SES_ESPropertyInfo`）、印章图像与自定义数据。
- `cert` 是**制章者证书**（见 §1.3），`signedValue` 是制章者用其私钥对 `eSealInfo` 的数字签名——这是印章完整性与不可否认性的来源。
- `SES_ESPropertyInfo`（§6.1.2.4）含 `certList`（签章者证书信息列表），即持章人绑定，见 §1.2。

### 1.2 SES_CertList：签章者证书列表（持章人绑定）

印章绑定到持章人通过 `certList`（签章者证书信息列表）+ 制章者签名值，**不存任何姓名/身份证号明文字段**；持章人身份只通过 X.509 证书表达。

```
SES_CertList ::= CHOICE {
    certs           CertInfoList,      -- 签章者证书信息列表
    certDigestList  CertDigestList     -- 签章者证书杂凑值列表
}
```

> [!note] 来源标注
> 本 ASN.1 块综合 **GB/T 38540 §6.1.2.4** + **C-0120 §6.2.3**。GB/T 38540 原文该 CHOICE 定义解析残缺（仅散落出现 `SES_CertList::=CHOICE{`、`certs CertInfoList`、`CertDigestList::=SEQUENCE OF CertDigestObj`，未给出完整第二分支名 `certDigestList`）；**完整的 `certs / certDigestList` 双分支定义以 C-0120 §6.2.3 为准**。

- `certListType`（INTEGER）：`1` = 数字证书（走 `certs` 分支），`2` = 证书杂凑值（走 `certDigestList` 分支）。
- 持章人可自然人、可机构法人，标准不限定。C-0120 §6.2.3 的 `type` 字段：代码 `01-04` = 电子公章标识（法定名称章/财务/发票/合同专用章），`05` = 电子名章标识——标准明确支持单位章与个人名章并存。
- **绑定媒介（强制）**：X.509 证书唯一。标准无"持章人姓名/身份证明文"字段，持章人身份仅通过证书（CN/SAN）承载，制章者签名保证完整性。
- **命名差异**：C-0120 §6.2.3 把 `certList` 对应概念称"电子印章所有者证书列表"（用"所有者"措辞），与 GB/T 38540 用"签章者证书"措辞并存——二者指同一字段，命名对照见 §6 术语速查表。

### 1.3 制章者证书与印章签名

- `cert` 字段（§6.1.3）= **制章者证书**。GB/T 38540 §3.6 注明确指出："电子印章中的制章者证书应是**该机构的单位证书**。"即证书归属是制章**机构**而非制章系统。
- `signedValue`（§6.1.5）= 制章者对印章信息的签名。签名链上用的是制章者（机构）的单位证书私钥，不是"制作系统"的证书。系统证书（C-0118 §9.2.3）用于系统间身份鉴别，不用于签印章本身——详见 §5。

### 1.4 证书↔印章绑定小结

| 绑定关系 | 数据结构承载 | 强制级别 |
|----------|--------------|----------|
| 印章 ↔ 持章人 | `certList`（签章者证书列表）+ 制章者签名 | 强制（GB/T 38540 §6.1.2.4） |
| 印章 ↔ 制章者 | `cert`（制章者证书）+ `signedValue`（制章者签名） | 强制（GB/T 38540 §6.1.3 / §6.1.5） |
| 用章 ↔ 用章人 | SES_Signature 的 `cert ∈ certList` 强制比对 | 强制（GB/T 38540 §7.2 a)3 / §7.3 c） |
| 持章人身份明文 | （无字段） | 标准刻意不存明文，身份仅靠 X.509 证书 |

关键结论：技术结构层把印章只绑 X.509 证书，完全不涉及"申请人/登录用户"概念——任何"登录用户=持章人"的约束都是平台策略，不是标准要求。

### 1.5 印章验证流程（GB/T 38540 §6.3）

印章本身的验证（区别于 §4.3 验章/签章验证）按 GB/T 38540 §6.3 为**四步**：

1. **格式**：检查印章数据格式是否符合 SESeal 定义。
2. **签名值**：验证制章者签名值（`signedValue`）与印章信息（`eSealInfo`）是否一致。
3. **制章者证书**：验证制章者证书的有效性（是否合法 CA 签发、是否在有效期内）。
4. **有效期**：检查印章是否在有效期内。

> [!warning] 跨标准结构差异（重要）
> 本流程以 **GB/T 38540 §6.3 为准（四步，不含状态校验）**；C-0120 §8 的印章验证为**五步**且含在线状态校验（c 步：联网在线查验或吊销列表查印章是否被吊销）。两个标准的步骤数与顺序不同——详见 §7.2 易踩坑 2，按不同标准实现验章会得到不同流程。

## 2. 角色全景与子系统（主题二之一）

### 2.1 五类核心角色术语

电子印章相关标准定义 **5 类核心角色术语**；但「申请人(applicant)」「持章人(holder)」「登录用户」**均不是**任何被查标准的术语——标准对其沉默，属平台策略层。

| 术语 | 定义 | 出处 |
|------|------|------|
| 制章者 / electronic seal maker | 电子印章系统中具有电子印章制作和管理权限的**机构** | GB/T 38540-2020 §3.6 |
| 签章者 / electronic seal signer | 电子印章的**所有者**，具备电子印章法定使用权限的**实体** | GB/T 38540-2020 §3.7 |
| 电子印章所有者（与签章者同义）/ owner | 具备电子印章法定使用权限的**主体** | C 0120-2018 §3.4、C 0119-2018 §3.5 |
| 电子印章制作主体 | 从事电子印章制作技术服务的**主体** | C 0118-2019 §3.2 |
| 电子印章使用主体 | 因业务或职权需要需使用电子印章的**主体** | C 0118-2019 §3.3 |

GB/T 38540 §3.7 把「签章者」与「电子印章所有者」**定义为同一实体**。C 0118 §9.4.2 流程中另引入（非术语）审核员、管理员、申请人/经办人/法定代表人——这些是业务流程角色，非标准术语。

**法律层补充**：《电子签名法》第三十四条（一）电子签名人 = "持有电子签名制作数据并以**本人身份或者以其所代表的人的名义**实施电子签名的人"——明确允许代理/代表签名。《电子印章管理办法》第二十一条确立「谁所有、谁控制，谁签章、谁负责」原则，责任归所有者，不要求亲自签。

### 2.2 子系统组成

C 0118-2019 §6《统一电子印章系统组成》列出六个子系统（a)–f)）。本手册在此基础上将 CA 归纳为独立子系统 S7（编号为本手册归纳，非 §6 原文条目），便于理解证书链。

| 编号 | 子系统 | 职责 | 标准来源 |
|------|--------|------|----------|
| S1 | 电子印章信任支撑系统 | 提供数字证书服务，是印章信任根 | C 0118 §6 a) |
| S2 | 电子印章管理系统 | 制作主体/状态发布系统/制作系统的注册与管理；申请审核 | C 0118 §6 b) |
| S3 | 电子印章制作系统 | 提供印章制作相关服务（部署于各级政务平台） | C 0118 §6 c) |
| S4 | 电子印章状态发布系统 | 发布印章状态（有效/注销等），供在线查验 | C 0118 §6 d) |
| S5 | 电子印章接入检测系统 | 制作系统接入前的合规检测 | C 0118 §6 e) |
| S6 | 电子印章应用（签章/验章） | 实际用章与验章的客户端/服务端 | C 0118 §6 f) |
| S7 | CA（证书签发） | 为制作主体/使用主体签发 X.509 证书（含单位证书、制作系统证书） | C 0118 §9 g)（§6 a) 中 CA 作为信任支撑的依赖被提及，本手册将 CA 归纳为独立子系统 S7，非 §6 原文条目） |

> [!note] 说明
> C 0118 §6 实际只列 a)–f) 六个子系统，并无独立的 CA 子系统条目；S1（信任支撑系统）以"CA 为电子印章系统提供数字证书服务"的方式涵盖 CA。本手册把 CA 单列为 S7 仅为便于讨论证书链与 R1/S3 证书体系分离（见 §5），非标准原文。

### 2.3 平台主体角色三角与运营角色（平台建模层）

标准层（§2.1）给出"签章者/制章者/使用主体/制作主体"等术语；本平台在领域模型层将其收敛为**主体三角 + 运营角色**（镜像见项目 `CONTEXT.md`「电子印章角色模型」段）。经 8 份标准 + 代码 + 对抗验证确认**主体三角不可合并**。

**主体三角（principal roles）**：

| 平台角色                 | 标准对应                                                    | 性质                         | 关键边界                 |
| -------------------- | ------------------------------------------------------- | -------------------------- | -------------------- |
| **owner / 主体**       | 签章者(GB/T 38540 §3.7)/使用主体(C 0118 §3.3)/所有者(C 0120 §3.4) | **实体**（单位章=单位/USCC；个人章=用户） | 持所有权 + 注销/挂失权        |
| **operator / 经办人**   | 经办人(C 0118 §9.3.1)/操作员(GB/T 33481 §5.2)                 | 自然人（代理人）                   | 代办制章申请，**非**所有者，无注销权 |
| **grantee / 被授权用章人** | 用章申请人(C 0118 §9.4.2)/申请人(GB/T 33481 §6.3)               | 自然人（用章末端）                  | 经授权用章，**无**注销权       |

最强分离依据：电子签名法 §34(一)「以**本人身份**或以**所代表的人的名义**」（法律根：持钥签字人≠被代表实体）；《电子印章管理办法》§21「**谁所有、谁控制，谁签章、谁负责**」（四动词总纲）；GB/T 33481 §6.3 用章申请(申请人)→审核(审核员)→操作(操作者)三角色互异。

> [!warning] 三角色不可合并
> 「签章者 = 操作员/申请人 = 同一个人」是**运行时巧合**（一人戴多帽），不是领域身份。模型按**权责**建模：owner 持注销权、grantee 无注销权、operator 是代理人；三者合成一个角色是平台明列的 `_Avoid_`。**唯一例外**：个人名章（C 0120 type 05 电子名章）——owner=申请人=签章人=本人，三角坍缩，属退化特例（《办法》§3 限定「用于单位事务办理」）；单位章（规范情形）必须撑开三角。

**申请人脱重载**：「申请人」非标准术语（§2.1），但平台须按生命周期阶段二分，不可混称：

- **制章-申领人**（registration applicant）= 制章申领的系统提交方（单位章由经办人代办、个人章由本人），即 §3.1 申领的提交人，属 operator 侧；
- **用章-申请人**（sign-use requester）= **grantee** = 逐次用章单据的发起方（§3.3 用章），「用章」末端角色。

标准本就用不同词（C 0118 §9.3.1「申领」vs §9.4.2.2「签章申请」）；两阶段是不同领域行为，代码两服务同名 `applicantId` 是残留重载。

**certList 装谁的证书（平台策略 ADR-0006）**：标准沉默（§1.2）。平台采**主体证书模型 Model A**——`certList=[主体证书]`（单位章=单位证书/个人章=用户证书），稳定、授权变更不重签；用章门禁靠 `SealAuthorization`(grantee) 承担，`cert∈certList` 因签章人恒用主体证书而自动满足。个人追责下沉到 `seal_usage_log.userId`（业务留痕，非密码学）。

**运营角色（operational roles）**——平台 RBAC（`services-basic`，7 角色）。法理依据 **GM/T 0031-2014** §3：定义**制章人**（=管理员，人）与签章人为术语，并以「印章管理员管理…安全审计」为电子印章管理系统功能。

| 角色 | RBAC | 标准依据 | 边界 |
|---|---|---|---|
| 审批人 / 用章审核员 | `SEAL_APPROVER`(22) / `SEAL_USAGE_REVIEWER`(26) | C 0118 §9.4.2.3、GB/T 33481 §5.2/§6.3 | 守制章门 / 用章审核门 |
| 制章人 | `SEAL_MAKER`(21) | GM/T 0031 §3 制章人（=管理员，**人**） | 执行 makeSeal 的自然人 |
| 印章管理员 / 主管 | `SEAL_ADMIN`(20) / `SEAL_MANAGER`(25) | GB/T 33481 §6.2「专人保管」 | 管理层，持注销/挂失权（管理角色 OR owner） |
| 审计员 | `SEAL_AUDITOR`(24) | GM/T 0031 安全审计功能 | **只读**，无写/签/批权 |

> [!note] 三层「制章X」+ 职能分离（SoD）
> 同一「制章」前缀指三种不同事物：**制章人**（GM/T 0031 §3，自然人管理员，=平台 `SEAL_MAKER`）/ **制章者·制章机构**（GB/T 38540 §3.6，**机构**，持单位证书、担责，=R1）/ **印章制作系统**（C 0118 §6c，软件基础设施，=S3，见 §5）。GM/T 0031 把制章人定义为「人」、GB/T 38540 把制章者定义为「机构」——两标准的系统性差异；平台 RBAC 的「制章人」取 GM/T 0031 的人层语义。
>
> **SoD**：平台经 V2 角色优化（`V2__seal_role_optimization.sql`）强制职能分离——`SEAL_ADMIN` 已剥离制作与用章权（管理员不制章、不签章），并设角色互斥；审计员只读。权责不交集是 GM/T 0031 角色分离在 RBAC 的落地。

## 3. 三大业务流程（主题二之二）

### 3.1 申领/申请流程（C 0118 §9.3.1）

1. **使用主体**（机构或个人）向**制作主体**申领电子印章。
2. 制作主体核验申请材料（表 1：上级单位加盖公章的申请文件 / 经办人身份证 / 经办人联系方式 / 设立该单位的有关文件）。
3. 制作主体登录电子印章系统录入申请信息，字段含：单位统一社会信用代码、单位名称、**法定代表人姓名/身份证/手机**、**经办人姓名/身份证/手机**等。
4. 由 CA 颁发证书——**一个数字证书只能对应一枚电子印章**。
5. 制作主体向使用主体交付印章。

> [!tip] 关键发现
> §9.3.1 d) 的申请字段**强制区分"法定代表人"和"经办人"**——经办人 ≠ 法定代表人 ≠ 印章所有者（单位）是标准支持的标准申请模型。**申请人不要求是所有者本人**。技术标准（GB/T 38540、C 0119）对申请工作流完全沉默，止于"生成/验证"；申请流程的标准化全部归于 C 0118 §9.3 与《电子印章管理办法》§13/§14。

> [!note] 发起方分层（法律层 vs 系统层）
> 制章申领的「发起方」是分层的，勿塌成单一角色：
> - **法律/业务层**（C 0118 §9.3.1 a）：申领法定发起方 = **使用主体（机构 = owner = 委托方）**——「电子印章使用主体向电子印章制作主体提交申领材料」。
> - **操作/系统层**（GB/T 33481 §5.2）：系统提交签名方 = **经办人/申领人（代理人）**——「发起申请的操作员…签名」。
>
> 机构无登录账号，由经办人登录代办、申领**为**机构（`orgCreditCode`），再交制章人（`SEAL_MAKER`）制作——**委托方 → 代理人 → 制作方**三段。这是 §2.3 主体三角（owner/operator）在制章链路的投影。

### 3.2 制章流程（GB/T 38540 §6 / GB/T 33481 §5.2）

1. 制作主体在制作系统（S3）中录入/生成印章信息（`eSealInfo`：印章头 + 属性 + 图像）。
2. 将持章人证书写入 `certList`。
3. 用**制章者（机构）的单位证书私钥**对 `eSealInfo` 签名，生成 `signedValue`（§6.1.5）。
4. 装配 `cert`（制章者证书）+ `signatureAlgID` + `signedValue`，形成 SESeal。
5. （本平台硬约束）印章交付前置为「已制作」（`sealData != null`），而非「已备案」——公安部备案刻意不实现（私有部署）。

GB/T 33481 §5.2 原文："电子印章制作由**电子印章制章系统**制作电子印章，电子印章由**制章者私钥**进行数字签名"——同一句里把 S3（系统制作）与 R1（制章者私钥签名）分开，印证 §5 的 R1/S3 区分。

### 3.3 用章/签章流程（GB/T 38540 §7 / C 0118 §9.4.2）

签章时生成 SES_Signature（结构见 §4.3.2），核心是**签章者证书 `cert` + 私钥生成的 `signature` + 强制证书列表比对**：

- GB/T 38540 §7.2 a)3)（**关键强制**）："提取印章中的签章者证书信息列表，判断所选签章者证书**是否在列表中**……比对失败，返回错误代码并退出签章流程。"§7.3 c) 验证同样强制——只有 `certList` 中的证书才能用这枚印章签章。
- C 0119 §6 `cert` = "执行本次签章操作的电子印章所有者数字证书"。GM/T 0112 §7.5 d) 用词为「**操作人**」，与"所有者"分离。

**集中式 vs 分散式用章（C 0118 §9.4.2.4）**：
- **集中式**：申请人在系统内签章（印章私钥托管在平台/网关侧，用章人发起调用）。一个自然人可被授权用多枚章，是 C 0118 §9.4.2.4 b) 的标准场景。
- **分散式**：由**电子印章管理员**对用章对象签章，管理员应核对用章申请者/对象/审核员/印章名称。持章人为机构时，标准明确允许并规范了"管理员/经办人代表机构持有与管理"的代理模型，要求设置审核员/申请者等内部角色分离。

> [!note] 本平台工程边界
> `drawing-sign-common` 只有 `Sm3Util`（客户端摘要）+ `SesSignatureAssembler`（客户端 ASN.1 装配）+ `UocsSignClient`（调网关），**SM2 签名/SM4 加密的密码运算在 UOCS 签章网关侧（私钥不出网关）**——这正是集中式用章的工程分水岭。分散式用章下，私钥位于业务系统侧 UKey。

## 4. 印章生命周期与验章

### 4.1 生命周期阶段

印章从申请到终止，经历：申请 → 审核 → 制作 → 交付/启用 → 使用 → （停用/恢复）→ 注销。维护操作以 GB/T 33481 §5.3 为准（见 §4.2）。

### 4.2 生命周期状态机

**标准依据**：GB/T 33481-2016 §5.3 的维护操作清单为五项——**查看、注销、停用、恢复、变更**。注意：**该清单不含"吊销"**。

> [!warning] 关于"吊销/revoked"（重要）
> 标准层面的印章终态操作是"**注销**"。"吊销/撤销"是**证书生命周期概念**（GB/T 38540 §6.3 c"证书是否被撤销"、§7.3 撤销列表），不是印章状态机状态。C 0118 §9.3.3 的挂失流程是"登录系统挂失原有电子印章 + 申请新印章"，并未使用"吊销"措辞；C 0118 §9.3.4 的终态操作叫"注销"。本手册为合并表达证书被 CA 吊销导致的印章失效场景，使用"注销/失效"状态——这是对 GB/T 33481 §5.3"注销"+ 证书吊销场景的**合并归纳，非标准状态名**。

> 本表把"注销/失效"作为合并终态（含挂失后注销、证书被 CA 吊销导致的印章失效），非标准状态名。标准层面的印章终态操作统一为 GB/T 33481 §5.3 的"注销"；证书吊销是证书层概念，会**导致**印章失效，但不应直接搬为印章状态机的一个独立"吊销"状态。

### 4.3 验章

验章（验证电子签章 SES_Signature）分两个层面：印章本身的有效性 + 签章数据的有效性。

#### 4.3.1 验章两阶段

GB/T 38540 §7.3 把验章分为：先验证印章（§6.3 印章验证四步，见 §1.5），再验证签章数据（§7.3：提取印章 certList 比对、验证签名值、验证证书链、验证有效期）。状态校验（印章是否被注销/吊销）在 GB/T 38540 中属于 §7.3 验章阶段或外部状态发布系统（S4）查询，**不在 §6.3 印章验证四步内**。

#### 4.3.2 SES_Signature 结构

GB/T 38540-2020 §7.1.1 定义 SES_Signature（关键字段）：

```
SES_Signature ::= SEQUENCE {
    toSign          TBS_Sign,      -- 签章信息（待签内容）
    cert            Certificate,   -- 签章者证书
    signatureAlgID  OBJECT IDENTIFIER,  -- 签名算法标识
    signature       BIT STRING,    -- 签章者签名值
    timeStamp       TimeStamp      -- 时戳
}
```

> [!note] 字段名 vs 类型
> 第一个字段名是 `toSign`，其类型为 `TBS_Sign`（签章信息）。`cert` = 签章者证书（执行本次签章操作的电子印章所有者数字证书），`signature` = 签章者用其私钥对 `toSign` 的签名，`timeStamp` = 时戳。

#### 4.3.3 本地验证 vs 在线验证

| 验证方式 | 校验内容 | 依赖 |
|----------|----------|------|
| **本地验证** | 用制章者证书验印章真实性；验证签名值、证书链、有效期[^33481-77] | 离线，仅需印章/签章数据 + 证书链 + CRL |
| **在线验证** | 本地全部项 + 联网查询印章状态（是否被注销/吊销） | 在线，依赖状态发布系统（S4）或 OCSP/吊销列表 |

## 5. 概念辨析：制章机构（R1）与印章制作系统（S3）（主题三）

> 本节是面向平台领域建模的长期参考性概念辨析，核心结论约束 `service-seal` 等模块的角色映射与领域模型。

### 5.1 一句话结论

**不是同一个东西，也不应在概念与职责上合并——但归属层可以同属一个组织（一个制章机构自建、自运营一套制作系统是允许的、且是本平台的常见形态）。** R1（制章机构 / 制章者 / 制作主体）是承担法律责任的**机构**（人/组织），S3（印章制作系统）是被 R1 使用的**技术工具/软件基础设施**；二者是"主体用工具"的关系。C 0118 §6 b) 刻意把二者作为并列的两个注册对象（"电子印章管理系统提供电子印章**制作主体**、电子印章状态发布系统、电子印章**制作系统**的注册和管理服务"），不可混同。

### 5.2 概念区分（机构 vs 系统）

| 维度 | R1 制章机构（制章者 / 制作主体） | S3 印章制作系统 |
|------|---------------------|---------------------|
| 范畴 | 人/组织/机构（法定主体） | 软件/系统/基础设施（技术工具） |
| 持有证书 | **制章者证书 = 该机构的单位证书**（GB/T 38540 §3.6 注） | **电子印章制作系统证书**（C 0118 §9.2.3，由 CA 印章根签发，用于身份鉴别） |
| 承担责任 | 法律责任（《电子印章管理办法》第七章；数字签名不可否认性落在机构） | 无法律责任能力（系统本身不能被追责） |
| 标识 | 统一社会信用代码、单位名称（C 0122 §5.3 `mspUnitCode`/`mspUnitNameCn`） | 系统名称、系统 IP:端口、系统公钥（C 0118 §9.2.3 a)） |
| 在 C 0118 §6 b) 中 | 作为"制作主体"被注册 | 作为"制作系统"被注册（**并列、独立**） |
| 在业务流程中 | **登录**电子印章系统进行操作（C 0118 §9.3.1 d)） | 被登录、被使用的工具（C 0118 §9.3.1 g)） |

**关键判据**——GB/T 38540 §3.6 的注："电子印章中的制章者证书应是**该机构的单位证书**"。证书归属是机构而非系统，这是法律责任归属的直接体现：数字签名的不叮抵赖性落在"机构"上，而不是落在"软件系统"上。

**归属层允许同一组织**：《电子印章管理办法》第二十条"电子印章制作管理单位**可以自行**或者委托相关单位具体实施电子印章的制作"——"自行"即自制、自用、自管一套制作系统。本平台正是此形态：运营方是制章机构（R1），其 `service-seal` 模块实现制作系统（S3）的功能。

**职责层不得合并**：即使归属同一组织，"制章机构"与"制作系统"在概念模型、注册关系、证书体系、审计链上仍必须保持分离——法律责任归属、审计可追溯、C 0118 §6 b) 并列注册、制章者证书归属机构而非系统、法定监督责任始终在 R1，五条理由共同要求二者分离。

### 5.3 证书命名差异（制章者证书 vs 制章系统证书）

C 0118 §6 b) 把"制作主体注册"与"制作系统注册"分离，对应两套证书体系：

| 推送/注册对象 | 字段特征 | 性质 |
|----------|----------|------|
| **制作单位**（C 0122 §5.3 `taskCode=1021`） | `mspUnitNameCn`/`mspUnitCode`（统一社会信用代码）/`mspUnitAddress`/`approveUnitName`（制作资格授权单位）/`operator`（经办人）/`keyPlus`（制作**单位**证书） | **机构（R1）** |
| **制作系统**（C 0118 §9.2.3 注册） | 系统名称、系统 IP:端口、系统所在省市、系统公钥 → 签发"电子印章制作**系统**证书" | **系统（S3）** |

**命名差异（系统性）**：**C 0120 §6.1/§6.3/§6.5/§8 全篇**统一用"**制章系统**"措辞（§6.1 ASN.1 注释、§6.3 标题"制章系统证书"、§6.5"制章系统对印章信息域的签名值"、§8 验证流程 d)"验证电子印章制章系统证书的有效性"）；而 GB/T 38540 §3.6 注 + §6.1.3 用"**制章者**"措辞。这是两个标准体系对同一字段的系统性命名差异，论断方向正确但不止 §6.1 一处——实现者按不同标准对接会看到两种命名，二者指同一字段（印章里签名所用证书）。

**落地启示**：领域模型上 `SealMaker`（R1）与 `SealMakingSystem`（S3）应是两个概念；签名链上印章信息域用制章者（机构）单位证书私钥，系统证书用于系统间通信；审计字段同时记录操作主体（经办人）与制作点（S3 实例）。

> [!note] 整合说明
> 本节为单次辨析（2026-08-04）的整合版，核心结论与证据已完备；5 条理由的逐条论证、落地详细分点等展开从略，需要时可回查标准原文（GB/T 38540 §3.6、C 0118 §6 b)/§9.2.3/§9.3.1、《电子印章管理办法》第二十条）。

## 7. 易踩坑与命名差异

### 7.1 关于状态名的声明

本手册中出现的印章状态名（"正常/停用/注销/失效"等）是**本手册的归纳**，用于组织状态机描述。**标准层面**，GB/T 33481 §5.3 给出的是**维护操作清单**（查看/注销/停用/恢复/变更），而非一组带编号的状态枚举。"吊销/revoked"**不是**印章状态机状态，是证书生命周期概念——见 §4.2 与易踩坑 1。

### 7.2 易踩坑清单

1. **印章"吊销"非标准状态（GB/T 33481 §5.3 无"吊销"）**。GB/T 33481 §5.3 维护操作清单只有"查看/注销/停用/恢复/变更"五项，没有"吊销"；标准层面的印章终态操作是"**注销**"。C 0118 §9.3.3 挂失流程是"挂失原章 + 申请新章"，C 0118 §9.3.4 终态操作叫"注销"。"**吊销/撤销**"是证书层概念（GB/T 38540 §6.3 c"证书是否被撤销"、§7.3 撤销列表）——证书被 CA 吊销会**导致**印章失效，但不应把"吊销"直接搬为印章状态机的一个独立终态，否则读者会误以为标准定义了"吊销"印章状态。

2. **验章流程跨标准差异：GB/T 38540 §6.3（四步）vs C 0120 §8（五步）**。GB/T 38540 §6.3 印章验证为四步（a 格式 / b 签名值 / c 制章者证书 / d 有效期），**不含状态校验**（状态校验在 §7.3 验章阶段或外部状态发布系统）；C 0120 §8 印章验证为**五步**且含在线状态校验（a 格式 / b 签名值 / **c 状态有效性（联网在线查验或吊销列表查印章是否被吊销）** / d 制章系统证书有效性 / e 有效期）。两个标准的步骤数与顺序不同：**按 GB/T 38540 实现时勿把状态校验塞进 §6.3，按 C 0120 对接政务平台时勿漏状态校验 c 步**。

3. **"制章者证书"（GB/T 38540）vs"制章系统证书"（C 0120）命名差异**。C 0120 §6.1/§6.3/§6.5/§8 **全篇**用"制章系统"措辞，与 GB/T 38540 §3.6 注 + §6.1.3 的"制章者"措辞存在**系统性命名差异**（不止 §6.1 一处）。二者指同一字段（印章信息域签名所用证书），实现者按不同标准对接会看到两种命名，注意勿误判为两个不同证书。详见 §5.3。

4. **持章人身份无明文字段，仅靠 X.509 证书**。标准刻意不存姓名/身份证明文，持章人身份仅通过证书 CN/SAN 承载。任何"申请人=持章人=登录用户"的约束都是平台策略，不是标准要求——技术结构层把印章只绑证书，业务层（C 0118 §9.3.1）强制区分法定代表人/经办人，明确支持经办人≠所有者的代理申请。
