Module Federation 原理课 · 第 1 课 · 阶段 A｜地图与地基

大局观：Module Federation 到底在解决什么问题

你项目里已经在用 Module Federation（模块联邦），但它是个黑盒。这一课不碰任何配置——只给你一张地图和一个能装进脑子的核心心智模型。之后所有细节（模块系统、打包、运行时、shared），都会挂回到这张图上。

一句话收获：你能用一句话说清 MF 解决的问题，并在脑中装下它的核心动作——一个应用在运行时，把另一个独立部署应用的一块代码，拉过来当自己的模块用。

1. 先看没有 MF 的世界：一块"巨石"前端

传统前端是一个大应用：所有页面、所有团队的代码挤在一个仓库里，一次 build（构建） 打成一坨 bundle（打包产物，即最终发给浏览器的 JS 文件），一次 deploy（部署，即发布上线）。这块"巨石"会带来三个痛点：

  1. 改一个小地方，整体重构建重部署

    购物车团队改一行，也要把整个应用重新打包、整体上线。

  2. 多个团队挤在一个构建里互相踩脚

    谁的代码出问题，可能拖垮整个构建；谁都不敢乱动。

  3. 想复用别的应用里的组件，很难

    要么复制粘贴代码（永远不同步），要么发一个 npm 包（慢，见第 3 节）。

一个熟悉的类比：后端的"单体 → 微服务"

后端早就从"单体应用"演进到了 microservices（微服务，即把大系统拆成一堆可独立开发、独立部署的小服务）。前端也想要这种"各团队独立开发、独立上线"的自由——Module Federation 就是把这个思路搬到浏览器里。难点在于：浏览器里的代码最终要合到一起跑，这正是 MF 要巧妙解决的。

2. MF 的一句话定义 + 核心心智模型

官方定义（记住这一句就够了）：

Module Federation 让多个独立构建、独立部署的 JavaScript 应用，在运行时互相共享、加载代码。
— 综合 module-federation.io 与 webpack 官方

这句话里藏着两个角色，整门课都围着它俩转：

角色它做什么一句话记忆
remote（远程 / 被调方）把自己的一部分代码 expose（暴露，即"挂出去供别人取用"） 出来。它独立构建、独立部署，有自己的网址。"我把我的组件挂出来，谁要谁拿。"
host（宿主 / 调用方）用户真正打开的那个站点。在代码跑起来时（运行时），去 remote 的网址把那块代码拉回来，当自己的模块直接用。"我用的时候，现去你那儿把代码取过来。"

3. 为什么"运行时"这三个字是全部的重点

"在应用之间共享代码"有三种做法。前两种你可能都见过，只有第三种是 MF——差别全在"什么时候把代码合进来"：

做法代码何时合进来remote 改了之后问题
复制粘贴手动，一开始host 要手动再抄一遍永远不同步
发 npm 包构建时（打进 bundle）remote 发版 → host 升级依赖 → 重新构建 → 重新部署慢；耦合在构建阶段
Module Federation运行时（现拉）remote 独立部署新版，host 什么都不用动，用户下次刷新就拿到新代码——（这正是它的价值）

所以一句话：MF ≈ 把 npm 包的"共享"从构建时挪到了运行时。正因为是运行时现拉，remote 才能真正做到"独立部署、随时上线"，前端的"微服务"才成立。

锚定到你的真实项目

你项目里写的那句 remotes: { ... }，其实就是在告诉 host："这些远程应用的地址在这儿，运行时去这些地方拉代码。" 现在你还不用懂它的语法——记住它表达的是上面这张图就行。到阶段 B我们会把这句配置逐字拆开。

诊断 · 一个最常见的误解

先想 30 秒，再点开。

既然 host 要用 remote 的代码，那构建时把它打进 host 自己的 bundle 里不就行了？

不对，而且正好相反。如果构建时就打进去，它就退化成了普通依赖（等同复制代码 / npm 包）：remote 一改，host 就得重新构建、重新部署——MF 的全部价值就没了。

MF 的做法是：host 的产物里只留一个"去哪拉、拉什么"的指引，真正的 remote 代码在运行时才通过网络取回。所以 remote 能独立发新版，host 原封不动。"不在构建时打进来"正是 MF 的精髓，不是缺陷。
