自动触发机制：skill 靠什么决定该不该上场

你以为 skill 是按名字调用的。其实它靠 description 被匹配——而 using-superpowers 给了一条几乎不讲理的强制规则。 搞懂这一层，「该用时没触发」就从玄学变成可诊断、可主动控制的问题。

这节课的收获：给一句用户请求，你能预测哪个 skill 该触发、为什么有时不触发、以及怎么改写请求让它必触发。

1. 入口只有一个：Skill 工具

在 Claude Code 里，你（或 agent）不「加载」一个 skill，你 invoke（调用）它。 唯一的入口是 Skill 工具。调一次，skill 的正文就被读进上下文，agent 按它走。

那么问题来了：agent 凭什么决定调哪个、调不调？ 这就是你要的「触发机制」。它分两层。

2. 两层机制（全课的核心）

Tier 1 — using-superpowers：常驻 bootloader

你在每次会话开头都能看到一段以 <EXTREMELY_IMPORTANT> 包起来的注入文本—— 那就是 using-superpowers skill 的全文。它为什么每次都出现？因为它的 description 是：

Use when starting any conversation — establishes how to find and use skills, requiring skill invocation before ANY response…

「任何对话开始时」→ 每次都匹配 → 每次都注入。它注入的不是某个能力，而是「调度总则」本身—— 「进任何回复前先查 skill、1% 可能就 invoke、process 先于 implementation」这三条军规，全靠它常驻在 system prompt 里强制执行。

Tier 2 — 其它 13 个 skill：按需 invoke

其余的 skill（brainstorming、systematic-debugging、test-driven-development…） 不会自动注入。它们躺在那里，等当前任务匹配上自己的 description，再被 Skill 工具按需调起。

一句话记住这层关系：

using-superpowers 是调度员，其它 skill 是被调度的人。调度员一直在岗，被调度的人要按铃才来。

3. description 就是触发契约

每个 superpowers skill 的描述都以 「Use when…」 开头。匹配发生在 description 文本 上， 不在 skill 名字上。所以诊断「为什么没触发」的第一步，永远是去读它的 description。

看四个真实的 description（原文，未改写）：

Skilldescription（触发契约）锚词
systematic-debugging Use when encountering any bug, test failure, or unexpected behavior, before proposing fixes bug / 失败 / 异常
brainstorming You MUST use this before any creative work — creating features, building components… 创造性工作 / 建功能
verification-before-completion Use when about to claim work is complete, fixed, or passing, before committing or creating PRs 声称完成 / 提交前
test-driven-development Use when implementing any feature or bugfix, before writing implementation code 实现功能 / 修 bug

看出来了吗？触发词就埋在 description 里。你的请求里有没有「bug / 失败 / 异常」「建功能」「完成了」「实现」这类词， 直接决定 Tier 2 的匹配成不成立。

4. 调度员的三条军规

using-superpowers 常驻注入的，是这三条：

  1. 次序在前：查 skill 发生在任何回复之前——包括澄清提问、探代码、读文件之前。
  2. 门槛极低：只要有 1% 的可能一个 skill 适用，必须 invoke。「不确定要不要用」→ 用。
  3. process 先于 implementation：
    • 「帮我做个 X」→ brainstorming 先上（先理需求/设计），再谈实现。
    • 「修这个 bug」→ systematic-debugging 先上（先定位根因），再谈修。

还有那张 Red Flags 表——它列的是「你在合理化跳过 skill」的念头： 「这就是个简单问题」「我记得这个 skill 怎么用」「这不算个任务」…… 你「觉得不需要」本身，就是表里的一面红旗。

5. 为什么你的触发「不稳定」

因为 Tier 2 是模型每一轮做的判断：这个任务，匹配上哪个 description？判断靠的是你请求里的词。 同样意图，措辞不同 → 匹配不同 → 触发不同。

请求措辞能不能稳匹配为什么
「这个功能有时候快有时候慢，帮我看看」 ❌ 大概率不触发 只有「慢」这种模糊感受，没踩中 bug/失败/异常 的锚词
「这是个性能 bug：复现 X，预期 Y，实际 Z」 ✅ 稳稳触发 systematic-debugging 「bug」+ 复现 + 预期/实际——description 的锚词齐了

所以触发的把手在你手里：触发活在请求的动词和症状里。 改写请求 = 改变匹配。 这不是玄学，是可主动控制的。

还有最稳的一招：显式点名。「用 systematic-debugging 帮我排查」—— 显式 invoke 永远比隐式匹配可靠。显式 > 隐式。

练习 · 预测触发

下面三句用户请求，第一个该触发的 superpowers skill 是哪个？选完即时给反馈。

Q1.「帮我修这个 bug，报错日志在下面」——第一个该触发的 skill？

Q2.「我想做一个 XX 功能」（你还没问需求）——第一个该触发的 skill？

Q3.「改好了，应该能跑了」（但还没跑测试）——哪个 skill 在拦你？

练习 · 诊断漏触发

先自己想 30 秒，再点开看答案。

「这个功能有时候快有时候慢，帮我看看」——为什么 systematic-debugging 可能没触发？怎么改写让它必触发？

为什么没触发：systematic-debugging 的 description 锚词是 bug / test failure / unexpected behavior。原句只有「慢」这种模糊感受，一个锚词都没踩中， 模型判断「相关性不足」→ 跳过 → 直接猜个原因。

怎么改写（三档，从隐到显）：

  • 补锚词：「这是个性能 bug，偶发，复现步骤 X，预期 Y、实际 Z」
  • 给症状：「这个功能有异常行为：压测下 P99 会突刺」
  • 显式点名（最稳）：「用 systematic-debugging 帮我系统排查这个性能问题」

记住：显式 invoke > 隐式匹配。当你知道自己要哪个 skill 时，直接点名，别赌模型猜对。

「帮我看一下这段代码」——为什么可能一个 superpowers skill 都不触发？

「看一下」既不是创造性工作（→ brainstorming），也不是 bug（→ systematic-debugging）， 也没声称完成（→ verification）。「看一下」是阅读/浏览，没有动词踩中任何 description 的锚词。 所以模型大概率直接读代码回答——这在 superpowers 的规则下是合理的，不是漏触发。 不是每个请求都该触发 skill；触发是为了把方法论带进来，没有方法论需求时，裸读裸答没错。
