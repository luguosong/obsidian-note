第 11 课 · 单 skill 深挖 · 第三条匝道

一个「太大、装不进一个会话」的模糊工程，怎么起步？——wayfinder

第 1 课讲过三条匝道（triage / diagnosing-bugs / wayfinder）——不从「我有个想法」直接起步、而是汇入主流程的三个入口。前两条你已在别处照过面。第三条 wayfinder（探路者）最特别：当活儿大到一个 agent 会话根本装不下、而且从这里到终点的路还笼在雾里时，它不硬冲终点，而是先画一张地图、把雾一格格推开。

一句话收获：wayfinder 把一个太大太模糊的工程，变成 issue tracker 上一张「决策票」的共享地图；它的铁律是 plan, don't do（只规划、不动手）——每张票解一个决策、一个会话只解一个，产出的是 decisions（决策）不是 deliverables（交付物）。雾一点点散尽、路清了，它不自己开建，而是汇入主流程的 to-spec，把地图上一串已定的决策收拢成一份可构建的 plan，再走 to-tickets → implement。

1. 定位：第三条匝道，专治「一个会话装不下」

什么时候该掏出 wayfinder？一手源开门见山：

A loose idea has arrived — too big for one agent session, and wrapped in fog: the way from here to the destination isn't visible yet. Wayfinding is about finding that way, not charging at the destination.
— wayfinder / SKILL.md

两个触发条件缺一不可：①太大——超出一个 agent 会话能装下的量（想想绿地新项目、一次巨型 feature 构建）；②有雾——从当下到终点的路还看不见。少了任何一个，就不该用它。

锋利的判据：和 grill-with-docs 划清界

你已经熟悉主流程开头的 grill-with-docs（磨想法 + 沉淀领域文档）。ask-matt 路由器用一句话把两者切开：

Where /grill-with-docs sharpens an idea you can hold in one session, wayfinder is for the idea you can't … it's slower and denser, so save it for exactly that, never a well-scoped feature.
— ask-matt / SKILL.md

grill-with-docs 磨的是一个会话装得下的想法；wayfinder 专治装不下的。它是这套 skill 里认知负荷最高的一条流，慢而密——普通、边界清楚的 feature 别用它，那是主流程的活。

用之前的第一个动作，是命名终点（destination，终点）。这不是走流程，而是定 scope（范围）——一手源说「naming it is the first act of charting; it shapes every ticket」。终点可以是一份待交接迭代的 spec、一个开工前必须锁死的决策，也可以是一次就地的改造（如数据结构迁移）。地图与领域无关：工程、课程内容，什么形状都能装。

2. 核心铁律：Plan, don't do —— 决策票，不是构建片

这是 wayfinder 的心脏，也是它最容易被误用的地方。地图上的每张票（ticket），解的是一个决策，不是一段要去实现的构建：

its decision tickets — questions whose resolution is a decision, not slices of a build to execute … absent [an override], produce decisions, not deliverables.
— wayfinder / SKILL.md

拿你第 9 课已经熟的 to-tickets 一对照，界线立刻清楚——这俩产出的「票」根本不是一种东西：

wayfinder 的决策票to-tickets 的纵切片
前提路还看不清（有雾）路已清，只等拆着建
每张票是一个待拍板的问题（decision）一条 schema→API→UI→test 打通的 tracer-bullet 纵切片
解它 = 决定（decide）建造（execute）
产出decisions（决策）deliverables（可运行的切片）

一句话：wayfinder 在替你「决定」，to-tickets 在替你「建造」。所以 wayfinder 是匝道、跑在主流程前面，而不是主流程的替代。

「想动手了」是个信号，不是许可

一手源点破一个特别实用的自省："The pull to just do the work is usually the signal you've reached the edge of the map and it's time to hand off."（那股「别决策了、直接开干吧」的冲动，通常说明你已经走到地图边缘、该移交了。）想动手，不代表现在就该在地图里动手——而代表雾已经散到可以交给主流程了。（除非某次 effort 在 ## Notes 里显式声明「把执行也纳进地图」，否则默认只产决策。）

3. 地图长什么样：决策的「索引」+ 一片战争迷雾

地图是 issue tracker 上一个打了 wayfinder:map 标签的 issue，它的每张票是这个 issue 的子 issue。两个要点：

  1. 地图是「索引」，不是「仓库」（index, not a store）

    一个决策只住在一个地方——它自己那张票里。地图从不复述决策，只用一行 gist（要点）+ 链接指过去。这正是你第 7 课「一处真相、别处引用」的老规矩落在这里。地图体固定五段：Destination（终点）/ Notes（本 effort 的领域、要调的 skill、偏好）/ Decisions so far（已定决策的索引）/ Not yet specified（战争迷雾）/ Out of scope（越界，永不毕业）。它低分辨率、每会话开头加载一次；开着的票不列在地图上——它们是开着的子 issue，靠查询找。

  2. 地图是「故意不完整」的：战争迷雾（fog of war）

    "The map is deliberately incomplete: don't chart what you can't yet see." 活票之外那片你隐约知道要来、却还钉不下来的决策，就是战争迷雾，写在 Not yet specified（尚待明确） 段里。解掉一张票，就推开它前方的雾，把此刻能说清的部分「毕业（graduate）」成新票——一次一点，直到路清、无票可解。

「该开票、还是留在雾里」——就一个判据

唯一的测试：你现在能不能把这个问题精确说出来——而不是能不能答出来。

  • 开票：问题已经够锋利——哪怕它被别的票阻塞、你眼下动不了，也照样开票。
  • 留在雾里（Not yet specified）：你还没法把它问得那么利。别急着把雾预切成一张张票——雾比票更粗，等前沿推到那儿，一团雾可能毕业成好几张票、也可能一张都不。

注意区分：能钉下来但越过了终点的活，不进雾、进 Out of scope（是 scope 问题，不是 sharpness 问题）；一旦发现某张已开的票其实越界，关掉它、在 Out of scope 留一行 gist，不把它算进 Decisions so far（那里只记真正走过的路）。

能取的票叫 frontier（前沿）——开着、未被阻塞、未被认领的子 issue，就是「已知世界的边缘」。阻塞用 tracker 原生的依赖关系表达（这样前沿能在 tracker 自己的 UI 里可视化，人不打开地图也看得见什么可取）。一张票认领（claim）＝动工前先把它 assign 给自己，好让并发的其它会话跳过它。每张票还带一个 wayfinder:<type> 标签，标明它靠哪种方式解——四选一：

票类型谁来解用在
grilling（默认）HITL · /grilling+/domain-modeling 一次一问大多数决策：拷问出共识
researchAFK · /research 子 agent决策卡在一个工作目录外的事实上
prototypeHITL · /prototype「它该长啥样 / 该怎么表现」——先造个粗样来反应
taskHITL 或 AFK唯一「做而非决」的类型：注册服务/开权限/搬数据等挡在决策前的手工活，靠解阻塞挣得一席

HITL（human in the loop，真人在环）＝必须和真人现场一来一回才能解，agent 绝不替真人那半边作答（一个自问自答的 grilling agent 就破了规矩）；AFK（away from keyboard，离线自动）＝agent 独立跑完。

4. 一次只解一个决策 —— 雾散尽，汇入 to-spec

wayfinder 分两种调用，但有一条铁律贯穿两者：一个会话绝不解超过一张票（唯一例外是 research 票，可并行地丢给子 agent 跑）。

  • 画地图（Chart the map）：拿松散想法起手——先 grill 命名终点，再广度优先地 grill 铺开前沿，建地图、把此刻能定的票建出来（再补一遍 blocking 边），点火 research 子 agent。这一整会话只画不解——「charting hand-resolves nothing」。（若铺开后压根没冒出雾，说明整件事一个会话就装得下、根本不需要地图——停下来问用户怎么走。）
  • 走地图（Work through the map）：拿一张地图起手，取前沿第一张票（或用户指定的那张），认领→解→记（resolution comment + 关票 + 往 Decisions so far 追一行）→ 让新毕业的雾变成新票。然后就停。

那这条匝道到底怎么汇回主流程？——雾散尽、路清了，它移交、不开建：

When the map clears, it hands off, it doesn't build: merge onto the main flow at /to-spec, which collapses the map's linked decisions into a buildable plan, then /to-tickets and /implement as usual. … go straight to /implement only when the effort turned out genuinely small.
— ask-matt / SKILL.md

默认落点是 to-spec：它把地图上一串已定的决策收拢成一份可构建的 plan，再交给你熟悉的 to-tickets（拆 tracer-bullet 纵切片）→ implement。别把地图直接甩进 implement——那会跳过「收拢」这一步、把票里的细节全丢掉；只有当这摊活其实很小时才可直连。这样整条弧就闭合了：wayfinder 先「决定」→ to-spec/to-tickets 把决定变成「构建片」→ implement 建。

  • wayfinder / SKILL.md —— 全部细节的一手源：Plan, don't do / Refer by name / 地图体五段 / Fog of war（含「开票还是留雾」判据）/ 四种 ticket 类型（HITL vs AFK）/ 两种调用（Chart vs Work through）。最高优先「读」。
