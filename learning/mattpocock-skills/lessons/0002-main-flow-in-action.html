主流程实战：用 todo CLI（命令行）跑通 idea → ship（上线）

第 1 课给了地图。这节课用一个虚构项目（一个极简 todo CLI）把它走一遍—— 每一步看做什么、问什么、产出什么、如何衔接。 走完，你就有了端到端跑通的肌肉记忆，而不是 5 个散点。

这节课的收获：面对"我想做 X"，你能说出每一格该执行哪个 skill、产出什么文件、下一步怎么接——特别是 v1.1 的 to-spec（转规格）→ to-tickets（转工单）两步，以及 implement（实现）内部的 tdd（测试驱动）+ code-review（代码评审）闭环。

演练载体：一个极简 todo CLI

设想你有个小仓库 todo-cli/（命令行待办），已经能 add / list。现在你想加一个"把任务标记为完成"的功能。就这么简单一件事——但完整地走一遍主流程。

主流程骨架（v1.1，来自路由器 ask-matt）：grill-with-docs → to-spec → to-tickets → implement(驱动 tdd、收尾 code-review) → ship

第 1 步 · grill-with-docs（有库拷问）：对齐 + 沉淀共享语言

有代码库 → 从 grill-with-docs 进。它的引擎是 v1.1 抽出的共享原语 grilling（拷问原语）：一次只问一个问题、每个带推荐答案，事实去查代码库、决策留给你，达到共识前不往下做。

你会被这样追问（每题它会先给推荐答案，你确认或推翻）：

# grilling 会问的问题样例（一次一个）
Q: "完成"是永久状态，还是可以再切回未完成？
   推荐：可来回切换（todo 常见语义）。
Q: 已完成的任务在 list 里怎么显示？
   推荐：默认隐藏，加 --all 才显示。
Q: 数据存哪？现状是 JSON 文件，要不要改？
   推荐：沿用现有 JSON（先去读了一下 storage.ts，确认了格式）。
Q: 完成动作要不要记时间戳 completed_at？
   推荐：记，后面做统计要用。

它边问边沉淀——这就是 grill-with-docs 区别于 grill-me（无库拷问）的地方（防失败模式 #2 verbosity，啰嗦冗余）：

# CONTEXT.md（项目领域词汇表，agent 每次会话都读）
## Task
一条待办。状态在 open / done 间切换。
- open：未完成，list 默认显示
- done：已完成，仅在 list --all 显示，带 completed_at

# ADR-0003（难撤销的决策，记成 ADR）
## 决定：状态机只有 open↔done 两态，不引入 in_progress
## 因为：三态会把"完成"的语义复杂化，当前无需求支撑

产出：一份对齐过的对话 + 更新过的 CONTEXT.md（领域上下文档）/ADR（架构决策记录）。下一步把这些思考固化成 spec（规格说明）。

第 2 步的分支 · 需要 runnable（可运行）答案？→ prototype（原型）+ handoff（交接）

grilling 到某个问题时，发现"光聊不清，得跑起来看"——比如你拿不准 --all 的输出要不要分组。这时走主干的一个分支：

  1. handoff 把当前对话压成一份 handoff 文档（存到系统临时目录，不重复 spec/ADR 已有的）→ 开新会话引用它；
  2. 新会话里 prototype：写个一次性的小程序，把"分组 vs 不分组"两种输出都跑出来给你看；
  3. handoff 把结论带回，在原始思路里引用它。
铁律：原型从第一天就是一次性的——留答案，删代码。别把原型演进成产品。

多数功能不绕这个分支，直接进第 3 步。

第 3 步 · to-spec：把对话综合成 spec（不 interview）

关键区别：to-spec 不再 interview（访谈式追问），只 synthesize（综合）——它把第 1 步已经聊过的东西整理成结构化 spec，发到 issue tracker（工单系统）并打 ready-for-agent（可交 agent 执行）标签。

它干的一件重要事（防失败模式 #4 ball of mud（一团泥/设计腐化））：先和你商量要在哪些 seams（接缝）上测试：

# to-spec 的 seams 讨论（优先用现有 seam、用最高 seam）
提议：在 CLI 入口层测（最高 seam，一次覆盖 parse→storage→render）。
理由：已有 cli.test.ts 在这层，不用新建 seam。
理想：全功能只跨这 1 个 seam——seam 越少越好。

spec 模板的关键段（不写具体文件路径/代码，那些会很快过时）：

# spec 关键段（to-spec 模板节选）
## Problem Statement
用户无法把任务标记为完成，只能增删查。
## User Stories
1. 作为用户，我想把任务标记为完成，这样我能追踪进度
2. 作为用户，我想用 --all 看到已完成任务，这样我能回顾
## Implementation Decisions
- 状态机：open ↔ done（见 ADR-0003）
- 沿用现有 JSON storage，加 completed_at 字段
## Testing Decisions
- 只在 CLI seam 测外部行为，不测内部实现细节
- 仿照现有 cli.test.ts 的风格

第 4 步 · to-tickets：拆成 tracer-bullet（曳光弹式）纵切片

把 spec 拆成纵切片——每片从 schema（数据结构）到 UI 到 test 全打通、能独立验证、装得进一个新窗口。每片声明谁 block 它。

# to-tickets 产出（发到 tracker，每片 ready-for-agent）
T1  完成/取消完成 + completed_at + CLI seam 测试
    Blocked by: 无 — 可立即开始
T2  list 默认隐藏 done，--all 显示
    Blocked by: T1（依赖完成态语义）
T3  --all 输出分组（done/open 分组显示）
    Blocked by: T2

它会把你拉进来确认：颗粒度合不合适？blocking edges（阻塞依赖边）对不对？要不要合并/再拆？确认后才发。

例外：wide refactor（大范围重构）不能硬塞进纵切

如果某次变更是一个机械改动横扫全仓（改一个列名、改一个共享类型），blast radius（影响面）太大，没有纵切片能单独落地变绿。这时不切纵切，改成 expand–contract（扩张—收缩）：先 expand（扩张：新旧并存，不破坏任何调用方）→ 分批 migrate（迁移：按包/目录，每批一个 ticket、都让 CI 持续集成绿）→ 最后 contract（收缩：删旧形式）。当连分批都无法单独变绿，就让它们共享一个集成分支，只在最终一个 ticket 兑现"变绿"。

第 5 步 · implement：每 ticket 一个新会话（tdd + code-review）

每个 ticket 开一个全新会话，把 spec + 这一个 ticket 喂给 implement。它会：

  1. 在 pre-agreed seams（预先商定的接缝）驱动 tdd

    红 → 绿 → 重构，一片一片来。第 3 步商量的那个 CLI seam 在这里用上。定期 typecheck（类型检查）、单测，收尾跑一次全量测试。

  2. 收尾跑 code-review（两轴，parallel sub-agents 并行子 agent）

    自一个 fixed point（固定基点）的 diff（差异），两个 sub-agent（子 agent）并行跑、互不污染 context（上下文），最后并列报告不合并重排：

    • Standards（标准轴）：符不符合 repo 的编码标准 + 一套 Fowler smell baseline（Fowler 坏味道基线）（《Refactoring》ch.3）。repo 标准覆盖 baseline；tooling 已管的不报。
    • Spec（规格轴）：忠不忠实实现 originating spec（原始规格）——缺了什么、多了什么（scope creep，范围蔓延）、实现得对不对。

    为什么要分两轴？因为一轴过另一轴可以挂：代码很规范但答非所问 = Standards 过、Spec 挂；答对了但破了规矩 = Spec 过、Standards 挂。分开报才不会被互相掩盖。

  3. 提交到当前分支

    review 过了才提交。下一个 ticket 再开新会话，重来一次。

Context hygiene（上下文卫生）：什么时候别硬撑

阶段窗口策略
第 1–3 步（grilling → spec → tickets）同一未打断窗口，中途别 compact（压缩摘要）/ 清空——它们要建立在同一串思考上
每个 implement全新窗口，从 ticket 起手
逼近 smart zone（模型清醒区，~120k）还没到 to-tickets别硬撑——handoff 换新会话继续

Q2. 你在跑第 1–3 步，对话已经很長、接近 smart zone，但 to-tickets 还没跑完。该怎么做？

推荐一手源

  • to-spec/SKILL.md —— spec 模板 + seams 讨论规则（优先用现有 seam、用最高 seam、理想只跨一个）。
  • to-tickets/SKILL.md —— 纵切规则 + blocking edges + wide refactor 的 expand–contract 例外。
  • implement/SKILL.md —— 在 pre-agreed seams 驱动 tdd + 收尾 code-review。
  • code-review/SKILL.md —— 两轴 parallel sub-agents + Fowler smell baseline + 为什么不合并重排。
  • grilling/SKILL.md —— grill-with-docs 背后的引擎（一次一题、带推荐、确认 gate）。
