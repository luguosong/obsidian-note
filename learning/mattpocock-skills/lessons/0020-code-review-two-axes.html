提交前的最后一道闸——code-review 的两条正交轴

主流程 grill-with-docs → to-spec → to-tickets → implement 的收尾：上一课 implement 每做完一片 tracer-bullet，末尾都会调 /code-review 再提交。这节看这道闸怎么把「代码合不合规范」和「代码对不对需求」拆成两条互不干扰的轴来审——以及为什么非拆不可。

一句话收获：code-review 审的是「某个固定点到 HEAD」的 diff，沿两条刻意分开的轴：Standards（标准轴）——代码合不合这个仓库的编码规范 + 一套 Fowler 坏味道基线；Spec（规格轴）——代码忠不忠实地实现了那个 originating issue / spec。两轴作为并行子 agent（parallel sub-agents）跑、互不污染上下文，最后并列报告、绝不合并也不重排。因为一个改动能过一轴、却栽在另一轴——合并只会让一轴掩盖另一轴。

1. 两轴是什么，为什么非拆不可

code-review 是 model-invoked（implement 收尾自动调它；你也能手动「review 从某点到现在的改动」）。它把审查劈成两条正交的轴：

轴问的问题参照物
Standards代码怎么写——合不合规范？仓库文档化的编码标准 + Fowler 坏味道基线
Spec代码做对没有——忠实实现需求了吗？originating issue / spec / PRD

为什么一定要分开？因为一个改动可以在一条轴上满分、在另一条轴上不及格：

Code that follows every standard but implements the wrong thing → Standards pass, Spec fail.
Code that does exactly what the issue asked but breaks the project's conventions → Spec pass, Standards fail.
— code-review / SKILL.md

回声：这和 triage 的两维正交是同一种智慧

第 6 课 triage 给 issue 打的是两维正交标签——category（是什么）× state（卡在哪），各答各的、互不替代。code-review 的两轴同理：「写得对不对」和「做得对不对」是两个独立问题，拿一个去衡量另一个只会误判。分开报告，就是不让「代码很漂亮」掩盖「做错了东西」，也不让「功能没错」掩盖「一身坏味道」。

2. 机制：parallel sub-agents，不合并、不重排

两轴不是先后跑、也不是混在一个脑子里跑，而是各起一个 general-purpose 子 agent、并行跑——一手源点破关键：

Both axes run as parallel sub-agents so they don't pollute each other's context, then this skill aggregates their findings.
— code-review / SKILL.md

为什么要并行独立？因为如果同一个 agent 先想 Standards 再想 Spec，前一轴的判断会污染后一轴（「我刚夸过这段代码干净，大概也实现对了吧」）。分成两个互不通气的子 agent，各自只带自己那一轴的 brief，才能各说各话、互不影响。

聚合时的纪律同样硬：并列放在 ## Standards 和 ## Spec 两个标题下，逐字或轻度清理，绝不 merge（合并）、绝不 rerank（重排）。收尾只给一行小结：每轴各几条 finding、每轴内部最糟的一条是什么——但不跨轴评「哪条最严重」。因为跨轴重排，正是「分轴」要防的那件事：

fixed point → HEAD 的 diff一份输入
→
Standards 子 agent规范 + 坏味道
→
Spec 子 agent对不对需求
→
并列聚合不合并·不重排

3. Standards 轴的底牌：Fowler 坏味道基线

Standards 轴不只看仓库写下来的规范——就算仓库什么都没文档化，它也永远额外带一套 Fowler「代码坏味道」基线（出自《重构》第 3 章）。这直接接上 第 1 课 4 失败模式里的 #4 ball-of-mud（设计腐化）。基线里有 12 个坏味道，每个都是「是什么 → 怎么修」，比如：

坏味道是什么 → 怎么修
Mysterious Name名字没揭示它干什么 → 改名；起不出诚实的名，说明设计浑浊
Feature Envy一个方法总伸手去够别的对象的数据 → 把方法搬到它眼馋的数据那边
Primitive Obsession用基本类型/字符串顶替一个该有自己类型的领域概念 → 给概念立个小类型
Shotgun Surgery一个逻辑改动逼你散弹式地改一堆文件 → 把一起变的东西收进一个模块

还有 Duplicated Code / Data Clumps / Repeated Switches / Divergent Change / Speculative Generality / Message Chains / Middle Man / Refused Bequest——共 12 个。

两条铁律绑住这套基线

  • 仓库覆盖基线（repo overrides）：仓库文档化的标准永远赢——它若认可某种做法，就把基线里对应的坏味道压掉。这正是第 4 课「间接层」：setup 写下的仓库现实，凌驾于通用基线之上。
  • 永远是判断题（judgement call）：每个坏味道只是带标签的启发式（「possible Feature Envy」），不是硬违规；而且 tooling（linter/formatter）已经强制的，一律跳过——评审只花在工具管不了的地方。

对比：documented-standard（文档化标准）的违反可以是硬违规；baseline smell 则永远是判断题。两者别混。

4. 跑起来：钉固定点、找 spec、并列出报告

三个机制细节把这道闸落地：

  1. 钉 fixed point（固定点）

    你给一个固定点——commit SHA / 分支 / tag / main / HEAD~5。审的是 git diff <fixed-point>...HEAD（三点，即和 merge-base 比）。开跑前先确认这个 ref 解析得出、且 diff 非空——坏 ref / 空 diff 要在这里就失败，别等两个子 agent 跑起来才发现。

  2. 找 spec 来源（Spec 轴要用）

    按顺序找：commit message 里的 issue 引用（#123 / Closes #45）→ 走 docs/agents/issue-tracker.md 取；你传的路径；docs/·specs/·.scratch/ 下匹配分支/feature 的 spec；都没有就问你。确实没有 spec，Spec 轴就跳过、报「no spec available」——Standards 轴照跑。

  3. 并列聚合出报告

    ## Standards 和 ## Spec 两段并列，逐字/轻清理；不合并不重排；收尾一行：每轴 finding 数 + 每轴内最糟，不跨轴选唯一赢家。

要点：implement 跑完，你不用再手动跑一次

implement 的收尾步骤本身就写着「Once done, use /code-review to review the work」——顺序是 tdd → 测试 → code-review → 提交，这道闸在提交前自动过一遍（每片 tracer-bullet 各一次，fixed point 是当片起点）。所以主流程里它是自动的。

你手动跑 code-review，是为了换一个 fixed point / 换一个范围审别的 diff——正如它 description 说的「review a branch, a PR, or since X」：比如一条 feature 分支跨了好几片纵切、你想把整条分支对 main 整体再审一遍，或审别人的 PR / 一段 WIP。不是因为 implement 漏跑了，而是因为你要审的范围不一样。
