第 12 课 · 单 skill 深挖 · 架构深化（治 ball-of-mud）

架构审查报告生成之后，我该做什么？——improve-codebase-architecture

你刚在真实仓库跑了这个 skill，拿到一份 architecture-review-…​.html、里面 6 张候选卡。两个卡点很自然：①要不要对每一张都开一次 wayfinder？②报告出来后到底该干嘛？答案的钥匙是一句话——这个 skill 是一条三步流程，而报告不是终点、是交接点：你只挑一张卡，agent 用 上一课刚辨过的 grilling（拷问）而不是 wayfinder（探路者） 陪你把那一张深化清楚。

一句话收获：improve-codebase-architecture ＝ Explore 找热点 → 产 HTML 候选报告 → 对你挑中的那一张卡跑 grilling 三步。报告里的 N 张卡不是每张都跑、也不是 wayfinder——你只挑一张（懒得权衡就从结尾的 Top recommendation 起），agent 用 grilling 把它的深化决策拷问出共识。它的产出是决策 / 设计，不是代码；真要落地，再接 to-spec → to-tickets → implement（小而清晰时可跳 to-spec 直接 to-tickets）。

1. 它防的是哪类失败：把「浅模块」改造成「深模块」

先定位。这条 skill 是 user-invoked（front-matter 带 disable-model-invocation: true，你得手动唤它，见 第 1 课），专治 4 失败模式里的第 4 类 ball-of-mud（设计腐化）。它要做的事，一手源写得很直白：

Surface architectural friction and propose deepening opportunities — refactors that turn shallow modules into deep ones. The aim is testability and AI-navigability.
— improve-codebase-architecture / SKILL.md

深化机会（deepening opportunity）＝把一个浅模块改造成深模块的重构。这套词汇不是它自己的——它建在 codebase-design（词汇层 skill）之上，术语必须原样用（module／interface／depth／seam（接缝）／adapter／leverage（杠杆）／locality（局部性）），别漂成 “component／service／API／boundary”。核心就一组对照：

深模块（deep）· 要的浅模块（shallow）· 避的
形状小接口 + 大实现：大量行为藏在简单接口后大接口 + 薄实现：接口几乎和实现一样复杂、只做转发
调用者得到leverage：学一点接口、换来一大片能力没杠杆：每个调用点都得懂内部
维护者得到locality：改动 / bug / 验证都收在一处复杂度散到 N 个调用点

怎么判断「它是不是浅的」——删除测试（deletion test）

一手源给的探针：“Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep.”——想象把这个模块删掉：复杂度凭空消失＝它只是个转发壳（浅，正是要深化的目标）；复杂度在 N 个调用点重新冒出来＝它在挣钱（深，别动）。配套还有两把尺：“接口即测试面”（想测到接口背后，多半是模块形状错了）、“一个 adapter 只是假想接缝，两个才是真接缝”（没有东西真的在变，就别造 seam）。

2. 骨架：这是一条「三步」流程，不是一次性报告

把整条 skill 摊平看，就三步——SKILL.md 的 ## Process 分得清清楚楚。报告只是第 ② 步的产物，前面有 Explore、后面有 grilling loop：

  1. ① Explore —— scope before you scan（YAGNI）

    深化的回报来自「让将来改这块更容易」，所以先决定往哪看再看：你若点了方向就用你的；没点就走一段 git log --oneline 找热点（反复出现的文件＝改得最勤＝深化最划算）。先读 CONTEXT.md 与该区 ADR，再用 Explore 子 agent 顺着摩擦走，逐条过删除测试。（你那份报告开头就写着：“5 个并行 reader 扫了 5 个热点区，产出 24 条摩擦，逐条过删除测试、滤掉 6 条已定 ADR”——正是这一步。）

  2. ② 产 HTML 报告 —— 候选卡，不给接口方案

    写一份自包含 HTML 到操作系统临时目录（Windows 是 %TEMP%），刻意不落进仓库，再 start 打开并告诉你绝对路径。每个候选渲染成一张卡：Files／Problem／Solution／Benefits／Before-After 图／推荐强度（Strong／Worth exploring／Speculative），结尾一段 Top recommendation。这一步的硬规矩：“Do NOT propose interfaces yet.”——先不设计接口，只抛候选，然后问你一句“Which of these would you like to explore?”。

  3. ③ grilling loop —— 你挑一张，它陪你拷问

    你选定候选后，它跑 /grilling 陪你走那张卡的决策树：约束、依赖、深化后模块的形状、seam 后面放什么、哪些测试能留存。决策一边结晶、副作用一边 inline 发生（下一节细说）。

3. 回答 Q1：6 张卡不是「每张都跑」，更不是 wayfinder

这是你的第一个问题，一手源三处措辞把它钉死——全是单选、逐个、用 grilling：

… then grill through whichever one you pick. （description）
… ask the user: “Which of these would you like to explore?” （步骤 ②）
Once the user picks a candidate, run the /grilling skill … （步骤 ③）
— improve-codebase-architecture / SKILL.md

你会想到 wayfinder，是因为刚学完它、正在模式匹配“又大又多又要分头处理→画地图”。但这里用不着拨雾——报告已经把摩擦收敛成 6 张问题已经问得很利的卡了。两者的分工，拿你上一课的判据一比就清楚：

grilling（本 skill 第 ③ 步用）wayfinder（第三条匝道）
前提范围已清：手里就是一张锋利的候选卡又大又有雾：一个会话装不下、路还看不见
它是共享原语：一次一问、拷问出共识（带确认 gate）一条匝道：画决策地图、一票一决策把雾推开
作用范围一张卡的决策树一整个模糊工程的决策全景
跑几个你挑中的那一个，一次一个地图上一串票，一会话解一张

那什么时候真的会升级到 wayfinder？

只有一种：你挑的那一张卡，一深挖发现它本身就是个“一个会话装不下、路还有雾”的巨活（比如你报告里的候选 ①——整套并行补偿引擎的拆除，牵连 ADR-0004、跨 service-seal 多处）。那时才可能把它升级成一次 wayfinder。这是例外，不是默认，更不是“对 6 张每张都开一张地图票”。默认永远是：挑一张 → grilling。

4. 回答 Q2：报告出来后，你和 agent 各做什么

第二个问题：HTML 生成后具体怎么走。分两侧看，锚在你这份 seal-platform 报告上——它有 6 张卡（4 Strong ＋ 2 Worth exploring）、Top recommendation 指向候选 ①：

谁做什么
agent 侧start <绝对路径> 打开报告、报出路径，然后只问一句“想探索哪一个？”——不先给接口方案。
你侧读这 6 张卡（Files／Problem／Solution／Benefits／Before-After／强度），挑一张。懒得自己权衡，就从结尾 Top recommendation（你这份＝候选 ① service-seal 重试引擎，leverage／locality 最大）起手。
然后 ③ grilling loop对选中项走决策树；决策结晶时 inline 触发三种副作用（见下）。

你的 6 张卡速览（挑哪张时对着看）：

强度候选（Problem → Solution 一句话）
Strong① service-seal 重试引擎：三套不一致的“异步重试+状态写入”＋@Lazy 回指 → 收敛成一个重试引擎＋抽 SealStatusChanger，消解 ADR-0004 未覆盖的第二处循环。← Top recommendation
Strong② 分发器 god-DTO ＋ 字符串 switch → 每个生命周期操作升为具名 public 方法、事务随逻辑、per-op 请求记录替代 god-DTO。
Strong③ StandardSignServiceImpl 浅 pass-through → 让标准接口承载密码学绑定契约（含 3 条已核实活 bug，独立成立）。
Strong④ CaProvider 12 方法策略接口（真有两 adapter 的只有 2 法）→ 写侧留 2 方法真 seam、读侧坍缩成直调。
Worth exploring⑤ 跨服务策略无归属模块（逐字抄、各自漂移；信任头是安全不变量）→ 每个策略提到一处 owned module。
Worth exploring⑥ 读模型 validEnd 静默失效 → 事件携带 validEnd 投影自愈（或删字段走实时），并二选一定读模型归属。

进入 grilling loop 后，决策一旦结晶，副作用就地发生（这正是它「informed by the domain model」的地方，接上你 第 10 课的领域层）：

  • 深化后的模块用了 CONTEXT.md 里没有的概念名？ → 跑 domain-modeling 把术语加进 CONTEXT.md（文件不存在就懒创建）；对话中磨利了某个模糊词，也当场更新。
  • 你用一个「承重理由」否掉了某张卡？ → agent 提议：“要不要记成一条 ADR，免得下次架构审查又提它？” ——只在这理由将来真会被需要时才记（“现在不值得”这类临时理由不记）。
  • 想比较深化后模块的几种接口画法？ → 跑 codebase-design 的 design-it-twice 并行子 agent 模式。

关键边界：它到「决策」为止，不产代码

这条 skill 的 SKILL.md 到 grilling loop 就停了——把“怎么深化”拍成决策 / 设计，不替你写实现，也不规定下游接谁。要落地就把决策接回主流程，默认 to-spec → to-tickets → implement。要不要经 to-spec？——它和 to-tickets 一样吃“当前对话”，但会多给你一份发布到 tracker 的 spec 文档 ＋ 一遍 seam pass：深化较大 / 多票、想留可交接的 spec 就走它；单个小而清晰、seam 已在 grilling 里定了的深化，可直接 to-tickets（它能直接吃对话）。越小越清晰、越能塌缩下游——和 上一课 wayfinder “effort 很小才直连 implement” 同理。
