第 10 课 · 单 skill 深挖 · 领域层（多人协作）

别人不用 ADR / skills 提交一大批改动，我的 docs/adr/ 会「失真」吗？

前三课（7 / 8 / 9）都是单人视角——文件区谁写谁读、ADR 会不会膨胀、工单层用完即冻。可现实是多人维护：另一个同事一口气推了一大批提交，却既没写 ADR、也没用这套 skill。你精心攒的 docs/adr/ 会不会就此失真、开始骗人？

一句话收获：别人的提交改不脏你已有的 ADR 条目——ADR 是「当时为什么这么定」的只增账本，谁也重写不了历史。真正会掉队的是覆盖度 / 时效：ADR 漏记了 supersede（集合成了不完整历史），CONTEXT.md 术语滞后（字典与代码打架）。而这种「文档漂移」是可见的（skill 拿文档核对代码、矛盾就举旗）且可回补的（improve-codebase-architecture 走 git log 找热点回补）；再加上 agent 从不整本读、只读你正在动工的区，没人碰的旧文档代价≈0。

1. 先分清「失真」到底指什么：改不脏 vs 会掉队

「失真」这个词其实混了两件性质完全不同的事，先拆开。

第一件：旧 ADR 条目会不会被别人改脏？——不会。回第 8 课、第 9 课：ADR 是只增账本、是长期记忆里不可变的历史记录。ADR-0005 记的是「某年某月，我们为了 X、在权衡 Y 后选了 Z」——这是一句时间戳事实。同事再怎么改代码，也改写不了当年那个决策发生过。所以不存在「旧条目被悄悄篡改成假话」这回事。

第二件：文档会不会落后于代码？——会，而且两种介质漂法不同。这才是「失真」的真身。领域层其实是两种介质（回第 7 课的维护模式），别人不同步时，它们各以不同方式掉队：

介质它本该是什么别人不同步时怎么漂漂移签名
docs/adr/
（只增账本）		 某时某人「为什么这么定」的历史决策 做了个新的架构决策，却没写一条 superseding ADR 漏记 supersede：ADR 集合成了不完整历史——旧条目仍是真的，只是过时了（没有 ADR-0012 记下这次推翻）
CONTEXT.md
（活的真相 / 术语表）		 镜像当前现实的领域术语表 在代码里改了某个概念名，却没同步字典 术语滞后：字典主动说谎——字典还写 Order，代码早已是 Purchase

一句话把「失真」摆正

失真 ≠「旧条目被改脏」（ADR 不可变，改不脏）；失真 =「文档落后于代码」——ADR 的覆盖度缺口（漏记的 supersede）+ CONTEXT.md 的术语滞后。认清这一点，下面两节就是在讲：这种掉队为什么不会悄悄发生、以及怎么补回来。

2. 为什么不会「悄悄」失真：三道让漂移显形的闸

关键不在「阻止别人制造漂移」（你管不了别人怎么提交），而在漂移一旦存在，就一定会被摆上桌，而不是默默腐蚀你的判断。这套 skill 有三道机制专门干这件事——前两道就写在你自己的 docs/agents/domain.md 里。

  1. Cross-reference with code（拿文档核对代码）

    domain-modeling skill 的硬动作之一：你一说「某处怎么工作」，它就去核对代码是否同意，发现矛盾当场质问。原文："Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"（你的代码取消的是整个 Order，可你刚说支持部分取消，到底哪个对？）——同事埋下的漂移，会在这一步变成一个被追问的问题。

  2. Flag ADR conflicts（与 ADR 冲突就举旗）

    你的 domain.md 白纸黑字："If your output contradicts an existing ADR, surface it explicitly rather than silently overriding."（若你的产出与现存 ADR 矛盾，显式点出、别静默覆盖。）于是当你在同事改过的区域动工、代码与一条过时的 ADR 打架时，agent 不会闷头照旧 ADR 办，而是举旗：「与 ADR-0005 冲突——但代码似乎已经改了，这条像是过时了。」

  3. Glossary gap 信号（字典里没有 = 信号）

    同样在你的 domain.md：需要的概念不在字典里，就是个信号——要么你在造项目不用的词（该收手），要么真有缺口（记给 domain-modeling）。同事新引入、却没进 CONTEXT.md 的术语，会以「缺口」的形式浮上来。

三道闸的共性：把漂移从「悄悄的、我以为文档还准」变成「显形的、被举旗的分歧」。你至少知道这里对不上了。

3. 漂移可回补：reconciliation 专盯别人那批提交的热点

显形之后怎么补？这套 skill 有一个专门吃「别人改了一大批、文档没跟上」的入口——improve-codebase-architecture（user-invoked）。它的 Explore 第一步，几乎是为你这个问题量身定的：

walk back a good stretch of the commit history (git log --oneline) to find the codebase's hot spots — the files and areas that keep coming up... Read the project's domain glossary (CONTEXT.md) and any ADRs in the area you're touching first.
— improve-codebase-architecture / SKILL.md

翻译成人话：它回溯 commit 历史找热点——而热点正是同事那批提交砸下去的地方；先读该区的 CONTEXT.md + ADR，再 grill 出摩擦，inline 更新领域模型：新术语补进 CONTEXT.md、load-bearing（承重）的新决策 offer 一条 ADR。这就是把漏记的 ADR 回补、把滞后的字典刷新的「重新对齐（reconciliation）」。同一份 SKILL.md 还点明 ADR 的定位——"ADRs record decisions this command should not re-litigate"（ADR 记的是不该重翻的决策），可见 ADR 是给未来当护栏的，不是代码状态的镜子。

另一条更轻的入口：grill-with-docs（它本体就是「grilling + domain-modeling」）。你下次在该区域规划新活时，domain-modeling 的 cross-reference 会自动拿 ADR / CONTEXT.md 核对当前代码，顺手把漂移补掉。

4. 诚实的边界：它是「拉取式」的，剩下的是社会问题

别把这套机制想成全自动的护城河。它是 pull-based / lazy（拉取式 / 惰性）的：漂移在你下次动工该区域时被修，不会主动全仓扫描。没人碰的角落会一直旧着——但这恰恰不危险：回第 8 课，agent 只读「动工区相关的 ADR」、从不整本读，所以没人读的旧 ADR 代价≈0。真正要命的场景是「我正要在这块动工、而这块的文档旧了」——而这块恰好被第 2 节三道闸 + 第 3 节 reconciliation 全覆盖。

skill 管不了的那一半：去社区练

这套 skill 没法强迫同事去写 ADR。让全队的 ADR 长期保持完整是社会 / 流程问题——PR 评审门禁、把「更新 ADR / CONTEXT.md」写进 definition-of-done、团队对 Nygard 式 ADR 的共识。这类判断属于「智慧」，去 GitHub Discussions / AI Hero Discord 这些有真人的场问真实团队怎么做（入口记在 RESOURCES.md 的 Wisdom 区）。skill 给你的是：漂移改不脏历史、会显形、可回补；团队纪律给你的是：漂移少发生。

推荐一手源

先读第一条——「拿文档核对代码」是漂移显形的心脏；其余按需核验：

  • domain-modeling / SKILL.md —— 漂移显形的心脏：Cross-reference with code（拿代码核对说法、矛盾即质问）+ Challenge against the glossary（术语冲突当场点出）+ ADR 三条件。最高优先「读」。
  • improve-codebase-architecture / SKILL.md —— 回补入口：Explore 走 git log --oneline 找 hot spots、先读该区 ADR/CONTEXT，"ADRs record decisions this command should not re-litigate"。
  • 你自己的 docs/agents/domain.md —— 读取端活样本：Flag ADR conflicts（矛盾显式点出、不静默覆盖）+ glossary gap 是信号。这套课讲的机制，你仓库里已经配好了。
  • grill-with-docs / SKILL.md —— 更轻的入口：本体＝grilling + domain-modeling，规划新活时顺手 cross-reference 补漂移。
