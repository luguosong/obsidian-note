第 9 课 · 单 skill 深挖 · 工单层

工单层（.scratch/）是工作记忆——用完就冻结，靠「提升」兜底

第 7 课你把工单层记成「活的状态机」，第 8 课又见了 ADR 这种「读好几年」的长期账本。那问题来了：一个 feature 一旦 ship，它的 .scratch/ 工单和 spec，是不是就死了——没人再读、没人再维护？这节课给工单层一个完整的生命周期，并借它把整张文件地图补成一张干净的「记忆二分」。

一句话收获：工单层是工作记忆（working memory）——ship 后就冻结退役，一般不再读、不再维护。这之所以安全，靠「提升（promotion）」：值得长期留的东西（架构 why → ADR、术语 → CONTEXT.md、实现 → 代码、被拒 → .out-of-scope/）在 ticket 死之前已被抬进长期记忆层。于是第 7 课的「三种维护模式」升级成「长期记忆 vs 工作记忆」的二分。

1. 先补一个遗留的错觉：「活的状态机」只是它在途的样子

第 7 课把工单层的维护模式写成「活的状态机」——靠标签 / 关闭在 tracker 上原地推进。那句话没错，但它只描述了工单层活跃在途（in-flight）时的样子，没说ship 之后它去哪了。

这一课就补上后半段。补完你会发现：工单层跟另外三块区域根本不是一类东西——它是唯一一块「用完就该退役」的区域。

2. 核心重构：四块文件区，其实分两类记忆

第 8 课我们已经看出苗头——docs/adr/「读好几年」，而工单层「只在活跃时有价值」。把这条线索推到底，第 7 课的四块区域就沿一条新轴劈成两半：

记忆类型哪些区域维护特征读取时机
长期记忆
（读好几年）		 ① 配置层
② 领域层（CONTEXT.md · docs/adr/）
④ .out-of-scope/		 第 7 课那三种模式：一次性脚手架 / 活的真相 / 只增不改账本——全是长期的 随时被相关 skill 读，跨越很多 feature
工作记忆
（用完冻结）		 ③ 工单层（.scratch/ 或 issues · spec · ticket） 第四种模式：用后冻结——不属于上面三种长期模式 只在该 feature 在途 / 评审时读

这就把第 7 课补完整了

第 7 课的「三种维护模式」其实全落在长期记忆这一侧。工单层被归为「活的状态机」，让它看着像第四种长期模式——但它不是。它真正的定位是工作记忆：一块用来把一份工作从 idea 运到 ship 的临时台面，运到了就收台。

3. 工单层的完整生命周期：活跃 → ship → 冻结退役

先认清 .scratch/ 是什么（据 setup 的 issue-tracker-local.md）：本地 markdown 版工单层，一个 feature 一个目录——

.scratch/<feature-slug>/
├── spec.md                    ← 规格（to-spec 产出）
└── issues/
    ├── 01-<slug>.md            ← 一条纵切片一份文件
    └── 02-<slug>.md            ← 按依赖 blockers-first 编号

它和 GitHub issues 是同一层的两种介质——to-tickets 产出的 ticket 内容一样，只是 blocking edges（阻塞边）一个写成文本、一个变成原生链接。生命周期也同构：

  1. 活跃在途

    第 7 课那台状态机：spec.md → 纵切 ticket → 逐片 implement，frontier（阻塞全清的那些）被一片片消费。

  2. ship

    最后一片纵切通过 code-review、合并。这个 feature 的工作结束。

  3. 冻结退役

    真 tracker（你的 GitHub）→ issue close（不是删），冻成历史、和 PR/commit 链在一起，可查但不再动。.scratch/ → 那个目录留在原地，是一张计划快照，没人再回去 sharpen 它。两者都变成「写一次就冻结」，不是活文档。

4. 为什么敢「用完即弃」——靠「提升」兜底

工单层敢做成一次性的，正因为值得长期留的东西，在 ticket 死之前已被抬进长期层。这个动作就叫提升（promotion）：

逐条对上号：

在途产生的东西提升到哪个长期层
架构级的「为什么这么定」ADR（领域层，读好几年）
新确立的领域术语CONTEXT.md（活的真相）
干出来的代码本身代码库（实现落地）
被拒的 enhancement.out-of-scope/（只增不改账本）
prototype 的验证结论折进真代码 + issue 上留 context pointer

提升的活样本：prototype

prototype（原型）skill 的收尾第一句就是提升："Fold any validated decision into the real code… The main branch keeps only the validated decision."（把验证过的决策折进真代码，主分支只留那个结论）。原型代码本身是 scratch、可丢；结论被提升，载体被丢弃——正是工单层的缩影。

所以 ticket 是可丢弃的载体：使命是把一份工作从 idea 运到 ship；运到了、keepers 都卸货进长期层了，空车退役即可。

5. 那 ship 之后还会被读吗？基本不会，两个例外

  1. code-review 找 spec

    收尾审查时，code-review 会去 docs/、specs/、.scratch/ 找与当前分支 / feature 匹配的 spec，做 Spec 轴审查——但那还是这个 feature 自己在途 / 评审阶段。

  2. 有人重启这个 feature

    回溯 / 重做同一个 feature 时才会翻它的旧工单。

除此之外，agent 不会去吃旧的 .scratch/ 目录——这正是第 8 课那条 context hygiene（上下文卫生）：只读当前 area 相关的，绝不把整仓历史工单灌进上下文。工作记忆用完即冻，长期记忆才是平时反复读的那几层。

推荐一手源

「工单层是什么、怎么退役、keepers 往哪提升」分散在这几处，均可核验：

  • setup · issue-tracker-local.md —— .scratch/ 的结构真相：一个 feature 一目录、spec.md、issues/<NN>-<slug>.md。
  • to-tickets / SKILL.md —— 一条纵切片一份文件、blockers-first 编号、frontier；本地文件与真 tracker 同产物、只边不同。
  • prototype / SKILL.md —— 「提升」的活样本：验证结论折进真代码、主分支只留 validated decision，原型载体丢弃。
  • code-review / SKILL.md —— ship 后仍被读的那个例外：收尾去 .scratch/ 等处找 spec 做 Spec 轴。
  • 你自己的 docs/agents/issue-tracker.md —— GitHub 版：close（不删）、「publish to issue tracker」＝ create issue 的活样本。
