ask-matt 的拓扑与跨会话：补回第 1 课故意推迟的那两块

第 1 课把 ask-matt（问 Matt · 路由器）的节点画成了一张地图——4 失败模式 × 主干 + 三匝道 × 全 skill 总表。 但有两块它当时只取了节点、没取结构：①这些节点在拓扑里到底是什么角色、三条匝道各自在哪一格汇回主流程；②工作跨会话时该换一个新会话还是留在原会话。这节课补全它们。

这节课的收获：给任意起点，你不止能说该用哪个 skill（第 1 课已练），还能说它在 ask-matt拓扑的哪一层、该在主流程哪一格汇回、换会话时该 handoff（交接）fork（分叉）还是 compact（压缩）continue（原地续）——即从"认节点"升级到"读拓扑 + 会话调度"。

1. 拓扑角色：一句话定整张图的结构

ask-matt 开头有一句第 1 课故意没取、但最该先读的结构定义句：

A flow is a path through the skills. Most paths run along one main flow, and two on-ramps merge onto it. Everything else is standalone, or a vocabulary layer that runs underneath.
— ask-matt/SKILL.md 开篇

一句把整张图劈成四种拓扑角色——不按"是什么 skill"分、按"它在工作流动里起什么结构作用"分：

拓扑角色结构作用判定（怎么归位）对应 skill
主流程（main flow）一条主干，"我有个想法 → ship" 绝大多数工作走的路是不是主干那串的一格？grill-with-docs / to-spec / to-tickets / implement
匝道（on-ramp）不从"想法"起步，汇入主流程会不会回到主干上？（会 = 匝道）triage / diagnosing-bugs / wayfinder
独立（standalone）跑在主干之外，不汇入用完即止、不接主流程？grill-me / prototype / research / teach / writing-great-skills
词汇层（vocabulary underneath）横向垫在底下，不在时间轴上解决的是"词"而非"流程"？domain-modeling / codebase-design

为什么要分这套角色？因为同一个 skill 名字在节点表里是平的，但它在拓扑里的位置决定了你怎么衔接它。两个最易混的点：

易混点 ①：匝道 vs 独立——判据是"会不会汇入"

prototype（原型）看起来像主流程第 2 步那个分支，但它能独立用于任何"得跑起来看"的设计问题、不必接主流程——所以它归 standalone，不是匝道。匝道的硬判据是"会不会汇回主干"：triage 的产出喂 implement、wayfinder 雾散接 to-spec；prototype 留答案删代码、用完即止。

易混点 ②：词汇层不在时间轴上——它"垫在底下"

domain-modeling / codebase-design 不是流程里的一格，你不会"先做完它们再进下一步"。它们横向铺在底下：当问题卡在"词"（一个术语模糊、一个模块该不该拆）而非"流程"时直接 reach，或让上面的 skill 带进来。正因如此，第 1 课那张总表把它们单独分组，不和流程 skill 混排。

四种角色在一张图里的样子——主干是一条横轴、三条匝道各从自己的入口汇入主干的一个站点、独立 skill 浮在主干外、词汇层横向铺底：

这张图里有一个真实细节值得点名：improve-codebase-architecture（架构体检）身兼两职——它是主干上的"代码库健康"节点（第 12 课：闲时扫深化机会、产 idea 进主流程），同时也是 diagnosing-bugs post-mortem（事后复盘）的出口（下一节细讲）。ask-matt 把它归在 Codebase health 段，而不是匝道。

2. 匝道的汇入点：三条匝道各在主干哪一格回流

知道一条路是匝道还不够——得知道它在主干的哪一站汇回，否则接错站、或重复别人已做过的工作。三条匝道的汇入点各不相同，这正是 mission success criteria 里要的那一格：

匝道起点汇入主干的哪一站为什么不走更早的站
triage 别人提的 raw issue（原始工单） → implement triage 的产出已经是 agent-ready（可交 agent 执行）的 issue（自带规格），不经 to-spec 再 synthesize——那是给对话用的
diagnosing-bugs 线上炸了 / 难 bug → 多在原地闭环（建紧反馈回路 → 修 + 回归即结） 它不常规汇入主流程；只在 post-mortem 发现"bug 落脚处无好 seam"时，把那块架构（非 bug 本身）交给 improve-codebase-architecture
wayfinder 巨大且模糊、一会话装不下 → to-spec 雾散后 "it hands off, it doesn't build"——to-spec 把 linked decisions（链状决策）收拢成可建计划；直连 implement 仅当 effort 真很小

三个汇入点都不是 to-tickets，这是个有意的规律：匝道汇入的是主干上它该进的那个阶段，而 to-tickets（转工单）是 to-spec 紧接的下游——只有你自己从 spec 来才到它。这也呼应第 1 课那个诊断题：to-tickets 产出的 ticket 已 ready-for-agent，不该再 triage。

ask-matt 原文对三条汇入点的措辞——triage: "which /implement later picks up"；diagnosing-bugs: "post-mortem hands off to /improve-codebase-architecture"；wayfinder: "hands off, it doesn't build... merge onto the main flow at /to-spec"。
— ask-matt/SKILL.md

3. Crossing sessions：fork 一个新会话，还是 continue 原会话

工作长了要换会话或减负时，有两个选择，第 2 课只借 handoff 讲了 context hygiene——这里讲全。ask-matt 用一句话钉死它们的区别：

/handoff forks; /compact continues.
— ask-matt/SKILL.md
/handoff · fork（分叉）/compact · continue（原地续）
会话压成 markdown 文件，开一个新会话引用它留在同一会话，让早期轮次被摘要
历史逐字历史完整保留在文件里早期轮次被压缩成摘要
何时用线程快满 / 要岔出去（如进 prototype 会话）阶段间有意打断、不在意逐字细节时

判据一句话：你要的是一个全新会话（连当前对话也换掉）→ fork；你要的是继续这个对话、只是减负 → continue。两者解决的问题不同：handoff 是换会话的桥，compact 是不换会话的减负。

原型绕行回路：handoff 在这里用了两次、且双向

第 2 课讲主流程第 2 步那个 prototype 分支时，handoff 只露了一面。其实那是一条绕行回路，handoff 用了两次、而且方向相反：

grilling 到某问"光聊不清，得跑起来看"
→
handoff 出压成文档·fork 到新会话
→
prototype一次性小程序·留答案删代码
→
handoff 回把结论带回·在原思路里引用

两次 handoff 都是 fork（都换了会话），只是方向相反——一次出、一次回。这正是 handoff 被叫作"两个 context window 之间的双向桥"的原因。

一条警告：别在阶段中途 compact

ask-matt 明确——don't compact mid-phase（别在阶段中途压缩）。主流程的 grill → spec → tickets 这串要保持在一个未打断的窗口里（它们建立在一串思考上）；compact 只放在阶段之间的有意打断。中途 compact，agent 会 lose its way（迷失方向）——这正是第 2 课 context hygiene 表那几行的出处。窗口快爆还没到 to-tickets？那就别 compact、直接 handoff fork 出去（见第 2 课的 smart zone 那行）。

检索练习 · 三连

选中即判。这三题避开第 1/2 课已考的"选哪个 skill"和 smart zone，专测拓扑角色 · 匝道汇入点 · fork vs continue。

Q1. 你让 research 读第三方 API 文档、整理成带引用的 markdown。它在 ask-matt 拓扑里是哪种角色？

Q2. triage 把一堆别人提的 bug 报告过完，产出了 agent-ready 的 issue。它们该汇入主干哪一站？

Q3. spec 写完了，准备拆 tickets——这是个自然的阶段间休息点，你想给当前会话减减负再继续。用哪个？
