第 24 课 · 单 skill 深挖 · triage 全流程

triage 完整执行流水线：Gather → Recommend → Verify → Grill → Apply

第 6 课讲了 triage 的「档位盘」——5 个状态标签是什么。这一课讲拨档的过程：一条 issue 进来后，triage 一步步做什么、何时等你确认、最后落地什么产物格式。读完这条流水线，你就能预测 triage 在任意时刻正在做哪一步，以及每步该产出什么。

一句话收获：triage 是 5 步流水线（Gather → Recommend → Verify → Grill → Apply），Gather 先做两次代码库核查防止冗余劳动，Apply 按最终状态走 5 条出口——每条出口有专属产物格式，不互换。

1. 起点：三种调用方式

triage（分诊）是 user-invoked（用户触发，见第 1 课），你用自然语言描述想做什么，skill 解读并执行：

调用方式示例triage 的响应
发现模式 "Show me anything that needs my attention" 查 tracker，按三个桶分组展示（最旧优先），等你选一条深入处理
单条处理 "/triage #42" 对该 issue / PR 走完整 5 步流水线
快速 override（状态直推） "Move #42 to ready-for-agent" 确认要执行的动作后直接执行，跳过整条流水线

发现模式的三个桶代表什么

三个桶分别是：① Unlabeled（从未被分诊的 issue）→ ② needs-triage（已标记、等待评估）→ ③ needs-info 且报告者已回复（信息到了，可以继续）。桶外的 issue（ready-for-agent / ready-for-human / wontfix）此刻不需要你介入，不显示。

2. 5 步流水线概览

选定一条 issue 后，triage 按这条流水线处理。第 ④ 步 Grill 是按需步骤——issue 已足够清晰时跳过。

  1. Gather（收集上下文）

    读 issue 全文（body、所有评论、标签、作者、日期）；若是 PR，还读 diff。查项目领域词汇表（CONTEXT.md，见第 7 课）和该区域的 ADR（架构决策记录，见第 8 课）。然后做两次代码库核查——见下一节。

  2. Recommend（给出建议，等确认）

    把推荐的 category（类别：bug / enhancement）和 state（状态角色）、推荐理由、代码库相关摘要（含是否已有实现）告诉维护者。然后等待指示，不自行执行。

  3. Verify（验证声明是否成立）

    对 bug：按报告者步骤尝试复现，报告结果（已复现并定位代码路径 / 无法复现 / 信息不足）。对 PR：check out diff，跑相关测试或命令，确认 diff 是否实现了其声称的功能。成功验证后写出的 agent brief 可信度显著提升。

  4. Grill（按需深化，可跳过）

    若 issue 需要进一步梳理才能写出精确 brief，调用 /grilling（共享原语，见第 17 课）和 /domain-modeling（见第 16 课），逐问题敲定细节，同步更新 CONTEXT.md 和 ADR。issue 已足够清晰时直接跳到 Apply。

  5. Apply（落地结果）

    按最终状态走对应出口，贴产物评论，推标签，必要时关闭 issue。

3. Gather 的两次代码库核查

Gather 读完 issue 之后，triage 必须做两次核查，结果都要在 Recommend 时汇报给维护者：

核查做什么命中时的处理
① redundancy（冗余）检查 用领域概念（非请求的字面措辞）搜代码库，确认是否已有对应实现，并汇报搜了哪里。SKILL.md 原话："search for an existing implementation … by domain concept (not just the request's wording)" Recommend 时注明"此功能已存在"；Apply 走 wontfix（已实现）出口——评论指向代码，绝不写 .out-of-scope/
② prior rejection（先前拒绝）检查 读 .out-of-scope/*.md 全部文件，找与此请求概念相似的被拒条目（"night theme" 匹配 dark-mode.md，按概念匹配，非逐字） Recommend 时浮出给维护者："与 .out-of-scope/dark-mode.md 相似，当时拒因是 X，你的看法还一样吗？"——维护者确认后才关闭

两次核查防的是两种浪费

① 做一遍代码里已存在的功能；② 反复处理已明确拒绝过的请求。关键区别：redundancy 命中（已实现）和 prior rejection 命中（曾被拒）是完全不同的情形，出口和产物截然不同——已实现绝不写 .out-of-scope/，否则会污染未来的去重检查。

4. Apply 的 5 条出口与专属产物

Apply 按维护者最终确认的状态走对应出口。完整模板见 AGENT-BRIEF.md（agent brief 格式与好坏示例）和 OUT-OF-SCOPE.md（知识库格式）。

状态产物关键约束
ready-for-agent 贴 agent brief 评论 描述行为（What），不写文件路径 / 行号；必须含具体可独立验证的 Acceptance Criteria（验收标准）；范围边界须明确写出
ready-for-human 结构同 agent brief，额外说明为何不能委托 agent 判断类工作 / 需外部访问 / 需手工测试——不可委托的原因要写明
needs-info 贴 triage notes（已确认的 + 还需要的） 把 Grill 阶段已解决的部分记进「已确认」避免丢失；问题要具体可操作，不能写"请提供更多信息"
wontfix（已实现） 评论指向现有实现的位置，关闭 绝不写 .out-of-scope/——那里只收被拒的 enhancement；写进已实现功能会污染去重检查
wontfix（拒绝 enhancement） 写（或追加）.out-of-scope/<concept>.md，评论链接，关闭 bug 拒绝不写 .out-of-scope/；同一概念多次请求追加到同一文件（非新建），概念名用 kebab-case

agent brief 的核心书写原则：行为合同，不是操作手册

agent brief 是给 AFK agent 的行为合同（behavioral contract）：描述「系统应当如何表现」（接口、类型、行为、边缘情况），而非「打开哪个文件、改第几行」。原因：路径和行号会随代码库变化失效。agent 会自己探索代码库做实现决策；brief 的职责是让 agent 知道「做完了」的样子是什么——即 Acceptance Criteria 里的每一条可验证断言。

5. 三个附加规则

  1. AI 免责声明（每条评论必须有，无例外）

    triage 在 issue tracker 上发表的每一条评论——无论是 agent brief、triage notes、还是 wontfix 关闭说明——开头必须贴这行声明：

    > This was generated by AI during triage.
    — triage/SKILL.md 原文，格式固定，原样引用

  2. 快速 override（跳过整条流水线直接推状态）

    维护者说"Move #42 to ready-for-agent"时，triage 信任维护者，跳过 5 步流水线，先确认将执行的动作（标签变化、评论内容、是否关闭），然后执行。若推到 ready-for-agent 但未经过 Grill，triage 会补问"是否需要写 agent brief"。

  3. 恢复上次 triage 会话

    若 issue 上已有 triage notes，triage 先读完全部历史评论，检查报告者是否回答了未解决的问题，呈现更新后的全貌再继续——不重问已解决的问题。这保证跨多个会话的 triage 工作不重头来过。
