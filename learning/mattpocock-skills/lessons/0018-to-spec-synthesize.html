把已经聊清的想法「定格」成一份 spec——to-spec 的不访谈与接缝

主流程 grill-with-docs → to-spec → to-tickets → implement 的第二步。上一课刚讲完开头那步（grilling + domain-modeling）怎么把想法拷问到共识；这节接着看：达成共识之后，to-spec 怎么把这摊对话定格成一份可交接的 spec——而且它一句都不再问你。

一句话收获：to-spec 是主流程的「定格」步——它的招牌是不 interview（不访谈）、只 synthesize（综合）：访谈早在上游 grill-with-docs 做完了，to-spec 只把你们已经聊清的东西综合成一份 spec，不再重新问你一遍。它干两件技术活：①用项目术语 + 尊重 ADR 把对话写成 spec 模板；②勾出测试用的 seam（接缝）——现有优先、位置最高、数量最少（理想是一个），并跟你确认。写完发布到 issue tracker、贴 ready-for-agent，直接进主流程下游。

1. 招牌一：不 interview，只 synthesize

这是 to-spec 最容易被误解、也最该先记住的一点。一手源开门就把话说死：

This skill takes the current conversation context and codebase understanding and produces a spec… Do NOT interview the user — just synthesize what you already know.
— to-spec / SKILL.md

为什么不问？因为该问的上游都问完了。回想主流程的分工：

grill-with-docs拷问 → 共识（问）
→
to-spec综合 → spec（不问）
→
to-tickets拆纵切片
→
implement建

grilling 的确认闸门已经保证「达成共识才往下走」；到了 to-spec，共识已经在对话里了，它的任务是把共识定格下来，不是再开一轮访谈。如果你发现 to-spec 在反复问你问题，多半是上游的 grill-with-docs 没做够——该回去补访谈，而不是让 to-spec 越俎代庖。

「不 interview 只 synthesize」是一条更宽的家法

to-spec 的这条规矩，和你已见过的几条是同一种「先对齐、后动手」的纪律：grilling 的确认闸门（共识前不动手）、wayfinder 的 plan, don't do（产决策不产交付物）。每一步都清清楚楚地只做自己那一格的事——to-spec 那一格就是「把已聊清的综合成文」。

2. 招牌二：勾接缝（seams）——在哪测，现在定

to-spec 的第二件技术活，是把测试的接缝先勾出来。一手源给了四条硬偏好：

Sketch out the seams at which you're going to test the feature. Existing seams should be preferred to new ones. Use the highest seam possible… The fewer seams across the codebase, the better - the ideal number is one. Check with the user that these seams match their expectations.
— to-spec / SKILL.md
  • 现有优先：能用已有的接缝就别新开——新接缝是新的维护面。
  • 位置最高：在尽可能高（靠近用户可观察行为）的地方测，别扎进内部实现。
  • 数量最少、理想是一个：接缝越少，测试落点越集中在关键路径上。
  • 跟你确认：接缝定得对不对，要你点头——这是 to-spec 里唯一需要你参与的地方（不是访谈，是确认接缝）。

seam（接缝）＝观察行为、又不伸手进内部的公共边界——测试就贴在这里。to-spec 是整条主流程里第一次把「在哪测」定下来的地方。

3. 收束：seam 这根线，起点就在 to-spec

「seam」这个词你在好几课里碰过——它其实是一根贯穿始终的线，而 to-spec 是它的起点（第一次拍板、并确认）：

哪一课seam 在那儿是什么
本课 to-spec勾并确认测试接缝：现有 / 最高 / 最少（起点）
第 2 课 tdd（implement 内）在 pre-agreed（事先约定）的 seam 上写测试——约定它的正是 to-spec
第 15 课 diagnosing-bugs回归测试要有 correct seam（够深到复现 bug）；无 seam＝架构发现
第 12 课 codebase-designdeletion test 判模块深浅：一个 adapter 是假想接缝、两个才是真接缝

连起来看：to-spec 约定接缝 → implement 的 tdd 在这些接缝上测 → 出了难 bug，diagnosing-bugs 检查接缝够不够深 → 接缝形状不对，交 codebase-design 词汇去评深浅。同一个「在哪观察行为」的问题，被四门 skill 从不同角度接力——to-spec 是第一棒。

4. spec 模板 + 「不写文件路径/代码」纪律

综合出来的 spec 有固定骨架（照模板填）：

段装什么
Problem Statement用户视角的问题
Solution用户视角的解法
User Stories一长串编号的「As an actor, I want feature, so that benefit」，穷尽覆盖
Implementation Decisions要建/改的模块、接口、架构决策、schema、API 契约
Testing Decisions什么是好测试（只测外部行为）、测哪些模块、有无 prior art（先例）
Out of Scope / Further Notes划出界外 / 其它补充

硬纪律：别写具体文件路径和代码片段

一手源："Do NOT include specific file paths or code snippets. They may end up being outdated very quickly."（会很快过时。）例外：若某个 prototype 产出的 snippet 比散文更精确地编码了一个决策（状态机 / reducer / schema / 类型形状），可内联——但只留决策相关的部分、不是能跑的 demo。这跟 CONTEXT.md 「无实现细节」、to-tickets 同款规则是一条心：规格描述「要什么」，不钉死「怎么实现的当下形状」。

写完，发布到 issue tracker、贴 ready-for-agent 标签，无需再走 triage（它天生就是 agent-ready 的）——正是第 14 课说的「spec 在 GitHub tracker 上是个 issue、不落仓库文件」。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. to-spec 拿到一段已达共识的对话，该做的是？

2. to-spec 勾测试接缝（seam）时，遵循的偏好是？

3. 写 spec 时，关于「要不要写具体文件路径和代码」，正确的是？

推荐一手源
