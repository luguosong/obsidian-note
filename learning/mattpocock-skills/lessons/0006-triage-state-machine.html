第 6 课 · 单 skill 深挖 ④ · triage

triage-labels.md 里的 5 个标签，是 triage 的一台状态机

你问："这 5 个标签具体有什么用，我还是没搞懂 setup。"——症结在于 setup 和 triage 是两个 skill：setup 只把这 5 个名字绑到你的仓库，真正拿它们当"档位"给 issue 分拣的，是另一个 skill triage（分诊）。这一课把断开的两半接上。

一句话收获：triage-labels.md 里那 5 个标签，是 triage skill 的 5 个状态——每个 issue 被分拣进其中恰好一个，代表"它此刻卡在流水线的哪一格"。setup 自己从不使用它们，只把这 5 个角色名翻译成你仓库真实的标签串（正是第 4 课的"间接层"）。名字住在 setup，含义住在 triage。

1. 先解开困惑：写字典的 setup ≠ 用字典的 triage

你觉得 setup 神秘，是因为它产出的 triage-labels.md 只是一张"名字对照表"——它列了 5 个标签，却一个字都没解释这些名字干嘛用。含义不在 setup 里，在 triage 里。两个 skill 分工是这样：

skill角色它对这 5 个标签做什么跑几次
setup-matt-pocock-skills写字典的人把 5 个 canonical role name（规范角色名）→ 你仓库真实的标签串，写进 triage-labels.md。自己不分拣任何 issue一次性（首配）
triage用字典的人每次分诊，把 issue 推过这 5 个状态；说"打上 ready-for-agent 角色"时，回查字典取你仓库的真实标签串每次分诊都跑

这就是 triage 自己 SKILL.md（技能定义文件）里的原话——它只认角色名，把"角色 → 真实标签"的映射外包给了 setup：

These are canonical role names — the actual label strings used in the issue tracker may differ. The mapping should have been provided to you — run /setup-matt-pocock-skills if not.（这些是规范角色名——工单系统里真实的标签串可能不同。映射本应已备好；没有就跑 setup）
— skills/engineering/triage/SKILL.md

为什么你的仓库里这层翻译"看着多余"

你的 triage-labels.md 左右两列完全一样（ready-for-agent → ready-for-agent），因为你用了默认名，所以字典看起来是废话。但换成 Linear、或把标签改成中文 可交给AI，triage 里"apply the ready-for-agent role"这句话一个字都不用改，只有字典右列变——这就是间接层救命的地方。

2. 这 5 个是"状态"；triage 里还有 2 个"类别"

看清一件事：triage 给每个 issue 打的是两种正交（互不干扰）的标签，你问的 5 个只是其中一维。

维度标签回答的问题在 triage-labels.md 里？
category（类别角色）bug · enhancement这是什么——坏了，还是要新功能否（GitHub 通用惯例，几乎所有 tracker 自带，无需映射）
state（状态角色）
← 你问的 5 个		needs-triage · needs-info · ready-for-agent · ready-for-human · wontfix它卡在哪——流水线上的哪一格是（这 5 个才需要 setup 映射）

规矩：每个被分诊过的 issue，恰好带 1 个 category + 1 个 state。若两个 state 打架（比如又 ready 又 wontfix），triage 会停下来 flag（标记异常）并先问 maintainer（维护者），不擅自行动。

3. 逐个拆 5 个状态：issue 卡在哪 + triage 做什么

每个标签 = 一个状态（issue 处于什么处境）＋ triage 落这个状态时实际采取的动作：

状态标签含义（issue 卡在哪）triage 采取的动作
needs-triage还没评估——默认起点，刚进来或待定夺打上该角色，等 maintainer 定夺（有进展可附一句评论）
needs-info卡在等 reporter（提报人）补料，信息不足没法往下走贴一条 triage notes：已确认什么 + 还缺什么（@reporter），问题要具体可答
ready-for-agent规格完整，AFK（away-from-keyboard，无人值守）agent 可以直接接手开做贴一份 agent brief（agent 任务简报）评论，让 agent 照着做
ready-for-human规格完整，但必须人来做（判断题 / 需外部访问 / 设计决策 / 手动测试）同 agent brief 的结构，外加一句为什么不能委托给 agent
wontfix不做——已实现过、或被拒关闭 issue；若是被拒的 enhancement，还要写进 .out-of-scope/（不做请求的知识库）并评论链接

为什么分 agent / human 两个"ready"

两者规格都已完整、都配简报——差别只在谁来执行。ready-for-agent 是"这活能无人值守跑"；ready-for-human 是"这活卡着人类判断、外部权限或设计取舍，agent 干不了"。这条线正是这套 skill 服务 AFK 工作流的核心：把能安全交给 agent 的活明确挑出来。

4. 把 5 个状态连成一台状态机

这 5 个不是并列的 5 个抽屉，而是有流向的状态机（state machine）——issue 在格子间移动：

照 SKILL.md 的原文流向：未打标签的 issue 一般先进 needs-triage；从这里分岔去 needs-info / ready-for-agent / ready-for-human / wontfix；needs-info 在 reporter 回复后退回 needs-triage 重新评估。maintainer 可随时越权改——triage 见到不寻常的跳转会先 flag 再问。

5. 回到你的仓库：这 5 格现在什么样

你的 docs/agents/triage-labels.md 用的是默认名、左右列 1:1，所以 triage 说"apply the ready-for-agent role"就是字面上给 issue 打 ready-for-agent 标签。这 5 个标签是 triage 预留的 5 个"档位"，setup 提前替你把档位刻好了名字。

动手 30 秒

在你仓库跑一句 gh issue list --label ready-for-agent——现在是空的，因为你还没跑过 /triage。这印证了本课的分工：setup 只把标签名刻好（字典已就位），要等 triage 真正分拣，issue 才会被贴进这 5 格。想改名？把 triage-labels.md 右列的 ready-for-agent 改成 afk-ok，triage 无需改一个字就跟着走——第 4 课的间接层，在 triage 上活起来了。

推荐一手源

要验证这 5 个状态和流向，去 triage 自己的定义文件最直接。本课最高优先级：

  • skills/engineering/triage/SKILL.md —— 本课全部论断的出处：2 个 category + 5 个 state 角色、状态转移、"canonical role names ↔ setup 映射"那句、每个状态落地时贴 brief / notes 的动作，都在此。
  • setup-matt-pocock-skills / SKILL.md —— 对照第 4 课：它写这张字典，triage 读它。两课合看，间接层就通了。
  • 你自己的 docs/agents/triage-labels.md —— 那张"名字对照表"活样本，左右列 1:1，改右列即改名。
