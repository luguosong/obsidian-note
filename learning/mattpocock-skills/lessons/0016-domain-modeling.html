把领域模型「越用越准」的那只手——domain-modeling 的四手法

domain-modeling（领域建模）这个名字，你在第 8·10·11·14·15 课反复撞见——它惰性写 CONTEXT.md / ADR、它 cross-reference 代码、它垫在 grill-with-docs 底下。这些都是它的侧影。这节课把它正面讲全：它到底是一门什么手艺，靠哪四个动作把模型磨利。

一句话收获：domain-modeling 是一门主动建模纪律——不是「读 CONTEXT.md 取个词」（那是任何 skill 的一行习惯、是被动消费模型），而是在你设计时当场挑战术语、逼出边界、把词和决策一结晶就写下来（主动改模型）。它的手艺就是四手法：challenge（挑战冲突词）· sharpen（磨利模糊词）· scenario（用具体场景压测关系）· cross-reference（拿代码核对说法）。产物是你早认识的两件——CONTEXT.md（术语表·活的真相）+ ADR（决策·只增账本）。它治 4 失败模式里的 #2 verbosity（没有共享语言）。

1. 定位：词汇层 · 主动建模 ≠ 被动读词

在 第 13 课的拓扑里，它是词汇层（vocabulary layer）——不在时间轴上、横向垫在整条流程底下，任何阶段都可能用到它。它治的失败模式是 #2 verbosity：团队没有一套共享语言（DDD 的 ubiquitous language / 统一语言），于是同一个东西各叫各的、沟通全是损耗。

但它最容易被误解的地方，是它和「读文档」的分野。一手源开门就把这条线画死：

Actively build and sharpen the project's domain model as you design… （Merely reading CONTEXT.md for vocabulary is not this skill — that's a one-line habit any skill can do. This skill is for when you're changing the model, not just consuming it.）
— domain-modeling / SKILL.md

两件事，别混

被动消费：tdd / to-spec / diagnosing-bugs 探码前「读 CONTEXT.md 让命名对齐术语」——这是每个 skill 的一行习惯，不是 domain-modeling。
主动建模：你正在设计 / 改变模型——挑战一个词、拍一个决策、发现代码和说法打架——这才触发 domain-modeling。它是 model-invoked：description 说「想钉住术语 / 记一个架构决策 / 别的 skill 需要维护模型时」就触发。

2. 四手法：模型是怎么被「磨利」的

这是本课的核心——建模在会话中发生的四个动作。每一个都带一手源的原话例句：

  1. Challenge · 挑战与字典冲突的词

    用户用的词和 CONTEXT.md 里已定的语言冲突时，当场点出来。"Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"（你字典里 cancellation 定义为 X，可你这儿像是 Y——到底哪个？）守的是已有共识不被悄悄漂走。

  2. Sharpen · 磨利模糊 / 过载的词

    用户用含糊或一词多义的词时，提一个精确的规范词。"You're saying 'account' — do you mean the Customer or the User? Those are different things."（你说 account——指 Customer 还是 User？这俩是两回事。）把一团模糊劈成清楚的概念。

  3. Scenario · 用具体场景压测关系

    讨论领域关系时，编具体场景去戳边界、逼用户把概念之间的界线说精确。不是抽象争论，而是「假设发生了这么一件事，那……？」用边缘 case 把隐含假设挤出来。

  4. Cross-reference · 拿代码核对说法

    用户说「某处怎么工作」时，去核对代码是否同意，发现矛盾就掀出来。"Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"（代码取消的是整个 Order，可你刚说支持部分取消——哪个对？）——第 10 课那「三道显形闸」的第一道，就是这一手。

四手法的共性：不放过任何一个含糊或矛盾——冲突的挑战、模糊的磨利、关系的压测、说法与代码的对账。模型就是这样一次次被逼精确的。

3. 两个产物 + 写法纪律

磨出来的东西，落进你早认识的两件长期记忆——但怎么写有硬规矩：

产物装什么写法纪律
CONTEXT.md
术语表 · 活的真相		 只装本项目特有的领域术语（通用编程概念不收） 术语表 only（无实现细节、不是 spec / 草稿本）· 定义tight（1–2 句、说它是什么不说它做什么）· opinionated（多词同义挑最佳、其余列 _Avoid_）· 词一结晶就 inline 写、不攒批
ADR
决策 · 只增账本		 架构级「为什么这么定」（1–3 句） sparingly——三条件全中才 offer：难逆 · 不解释会困惑 · 真权衡（正是第 8 课那道闸门）

文件都惰性 create：没东西写就不建。单上下文 = 根 CONTEXT.md + docs/adr/；多上下文 = 根 CONTEXT-MAP.md 路由到各 context（接第 8 课防线三、按 bounded context 分片）。

自指小彩蛋：本课的 GLOSSARY.md 就是一份 CONTEXT.md

你这门课的 GLOSSARY.md 用的正是 CONTEXT-FORMAT.md 的形状——每个术语一段 tight 定义 + 一行 _Avoid_ 列易混词。domain-modeling 之于代码库的领域语言，正如 teach 的 GLOSSARY 之于这门课的规范语言：同一套「建统一语言」的手艺，一个用在项目、一个用在学习。

推荐一手源

先读第一条——本课每个论断的出处；其余按需核验：

  • domain-modeling / SKILL.md —— 主动 vs 被动分野原话 + 四手法（challenge / sharpen / scenario / cross-reference）+ CONTEXT.md inline·glossary-only + offer ADR sparingly + 单/多 context 文件结构。最高优先「读」。
  • CONTEXT-FORMAT.md / ADR-FORMAT.md —— 两个产物的精确模板：CONTEXT 的 _Avoid_ 格式 + opinionated/tight/project-specific 规则；ADR 的 1–3 句模板 + 三条件 + 「什么够格写 ADR」清单。
  • 第 8 课 / 第 10 课 —— 对照回看：第 8 课的 ADR 三条件闸门就是它的 offer-ADR 规矩；第 10 课的 cross-reference / reconciliation 就是它的一手法在多人协作下的用法。
