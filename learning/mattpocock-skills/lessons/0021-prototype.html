用「扔掉的代码」回答一个设计问题——prototype

你在 第 9 课（提升的活样本）、第 11·14 课（wayfinder 的 prototype 票型、throwaway 分支）反复见过它的产物。这节短课正面讲它：prototype（原型）是为回答一个问题而写、写完就扔的代码——它的第一个动作，是选对分支。

一句话收获：prototype 是 throwaway code that answers a question（一次性代码，回答一个问题）——问题决定形状。第一步是选分支：问题是「这个逻辑 / 状态模型对不对？」就走 LOGIC（搭个极简交互式终端 app 把状态机推过难缠的 case）；问题是「这东西该长什么样？」就走 UI（在一条路由上生成几个差异极大的界面变体切换对比）。选错分支＝整个原型白做。六条通用规矩让它便宜、可扔；做完把验证过的决策折进真代码、原型本身扔上 throwaway 分支。它是 standalone（独立），任何「得跑起来才看得清」的设计问题都能用。

1. 选分支：问题决定形状（选错就白做）

一手源开门第一件事就是认清在回答哪个问题——从提示、周围代码、或直接问你——因为两个分支产出的东西截然不同：

LOGIC 分支UI 分支
回答的问题「这个逻辑 / 状态模型对不对、顺不顺？」「这东西该长什么样？」
产出的东西极简交互式终端 app，把状态机推过纸上难推的 case同一条路由上几个差异极大的界面变体，URL 参数 + 悬浮底栏切换
典型场景后端模块 / reducer / 状态机页面 / 组件

歧义时怎么办

「选错分支会浪费掉整个原型」，所以别猜。若问题真的模糊、又找不到人问，就按周围代码默认——后端模块 → LOGIC，页面 / 组件 → UI——并在原型顶部写明这个假设。

2. 六条通用规矩：让它便宜、可扔

无论哪个分支，都守这六条——核心精神是「一次性、快、别打磨」：

  1. 从第一天就是一次性的，且标明

    放在它将来要用的地方旁边（上下文一目了然），但命名让人一眼看出是原型、不是生产代码。UI 路由遵循项目已有路由约定，别自造新结构。

  2. 一条命令能跑

    用项目已有的 task runner（pnpm <name> / python <path> …），你不用动脑就能启动。

  3. 默认不持久化

    状态只放内存。持久化正是原型要检验的东西、不该依赖它；真要用库，就打个「PROTOTYPE — wipe me」的 scratch DB / 本地文件。

  4. 跳过打磨

    没测试、没超出「能跑」的错误处理、没抽象。目的是快速学到东西。

  5. 把状态摊开给你看

    每次操作后（LOGIC）/ 每次切变体时（UI），打印 / 渲染出全部相关状态，让你看清变了什么。

  6. 做完就「捕获」

    把验证过的决策折进真代码；再把原型本身当一手证据捕获——commit 到 out-of-main 的 throwaway 分支、在实现 issue 上留 context pointer；答案（结论 + 它解决的问题）也记下。主分支只留那个验证过的决策。

第 6 条正是第 9 课的「提升（promotion）」活样本：结论被提升、载体被丢弃。也正是 wayfinder 的 prototype 票型（HITL）产物落 throwaway 分支的由来（第 14 课）。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. 开始一个 prototype，第一个动作是？

2. 关于 prototype 的写法，哪条符合它的规矩？

3. 原型验证出结论后，正确的收尾是？
