把一份 spec 切成「一条条能独立跑通的细线」——to-tickets 的 tracer-bullet 纵切片

主流程 grill-with-docs → to-spec → to-tickets → implement 的第三步、也是最后一块拼图。上一课把想法定格成了一份 spec；这节看 to-tickets 怎么把这份 spec 切成一片片可独立建造、可独立验证的工单——切的方向，是这门 skill 的全部要害。

一句话收获：to-tickets 把 spec 切成 tracer-bullet（曳光弹）纵切片——每一片都是一条又窄又完整、穿透所有层（schema→API→UI→test）的细线，自己就能 demo / 验证、装得进一个全新的上下文窗口；片与片之间用 blocking edges（阻塞边）串起依赖，然后沿 frontier（前沿）一次只做一片、每片交给 implement、片间清空上下文。唯一的例外是 wide refactor（大范围重构）——一次机械变更却波及全仓、没有纵切能保持绿色，这时改用 expand–contract（先扩后缩）时序。

1. 核心：什么是 tracer-bullet 纵切片

「曳光弹」这个比喻的精髓是：先打一条能看见弹道的完整细线，而不是先把某一层堆满。一手源给纵切片定了四条规矩：

Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests) — vertical, NOT a horizontal slice of one layer · A completed slice is demoable or verifiable on its own · Each slice is sized to fit in a single fresh context window · Any prefactoring should be done first.
— to-tickets / SKILL.md
  • 又窄又完整、穿透每一层：一片薄薄地贯穿 schema → API → UI → 测试，是一条竖切，不是把「所有 schema」当一片、「所有 API」当另一片的横切。
  • 自己就能 demo / 验证：做完这一片，就有一个能演示、能验证的端到端行为，不是一堆还拼不起来的零件。
  • 装得进一个全新上下文窗口：一片的大小以「一个 fresh context 能吃下」为准——正好交给一次 implement。
  • prefactor 先行：需要的预重构先做（"make the change easy, then make the easy change"，先把改动变容易，再做那个容易的改动）。

纵 vs 横：这正是 tdd 那条反模式的同一课

第 2 课 tdd 的反模式 horizontal slicing（横切）——「先写所有测试、再写所有实现」——测的是想象的行为。to-tickets 的纵切是同一枚硬币：每片一条 tracer bullet、端到端打通、可独立验证，回应上一片教给你的东西。切错方向（横切），后面每一步都会歪。

2. blocking edges + frontier：一次只做一片

切好的片不是一盘散沙——每片要声明它被哪些片阻塞（blocked by）。没有 blocker 的片可以立刻开工；这些「blocker 全清、可立刻做」的片，就是 frontier（前沿）。

这正好接上第 9 课：to-tickets 产出的这些工单就是工单层（工作记忆）；frontier 被一片片消费，ship 后整批冻结退役。一次一片 + 片间清空上下文，也是第 2 课 context hygiene（上下文卫生）的直接落地——每片装进一个干净窗口，不让上一片的杂音污染下一片。

3. 唯一例外：wide refactor 走 expand–contract

纵切不是万能的。有一种活天生切不成纵片——一手源叫它 wide refactor（大范围重构）：

A wide refactor is one mechanical change — rename a column, retype a shared symbol — whose blast radius fans across the whole codebase, so a single edit breaks thousands of call sites at once and no vertical slice can land green.
— to-tickets / SKILL.md

一次机械变更（改列名、换一个共享符号的类型），爆炸半径横扫全仓：一改就同时打断上千个调用点，没有哪条纵切能一次落地还保持绿色。硬塞进 tracer bullet 只会全红。改用 expand–contract（先扩后缩）时序：

expand 扩新形态与旧并存
什么都不破
→
migrate 迁按爆炸半径分批
每批一 ticket·阻塞于 expand
旧形态还在→CI 保绿
→
contract 缩删旧形态
阻塞于所有 migrate 批

先 expand：把新形态加在旧的旁边，什么都不破。再 migrate：把调用点按爆炸半径分批（按包、按目录）迁过去，每一批是一个 ticket、阻塞于 expand，因为旧形态还在，批与批之间 CI 始终绿。最后 contract：等没有调用者了，删掉旧形态，这个 ticket 阻塞于每一个 migrate 批。

再狠一点——连分批都无法各自保绿时，仍保留这个序列，但让它们共享一条 integration branch（集成分支），全部阻塞于一个最后的 integrate-and-verify（集成并验证）ticket，绿色只在那里兑现。

4. 发布 + 主流程四步全通

切好、跟你确认（present 成编号列表：Title / Blocked by / What it delivers，问你 granularity 对不对、blocking 边对不对、要不要合并或再拆，迭代到你批准）之后，发布到配置的 tracker——工单内容一样，只是阻塞边的形状随 tracker 变（接第 14 课）：

tracker发布形态
GitHub（你的仓库）一片一个 issue、按依赖 blockers-first、用原生 blocking/sub-issue、贴 ready-for-agent
本地 markdown.scratch/<feature-slug>/issues/<NN>-<slug>.md，从 01 起 blockers-first 编号

然后沿 frontier 一次一片、每片用 /implement、片间清空上下文；不要 close 或改动任何 parent issue。同款硬纪律：别写具体文件路径/代码（会 stale，例外仍是 prototype 编码决策的 snippet）——和 to-spec、CONTEXT.md 一条心。
