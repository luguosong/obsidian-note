全局地图：4 失败模式 × 主流程 × 谁能调它

你已经零散用过 tdd / diagnosing-bugs / triage / to-prd / improve-codebase-architecture。 这节课不教任何一个的细节——它给你把它们串起来的那张地图。 仓库自带的 ask-matt 就是这张地图本身，而它建立在一个更深的判断上：所有 skill 都在防 4 类 agent 失败模式。

这节课的收获：给一句真实场景，你能立刻说出——它在主流程的哪一段、该用哪个 skill、这个 skill 防的是 4 失败模式里的哪一个。散点从此连成一张图。

1. 先定坐标系：4 失败模式（"它防什么病"）

Matt 把 Claude Code / Codex 这类 agent 的失败归成 4 类。每个 skill 都是某一类的药。 记住这 4 类，你就记住了"为什么这个 skill 存在"。

#失败模式你看到的症状主修复 skill背后的工程经典
1 Misalignment（没做对你想要的） "我做完了"——你一看，根本不是你要的 grill-me / grill-with-docs 《Pragmatic Programmer》
"没人一开始就知道自己要什么"
2 Verbosity（没有共享语言） agent 用 20 个词描述本该 1 个词的事 grill-with-docs（CONTEXT.md）/ domain-modeling 《Domain-Driven Design》
ubiquitous language
3 Code doesn't work（反馈回路缺失） agent 闭着眼写，跑起来全是错 tdd / diagnosing-bugs 《Pragmatic Programmer》
"反馈率是你的速度上限"
4 Ball of mud（设计腐化） 越加越难改，代码糊成一团 to-prd / improve-codebase-architecture 《XP》"每天投资设计" + 《Ousterhout》深模块

这 4 类是后面所有课的纵轴。每学一个 skill，先问："它防的是第几类？"

2. 第二条轴：谁能调它（user-invoked vs model-invoked）

README 把所有 skill 沿这条轴劈成两半：

user-invokedmodel-invoked
怎么触发 只能你手动调（打 /名字） 你或 agent自动 reach（任务匹配即上）
标志 frontmatter disable-model-invocation: true 没有这个标志
职责 编排流程（orchestrate） 持有可复用的纪律（reusable discipline）
典型 ask-matt grill-with-docs to-prd to-issues triage improve-codebase-architecture tdd diagnosing-bugs code-review prototype research domain-modeling codebase-design
一条铁律：user-invoked 可以调 model-invoked，但绝不能调另一个 user-invoked。user-invoked 是"流程入口"，彼此平级、互不嵌套。

你已经熟悉的 tdd / diagnosing-bugs 是 model-invoked（纪律），triage / to-prd / improve-codebase-architecture 是 user-invoked（入口）。这条轴解释了"为什么有的要手点、有的会自己上"。

3. 主流程：idea → ship（地图的主干）

绝大多数真实工作走这条主线。把鼠标在每一步上停一下，看它防第几类失败：

grill-with-docs 入口·对齐想法
防 #1 + #2
沉淀进 CONTEXT.md/ADR
→
to-prd 对话→PRD
防 #4（先想碰哪些模块）
→
to-issues PRD→可独立认领的 issue
纵切，不按层切
→
implement 每 issue 开新会话
内部驱动 tdd（防 #3）
收尾跑 code-review
→
ship 提交

主干上有两个分支（ask-matt 原话）：

  • 问题需要 runnable 答案？（状态/业务逻辑/得看一眼的 UI）→ 绕进 prototype，用 handoff 把上下文带出再带回。原型从第一天就是一次性的——留答案，删代码。
  • 多会话构建？是 → 走完整 to-prd → to-issues；否 → 直接 implement，同一窗口里干完。

Context hygiene（主干的关键操作约束）

  • 第 1–3 步保持同一个未打断的上下文窗口——grilling、PRD、issues 要建立在同一串思考上，中途别 compact / 清空。
  • 每个 issue 开全新会话跑 implement——issue 之间是独立的，别共享污染的上下文。
  • 窗口逼近 smart zone（~120k token，模型仍锐利的上限）还没到 to-issues？别硬撑——handoff 换新会话继续。

4. 两条 on-ramp（匝道：汇入主干）

有些起点不在"我有个想法"上，而是被动涌入的——它们走匝道汇入主干：

起点场景匝道 skill产出 / 汇入点
别人提的 bug 报告 / 功能请求堆着 triage 把 raw issue 过一遍 triage 角色状态机 → 产出 agent-ready issue → implement 接
线上炸了 / 难 bug（抗第一眼、偶发、回归） diagnosing-bugs 先建紧反馈回路（一条就能在本 bug 上变红的命令）→ 修 + 回归测试；若根因是"没好 seam 锁 bug"，交给 improve-codebase-architecture
别犯这个错：to-issues 产出的 issue 已经是 agent-ready 的，不要再 triage。triage 只处理你没创建的 raw issue。

5. 底层：词汇层（不是流程，是"语言"）

有两个 model-invoked 的引用垫在所有 skill 下面，各是各自词汇的唯一真相。它们不是流程节点—— 当问题是"词"而不是"流程"时，直接 reach 它们，或让上面的 skill 把它们带进来：

  • domain-modeling —— 管领域语言：把模糊术语磨尖、拆解一个身兼数职的词（"account" 干了三件事）、把难撤销的决策记成 ADR。它是 grill-with-docs 背后让 CONTEXT.md 保持干净 glossary 的那股力。
  • codebase-design —— 管模块形状的深模块词汇（module / interface / depth / seam / adapter / leverage / locality）：大量行为藏在简单接口后、落在干净的 seam 上。tdd 和 improve-codebase-architecture 都说这套话。

另外 improve-codebase-architecture 不在主流程上——它是代码库体检，闲时跑：扫出"可加深"的机会，挑一个就生成一个 idea，拿这个 idea 从 grill-with-docs 进主流程。它找候选，codebase-design 是你设计选中那个的工作台。

诊断 · 一个常见误区

先想 30 秒，再点开。

我用 to-prd 把一份 PRD 拆成了 12 个 issue。现在该不该把它们丢进 triage 过一遍？

不该。triage 只处理你没创建的 raw issue——bug 报告、外部涌进来的需求。to-issues 产出的 issue 已经是 agent-ready 的（有上下文、可独立认领），再 triage 是重复劳动、还可能把状态弄乱。

正确做法：每个 issue 开一个新会话，把 PRD + 这一个 issue 喂给 implement 直接干。
