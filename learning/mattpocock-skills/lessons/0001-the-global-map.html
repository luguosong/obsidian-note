mattpocock/skills 系统课 · 第 1 课 · 基于 v1.1.0

全局地图 + 全 skill 目录：一课定坐标

你已经零散用过 tdd / diagnosing-bugs / triage / improve-codebase-architecture（依次是：测试驱动开发 / 诊断难 bug / 工单分诊 / 架构体检）。 这节课不深挖任何一个——它给你把它们全串起来的那张图，外加一张覆盖全部 skill（技能）的目录总表当参考卡。 仓库自带的 ask-matt（问 Matt · 路由器）就是这张图本身，而图建立在一个更深的判断上：所有 skill 都在防 4 类 agent（AI 代理）失败模式。

这节课的收获：给一句真实场景，你能立刻定位——它在主流程的哪一段、该用哪个 skill、这个 skill 防 4 失败模式里的哪一类；再配一张按谁调分组、按调用先后排序的全 skill 总表随时回查。

1. 纵轴：4 失败模式（"它防什么病"）

Matt 把 agent 的失败归成 4 类，每个 skill 都是某一类的药。记住这 4 类，就记住了"为什么这个 skill 存在"。

#失败模式症状主修复工程经典
1Misalignment（没做对你想要的）"我做完了"——根本不是你要的grill-me / grill-with-docs《Pragmatic Programmer》没人一开始就知道要什么
2Verbosity（没有共享语言）20 个词描述本该 1 个词的事grill-with-docs / domain-modeling《DDD》ubiquitous language
3Code doesn't work（反馈回路缺失）闭着眼写，跑起来全是错tdd / diagnosing-bugs《Pragmatic Programmer》反馈率 = 速度上限
4Ball of mud（设计腐化）越加越难改，糊成一团to-spec / improve-codebase-architecture《XP》每天投资设计 ·《Ousterhout》深模块

下面的目录总表里，每个 skill 都标了它防第几类。

主干上有两个分支：需要 runnable（可运行的）答案（状态/逻辑/UI 得跑起来看）→ 绕进 prototype（原型），用 handoff（交接文档）双向桥接（留答案删代码）；是否多会话构建→ 是则走完整 to-spec/to-tickets，否则同窗口直接 implement。（主流程如何一步步走，见第 2 课。）

三条匝道：不从"我有个想法"起步的入口

底下垫着：grilling 是共享原语

v1.1 把"relentless interview（不停追问式访谈）"抽成独立的 model-invoked skill grilling——一次一题、每题带推荐答案，事实去查代码库、决策留给你，且带确认 gate（确认关卡）（共识前不 enact plan，即达成共识前不执行方案）。grill-me（无代码库）和 grill-with-docs（有代码库）都只是它的两种壳。

3. 全 skill 目录总表（参考卡）

整套 skill 先按谁调分两组，组内按调用先后排——一眼看清"谁负责编排、谁是可复用纪律"，又能顺着用它的先后找到它。

README 沿这条轴把 skill 劈两半：user-invoked（用户手动触发）只能你手动打 /名字、负责编排流程（标志 disable-model-invocation: true，即禁止模型自动触发）；model-invoked（模型自动触发）你或 agent 都能自动 reach（触达调用）、持有可复用的纪律。防 列对应上面 4 失败模式（"—" = 非防病，是基础设施 / 路由 / 学习）。

一条铁律：user-invoked 可以调 model-invoked，但绝不调另一个 user-invoked——入口彼此平级、互不嵌套。

词汇层的用法：domain-modeling（领域语言）和 codebase-design（模块形状语言）不是流程节点——当问题是"词"而非"流程"时直接 reach，或让上面的 skill 带进来。

「状态」列说明：「有状态」= 把工件持久化到文件系统 / issue tracker，之后的运行或另一会话能读回续上（Matt 讲 teach 时的口径）；「无状态」= 会话内一次性变换、不留可续接状态。有/无状态与 user/model 是两条正交轴——user-invoked 里既有有状态（teach/wayfinder）也有无状态（ask-matt/implement）。带 † 为 borderline：to-spec/to-tickets（产出落 tracker 供下游 session 读回）、handoff（写文档给新会话）、research（findings 写入仓库）判为有状态；prototype（"throwaway from day one"）判为无状态。逐个 SKILL.md 核实，见 学习记录 0009。

练习 · 把场景钉到地图上

四句真实场景，选完即时反馈。能钉对，地图就建好了。

Q1. 「我刚接手一堆别人提的 bug 报告和功能请求」——走哪个？

Q2. 「我有完整代码库，想加个功能，一会话装得下」——第一步走哪个？

Q3. 「从零做一个新平台，连分哪些模块、先验什么都没想清，肯定不止一个会话」——走哪个？

Q4. 「接入某第三方 API，想把它能做什么、有哪些限制读清整理成文档，但我自己不想读」——用哪个？

诊断 · 一个常见误区

先想 30 秒，再点开。

我用 to-tickets 把 spec 拆成了 12 个 ticket。该不该再丢进 triage 过一遍？

不该。triage 只处理你没创建的 raw issue（bug 报告、外部涌入的需求）。to-tickets 产出的 ticket 已经是 agent-ready 的（自带 ready-for-agent、可独立认领），再 triage 是重复劳动、还会弄乱状态。正确做法：每个 ticket 开新会话，把 spec + 这一个 ticket 喂给 implement。
