跑一次 wayfinder，到底往哪些文件里写了东西？——从决策地图到已提交代码的完整生命周期

第 11 课讲了 wayfinder（探路者）是什么——给「太大装不下一个会话」的模糊工程画一张决策地图，铁律 plan, don't do。这节课换一个角度追问它的物理产物：一次 wayfinder 从起手到收尾，产生 / 修改了哪些文件？执行完该接哪些 skill？那些 skill 又落到哪些文件？把整条弧上的每一个「工件」都钉在纸上。

一句话收获：追踪 wayfinder 全流程的每一个工件（artifact），你会看到它刻意几乎不碰你的仓库文件树——它的产物是 issue tracker 上的一张决策地图（你的仓库配了 GitHub tracker，所以 map 和票都是 GitHub issue，不是仓库里的 .md 文件），外加规划途中惰性写下的 CONTEXT.md/ADR、以及扔在 throwaway 分支上的 research/prototype 产物。真正的源码文件要等到三步之后的 /implement 才落到分支。看「工件落在哪种介质」，你就看见了 planning→building 那条边界——工件从「tracker 决策」→「spec/ticket issues」→「已提交代码」逐段位移。

1. 先分清两种「产物」：tracker 工件 vs 仓库文件

大多数 skill 的产物是文件（源码、CONTEXT.md、.scratch/ 工单）。wayfinder 不一样——它的规范工件（canonical artifact，即这条 skill 认定的唯一真身）是 issue tracker 上的一个 issue：

The map is a single issue on this repo's issue tracker, labelled wayfinder:map — the canonical artifact. Its tickets are child issues of the map. … Where the map, its child tickets, blocking, and frontier queries physically live is tracker-specific.
— wayfinder / SKILL.md

关键就在「tracker-specific（取决于你配的 tracker）」这句：地图物理上落在哪，由 setup-matt-pocock-skills 给这个仓库配的 tracker 决定。你的仓库配的是 GitHub（见 docs/agents/issue-tracker.md 的「Wayfinding operations」段），所以在你这里：

  • 地图 = 一个打 wayfinder:map 标签的 GitHub issue（gh issue create --label wayfinder:map）；
  • 决策票 = 挂在地图下的 GitHub 子 issue（sub-issue），打 wayfinder:<type> 标签；
  • 阻塞关系 = GitHub 的 原生 issue 依赖（UI 里可见，直接把前沿画出来）。

换句话说——在你的仓库里跑 wayfinder，地图和票都在 GitHub 上，不会在 git status 里冒出任何文件。这不是巧合，正是 plan, don't do 的物理体现：它产出决策（住在 issue 里），不产出交付物（会落成文件的东西）。

如果 tracker 是 local-markdown 会怎样？

一手源说「If no tracker has been provided, default to the local-markdown tracker」。那种配置下，地图和票才会变成 .scratch/ 下的 .md 文件。所以「wayfinder 产生哪些文件」没有唯一答案——它随 tracker 而变。你的答案是「GitHub issue，仓库里零文件」；只有换成本地 tracker，票才成文件。别拿别的仓库的经验套。

2. wayfinder 自己：两个阶段各自写了什么

wayfinder 有两种调用——先 Chart（画地图），之后每会话 Work through（走地图，解一张票）。逐步看它们各自的产物落在哪种介质：

2.1 Chart：画地图那一次会话

  1. 命名终点（跑 /grilling + /domain-modeling）

    这是 wayfinder 全程唯一常态会写仓库文件的地方：domain-modeling 一旦拍板术语或不可逆决策，就惰性写 CONTEXT.md（术语表）/ docs/adr/NNNN-*.md（ADR）——正是你在第 7–10 课学的领域层文件。

  2. 建地图 issue（wayfinder:map）

    体分五段：Destination / Notes / Decisions so far（空）/ Not yet specified / Out of scope。GitHub issue，非文件。

  3. 建能立刻说清的子票 + 第二遍连 blocking 边

    子票是 GitHub 子 issue（issue 得先有 id 才能互相引用，所以分两遍）。说不清的留在 Not yet specified 的雾里。GitHub issue，非文件。

  4. 点火 research 子 agent（若有 research 票）

    每张 research 票起一个 /research 后台 agent，把 findings 写成一份 Markdown 文件，落在 throwaway research/<name> 分支上，票里只留一个 context pointer（指针）。文件在 throwaway 分支，不进 main。

  5. 停

    「charting is one session's work; it hand-resolves nothing」——画完就停，一张票都不解。

2.2 Work through：之后每会话，解一张票

拿一张地图起手，取前沿第一张票→认领→解→记→毕业雾。产物按票类型分叉（四种类型的 HITL/AFK 见第 11 课）：

票类型解它产生什么落在哪种介质
grilling（默认）一次对话拍板一个决策；可能再调 domain-modeling决策记进 GitHub issue；术语/ADR 惰性写仓库文件
researchfindings Markdown（同 Chart 步 4）throwaway research/<name> 分支（不进 main）
prototype一次性代码（/prototype），验证一个「长啥样 / 怎么跑」提交到 out-of-main 的 throwaway 分支 + 票上挂 context pointer
task唯一「做事」的票：开账号 / 供权限 / 搬数据，好让某个决策能拍动的是外部系统；把 facts（凭证位置、URL、行数）记进票

无论哪种，收尾三连都是在 tracker 上改：贴 resolution comment（解答评论）→ close 掉这张 issue → 往地图的 Decisions so far 追一行 context pointer。然后把新毕业的雾变成新票、把越界的票关掉记进 Out of scope。

记住这条主线：wayfinder 循环几乎不动 main 的文件树

把 2.1 + 2.2 合起来看——除了 domain-modeling 惰性写的 CONTEXT.md/ADR，wayfinder 的每一步都在改 tracker 上的 issue；research/prototype 的代码产物刻意扔在 throwaway 分支、绝不进 main（「Assets created while resolving a ticket are linked from the issue, not pasted in」）。你的 main 分支源码树，从 Chart 到雾散基本纹丝不动。这就是 plan, don't do 留下的物证。

3. 雾散之后：接哪些 skill、它们又写哪些文件

地图上无票可解、路清了，wayfinder 移交、不开建——默认汇入主流程的 to-spec（第 11 课讲过的那条汇流路径）。三步下游各自的文件足迹如下：

  1. /to-spec —— 把地图的决策收拢成一份 spec

    它不再访谈、只综合（synthesize）：读 CONTEXT.md 术语 + 尊重相关 ADR，勾出测试用的 seam（接缝，跟你确认），写成 spec（Problem/Solution/User Stories/Implementation Decisions/…），发布成一个 GitHub issue 并打 ready-for-agent 标签。仓库文件：无新增（spec 是 issue）。

  2. /to-tickets —— 拆成 tracer-bullet 纵切片

    把 spec 拆成一片片打通 schema→API→UI→test 的纵切片、每片声明 blocking 边。你的 GitHub tracker 下：每片一个 GitHub issue（原生 blocking + ready-for-agent），仓库文件无新增。（只有本地 tracker 才会写成 .scratch/<feature-slug>/issues/NN-*.md 文件。）过程中可能预重构（prefactor）少量代码。

  3. /implement —— 真·文件在这里才落地

    按 spec/票在事先约定的 seam 上驱动 /tdd：写测试文件 + 源码文件，定期 typecheck、收尾跑全量测试，再用 /code-review（Standards + Spec 两轴并行子 agent，产一份审查报告）复查，最后提交到当前分支。这是整条弧上第一次、也是唯一一次让 main/工作分支的源码文件树真正改变。

一句话把弧闭合：wayfinder 先「决定」（issue）→ to-spec/to-tickets 把决定变成「构建片」（issue）→ implement 才「建」（提交文件）。（只有当这摊活其实很小时，才可跳过 to-spec 直连 implement——代价是丢掉「收拢」，见第 11 课。）

推荐一手源

先读第一条——本课每个「落在哪」都出自它；其余按需核验：

  • wayfinder / SKILL.md —— 地图/票/blocking 的介质是 tracker-specific、Chart 六步与 Work-through 五步的产物、research 落 research/<name> 分支、「assets linked, not pasted」。最高优先「读」。
  • 你仓库的 docs/agents/issue-tracker.md（本地）—— 「Wayfinding operations」段把上面的抽象坐实成你这个 GitHub 仓库的 gh 命令：map=gh issue create --label wayfinder:map、子票=sub-issue、blocking=原生依赖。这就是第 4 课「间接层」落在 wayfinder 上的样子。
  • to-spec / to-tickets / implement / code-review 的 SKILL.md —— 汇流三步各自的产物介质：spec/ticket 发成 issue（本地 tracker 才写 .scratch/*.md）、implement 提交源码到分支、code-review 出两轴报告。
