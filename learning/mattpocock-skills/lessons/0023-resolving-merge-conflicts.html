合并冲突不是「选一边」，是「合两个意图」——resolving-merge-conflicts

这是全局地图之外的一个 standalone 工具类 skill——不在主流程 / 匝道骨架里，纯粹在你手头正卡着一个 merge / rebase 冲突时派上用场。它把「解冲突」从「凭手感挑一边、或胡乱拼一起」变成一套五步纪律。

一句话收获：一个冲突不是两段文本打架，是两个意图相撞。resolving-merge-conflicts 的要害是：先去追每一边的一手源（commit / PR / issue）、搞懂各自为什么那么改，再解——能保就把两个意图都保住；不兼容时选匹配这次 merge 目标的那个、并记下 trade-off。铁律：绝不发明新行为、绝不 --abort、永远把冲突解完；收尾跑项目的自动检查（typecheck → 测试 → 格式化）、修好 merge 弄坏的，再 stage + commit。

1. 五步纪律

  1. 看清当前状态

    先摸清这次 merge / rebase 的处境：查 git 历史、看哪些文件冲突了。

  2. 为每个冲突追一手源

    深入搞懂每一边为什么这么改、原本的意图是什么——读 commit message、翻 PR、查原始 issue / ticket。你合不了你不理解的意图。

  3. 逐个 hunk 地解

    能保则两个意图都保；不兼容时，选匹配这次 merge 既定目标的那个、并记下这个取舍。不要发明新行为；永远解完，绝不 --abort。

  4. 跑项目的自动检查

    找出项目的自动检查并跑——通常是 typecheck → 测试 → 格式化；修好任何被 merge 弄坏的东西。

  5. 收尾这次 merge / rebase

    全部 stage、commit。若是 rebase，继续 rebase 流程直到所有 commit 都 rebase 完。

2. 三个最容易做错的地方

  • 不追一手源就动手（错）→ 盯着冲突标记凭手感挑一边。冲突是两个作者的意图相撞；不去读 commit / PR / issue 弄懂各自为什么，你只是在赌。这正是本课反复出现的「一手源优先·追回源头」在 merge 场景的又一次落地。
  • 发明第三种行为（错）→ 把两边揉成一个谁都没打算要的新逻辑（franken-merge）。纪律是：能保两个意图就都保；不能，就选匹配 merge 目标的那个——不新增。
  • 停在「能编译 / 无冲突标记」（错）→ 一次能合上、甚至能编译的 merge，未必行为正确。所以第 4 步必须跑项目的检查（typecheck → 测试 → 格式化）、修好 merge 弄坏的，才算数。

一条硬规则：永远解完，绝不 --abort

--abort 把冲突推回原点、什么也没解决。这门 skill 的立场是always resolve——哪怕某个 hunk 两边不兼容，也是做一个有记录的取舍（选匹配 merge 目标的、记下 trade-off），而不是撤退。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. 面对一个冲突 hunk，动手解之前该做的是？

2. 两边不兼容、没法都保时，正确做法是？

3. 所有 hunk 都解完之后，收尾正确的是？
