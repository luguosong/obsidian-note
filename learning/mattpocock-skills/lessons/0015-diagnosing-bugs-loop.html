难 bug 别急着猜原因——先造一条「能亮红灯」的回路：diagnosing-bugs

三条匝道（triage / diagnosing-bugs / wayfinder）你已照过两条。最后一条 diagnosing-bugs（诊断 bug）治的是 4 失败模式里的 #3 code-doesn't-work（反馈回路缺失）。它把「调试」这件看似靠灵感的事，变成一套先建回路、再谈假设的纪律——而全部重量都压在第一步。

一句话收获：diagnosing-bugs 的整条 skill 就是 Phase 1——在你形成任何假设之前，先造出一条能对这个 bug「亮红灯」的紧反馈回路（tight, red-capable feedback loop）。一手源原话："This is the skill. Everything else is mechanical." 铁律是 「没有能亮红灯的命令，就不许进 Phase 2」——它专防每个开发者的本能：读代码 → 猜原因。后面五个阶段（复现/最小化、假设、探针、修+回归、收尾）都只是机械地消费这条回路。这跟你熟的 tdd 是同一套紧回路纪律，只是用在 bug 上。

1. 定位：第三条匝道，治「反馈回路缺失」

它在 第 1 课的全局地图里是匝道——不从「我有个想法」起步，而是从「有个东西坏了」起步，修完汇回主流程。和另外两条匝道的区别：

  • 触发方式是 model-invoked：它的 front-matter 没有 disable-model-invocation: true——你说「debug 一下 / 这里报错了 / 这个慢」，agent 自己就会触发它。（对比 triage/wayfinder 都是 user-invoked、要你手动敲。）
  • 治的失败模式是 #3：agent 写了不工作的代码、却没有反馈信号告诉它哪错了。药方和 tdd 同源——先有能变红的信号，再动手。

开篇的一个小前提

探码前先读 CONTEXT.md（术语/心智模型）+ 该区的 ADR——和你在第 8–10 课见过的领域层消费习惯一致。诊断也吃这份共享语言。

2. Phase 1＝整条 skill：造一条紧的、能亮红灯的回路

一手源把话说死："This is the skill. Everything else is mechanical. If you have a tight pass/fail signal for the bug — one that goes red on this bug — you will find the cause… If you don't have one, no amount of staring at code will save you." 所以这一步要不成比例地下功夫——aggressive、creative、拒绝放弃。

造回路有十种手段，大致按优劣排序（能用上面的就别用下面的）：

档位手段什么时候用
1失败测试（在够到 bug 的 seam 上：unit/集成/e2e）首选，最紧
2–3curl/HTTP 脚本打 dev server；CLI + fixture diff 已知good快照有服务/命令行入口
4–5headless 浏览器脚本（Playwright）；回放抓下来的真实 trace/payloadbug 在 UI 或依赖真实数据
6–7一次性 harness（最小子系统 mock 依赖）；property/fuzz（1000 随机输入）难隔离 / 「有时候错」
8–9bisection harness（git bisect run）；differential（新旧版本同输入 diff）某两个状态之间冒出来的
10HITL bash 脚本（scripts/hitl-loop.template.sh 的 step/capture）最后手段：非要人点，也把人结构化地驱动、输出喂回 agent

有了 一条 回路，还要当产品一样打磨（tighten）：更快（缓存 setup、砍无关 init）、信号更利（断言具体症状而非「没崩」）、更确定（钉时间、种 RNG、隔离 fs/网络）。"A 30-second flaky loop is barely better than no loop; a 2-second deterministic one is a debugging superpower." 非确定 bug 不追求干净复现，而是把复现率抬高到可调试（100×、并行、加压、注 sleep；50% 可调，1% 不可）。

铁律：No red-capable command, no Phase 2

Phase 1 的完成判据不是「读懂了代码」，而是你能报出一条命令——脚本路径 / 测试调用 / 一条 curl——已经至少跑过一次（贴出调用和输出），且四条全中：能亮红（驱动真实 bug 代码路径、断言用户的确切症状，不是「没报错就算过」）· 确定（每次同判决）· 快（秒级）· agent 能无人值守跑。原话点破本课要害："If you catch yourself reading code to build a theory before this command exists, stop — jumping straight to a hypothesis is the exact failure this skill prevents."

3. Phase 2–4：后面全在「消费」这条回路

回路一旦亮红，剩下的都是机械动作——每一步都靠这条回路给判决：

  1. Phase 2 · 复现 + 最小化

    跑回路、看它变红，先确认这是用户描述的那个症状（不是旁边碰巧的另一个 bug——wrong bug = wrong fix）。然后把复现砍到最小：输入/调用者/配置/数据/步骤一次砍一个、每砍一刀重跑，直到每个剩下的元素都 load-bearing（承重，删任一个就变绿）。最小复现＝缩小 Phase 3 的假设空间 + 变成 Phase 5 的干净回归测试。

  2. Phase 3 · 假设

    测任何一条之前，先生成 3–5 条排好序的假设（只想一条会锚死在第一个念头上）。每条必须可证伪：「若 X 是因，则改 Y 会让 bug 消失 / 改 Z 会让它更糟」——说不出预测的就是 vibe，丢掉或磨利。把排序清单先给用户看：他们常一眼重排（「我们刚给 #3 上过线」）或告诉你哪些已排除。便宜的检查点、省大把时间；用户 AFK 就按自己排序走。

  3. Phase 4 · 探针（instrument）

    每个探针对应 Phase 3 的一条预测，一次只动一个变量。工具优先级：debugger/REPL（一个断点胜十条 log）> 边界处的定向 log > 绝不「log everything and grep」。每条 debug log 打唯一前缀 [DEBUG-a4f2]——收尾时一条 grep 全清（没打标签的会活下来）。性能回归：log 通常没用，先立基线测量（timing harness / profiler / query plan）再 bisect，先测量后修。

4. Phase 5–6：修 + 回归，以及匝道怎么汇回主流程

这两阶段藏着 diagnosing-bugs 作为匝道的汇入点——也是 第 13 课点过、本课坐实的那条线：

  1. Phase 5 · 修 + 回归测试

    先写回归测试、再修——但只在有 correct seam（正确接缝）时。correct seam ＝测试能在真实 bug 触发的那个调用点上复现 bug 模式。若唯一能用的 seam 太浅（单调用者测多调用者的 bug、单元测试复现不了触发链），在那儿写回归测试只会给虚假信心。没有 correct seam，这件事本身就是一个发现——是代码架构在阻止你把 bug 锁死，记下来、举给下一阶段。

  2. Phase 6 · 收尾 + 复盘（post-mortem）

    宣布完成前的清单：原始复现不再复现（重跑 Phase 1 回路）· 回归测试通过（或记录 seam 的缺席）· 所有 [DEBUG-] 清干净 · 一次性原型删掉 · 把「猜对的那条假设」写进 commit/PR（好让下一个调试者学到）。然后问一句：什么本可以防住这个 bug？

关键就在最后这一问。diagnosing-bugs 多数时候在原地闭环（建回路 → 修 + 回归即结）；只有当复盘答案指向架构问题（没有好 seam、调用者纠缠、隐藏耦合）时，才把那块架构（不是 bug 本身）交给 improve-codebase-architecture——而且是修完之后再提建议（此刻你掌握的信息比开工时多得多）。这就是它汇回主流程的唯一接口。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. 接手一个难 bug，diagnosing-bugs 要你做的第一件事是？

2. 修 bug 时发现没有能真实复现 bug 的 correct seam，该怎么办？

3. 复盘发现这个 bug 根子在架构（调用者纠缠、没好 seam）。diagnosing-bugs 把什么、交给谁？
