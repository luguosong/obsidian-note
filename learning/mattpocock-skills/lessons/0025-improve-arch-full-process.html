improve-codebase-architecture 三步细节：Explore 找什么 / 报告卡长什么样 / Grill 副作用何时触发

第 12 课建立了「三步框架」（Explore → 报告 → Grill）和核心判断（只挑一张、用 grilling 不用 wayfinder）。这一课往框架里填血肉：Explore 子 agent 具体找什么摩擦信号、报告每张卡有哪 6 个字段、Grill 的三个 inline 副作用各自在什么条件下触发。读完就能核对一次真实跑出的报告是否合规。

一句话收获：Explore 先做范围决策（有方向直取、没方向跑 git log），再用 5 类摩擦信号找候选；报告每张卡有 6 个固定字段，故意在这一步不提接口；Grill 的三个 inline 副作用各有精确触发条件，不是每次 Grill 都全跑。

1. Explore：先决定看哪里，再决定看什么

Explore 分两层——范围决策在前，摩擦扫描在后。范围决策的规则很简单：

条件做什么
用户指定了方向（某个模块、子系统、某个痛点） 直接取用户说的方向，跳过 git log 推断
用户没指定方向 走 git log --oneline，找热点——近期反复出现的文件和区域；改动很分散没热点，就扩网

SKILL.md 的原则："Scope before you scan — YAGNI. Deepening a module pays off by making future changes to it easier, so put extra weight on the parts of the codebase that have recently changed."

范围定了，子 agent 开始有机地探索——不走死板 checklist，而是找摩擦感。SKILL.md 列了 5 类摩擦信号：

  1. 概念太分散

    理解一个概念需要在很多小模块之间跳来跳去——locality（局部性）差的典型症状。

  2. 接口过于复杂（浅模块）

    模块的接口几乎和它的实现一样复杂，没有给调用者提供 leverage（杠杆）。

  3. 为了可测性提取纯函数，但 bug 藏在调用方式里

    纯函数本身无状态好测，但真正的 bug 发生在调用上下文里——locality 缺失的另一种形态。

  4. 模块之间跨 seam（接缝）泄漏耦合

    模块间的边界没有真正隔离，一侧的实现细节渗透到另一侧。

  5. 未被测试或难以通过现有接口测试

    测试写不进去，多半是接口形状不对——「接口即测试面」（the interface is the test surface）。

删除测试（deletion test）是通用探针

遇到可疑的模块，SKILL.md 给的快速判断方法："想象把它删掉——复杂度凭空消失就是个转发壳（浅，该深化）；复杂度在 N 个调用点重新冒出来就是在挣钱（深，别动）。"这个探针在摩擦扫描的任意时刻都可以用，不是只用一次。

2. 报告：候选卡的 6 个字段 + 两条硬约束

Explore 结束后，agent 把候选写成一份自包含 HTML 文件，写到 OS 临时目录（$TMPDIR → /tmp → %TEMP%，命名 architecture-review-<timestamp>.html），打开给你看并报告绝对路径。不落仓库。

每张候选卡有 6 个固定字段：

字段填什么
Files（文件范围）涉及哪些文件 / 模块
Problem（问题）当前架构为什么产生摩擦——用 codebase-design 词汇（浅/深/seam/leverage/locality）描述，不用 service/component/API
Solution（方案）会有什么变化，用平白英语描述
Benefits（收益）用 locality 和 leverage 解释收益，以及测试会如何改善
Before / After 图并排可视化：展示「浅」的现状和「深化」后的结构；每张卡独立绘制
Recommendation strength（推荐强度）三档之一：Strong / Worth exploring / Speculative，渲染成 badge

报告结尾有一个 Top recommendation 段——agent 建议先从哪张卡入手及原因。这是懒得权衡时的起点（见第 12 课）。

两条硬约束：

  • Do NOT propose interfaces yet（不在报告里提接口）——接口的具体设计在第 ③ 步 Grill 里敲定；报告只描述问题和方向，不做接口决策。文件写好后，agent 只问一句："Which of these would you like to explore?"
  • ADR 冲突要标注，但只在摩擦真实时才浮出——如果某张候选卡和已有 ADR 有矛盾，用警告 callout 标注（"contradicts ADR-0007 — but worth reopening because…"）；但理论上被 ADR 禁止的重构不逐条列出，只在摩擦严重到值得重开 ADR 时才写进卡。

3. Grill：三个 inline 副作用的精确触发条件

你挑中一张卡后，agent 跑 /grilling（见第 17 课）拷问决策树。这期间有三个 inline 副作用，不是每次 Grill 都全触发——各有各的条件：

副作用触发条件做什么
更新 CONTEXT.md 深化后的模块用了 CONTEXT.md 里没有的概念名，或对话中磨利了某个模糊术语 当场运行 /domain-modeling，把新概念 / 精确后的术语加进 CONTEXT.md（文件不存在就懒创建）
提议写 ADR 你用一个承重理由否掉了某张卡——该理由将来真会被未来探索者需要来避免重复建议 agent 询问："要不要记成一条 ADR，免得下次架构审查又提它？" ——只在理由有持久价值时才提；"现在不值得做"这类临时理由不记，自明理由也不记
比较接口方案（design-it-twice） 想对深化后模块的几种接口画法做比较 运行 /codebase-design 的 design-it-twice（并行子 agent 模式），同时探索两种接口设计再汇报

Grill 的产出是决策 / 设计，不是代码

SKILL.md 在 grilling loop 之后就停了——这条 skill 不规定下游。三步跑完，你拿到的是一个设计决策。落地走主流程：to-spec → to-tickets → implement。单个小而清晰、seam 在 Grill 里已定的深化，可跳过 to-spec 直连 to-tickets（它能直接吃当前对话）；较大或多 ticket 则走 to-spec 先产 spec 文档。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. Explore 阶段，什么时候才跑 git log --oneline 找热点？

2. 下面哪项是报告阶段（步骤②）明确禁止做的？

3. Grill 阶段，什么情况下才向维护者提议记一条 ADR？
