第 8 课 · 单 skill 深挖 · 领域层

docs/adr/ 只增不改，时间久了不会膨胀到读不动吗？

第 7 课你把 docs/adr/（ADR，架构决策记录）记成了「只增不改账本」。于是一个很自然的担心冒出来：只增不删 → 无限膨胀 → agent 迟早读不动。这节课把这个担心彻底拆掉。

一句话收获：docs/adr/ 不会拖垮 agent，靠三重防线——① 写入有三条件硬闸门，长得极慢；② agent 从不整本读，按文件名随机寻址、只开与当前 area（工作区域）相关的几份；③ 真到规模会按 bounded context（限界上下文）分片。所以「只增不改」在这里不等于「膨胀成负担」。

1. 先说清：一份 ADR 到底长什么样

ADR = Architecture Decision Record（架构决策记录）——一份记录「某个架构决策 + 为什么这么定」的极小 markdown 文件。不是设计文档、不是方案书，就是一张写给未来工程师的便签。

形态极简（据 ADR-FORMAT.md）：住在 docs/adr/，顺序编号 0001-event-sourced-orders.md、0002-postgres-for-write-model.md……；模板就一个标题 + 1–3 句话——背景是什么、决定了什么、为什么。照模板填出来一份真实的 ADR 大概长这样：

# 订单写模型采用事件溯源

订单的写模型走 event sourcing（事件溯源），读模型投影进 Postgres。
因为需要完整的订单变更审计流水；代价是读取侧要额外维护投影。

为什么要有它？代码只告诉你「现在是怎样」，不告诉你「当初为什么这么选」。ADR 补的就是那个 why。最经典的场景——你故意用手写 SQL 而不用 ORM。没有 ADR，半年后新来的工程师一看「这不对啊」，顺手「修」成 ORM，把你深思熟虑的选择改坏了；一份 ADR（「我们故意不用 ORM，因为 X」）就把这次「好心办坏事」挡住了。

ADR 不是本 skill 独创

ADR 是业界通行实践（约 2011 年 Michael Nygard 提出），domain-modeling 只是把它纳进来、再加上「三条件」这道更严的闸门（详见后文防线一）。所以它是一个可迁移的通用概念，不只服务于 Matt Pocock 的 skill。

2. 再拆掉那个错觉：「只增不改」≠「越读越慢」

一个 append-only（只追加）的存储会变得难维护，只有当你必须从头到尾顺序读完它时——比如一条越滚越长、每次都得从头翻的聊天记录。但 docs/adr/ 从设计上根本不是这样被读的。

它是一叠按文件名随机寻址的独立小卡片，不是一卷需要顺序展开的长轴。所以「条目在增加」这件事，本身并不制造阅读负担——真正决定负担的是写入速度和读取方式。下面三节，就是卡住这两头的三重防线。

对照第 7 课

第 7 课把 docs/adr/ 和 .out-of-scope/ 归为只增不改账本（新增、被推翻标 superseded 不删）。「只增不改」是为了保住历史（我们如何走到今天），不是让你顺序通读。这节课解释：为什么保住历史，不必以牺牲可读性为代价。

3. 防线一 · 写入有硬闸门，所以长得极慢

ADR 不是决策日志。domain-modeling（领域建模）skill 给写入设了一道很高的门槛——一个决策只有三条同时成立才够格写成 ADR，缺一即跳过：

  1. 难以逆转（hard to reverse）

    以后改主意的代价是实打实的。「容易回退的就别写——反正你会回退它。」

  2. 不解释会让人困惑（surprising without context）

    未来的读者看着代码会纳闷「当初到底为啥这么干？」。不奇怪的，没人会问。

  3. 是真权衡的结果（real trade-off）

    当时有真实的备选，你为具体理由选了这个。没有备选，就没什么可记的。

对比一下就懂它有多克制：commit log 每次提交都长、learning-records（学习记录）每上一课都长——它们是「事件流」。而 ADR 有这道闸门，绝大多数决策根本进不来。它只以架构级的步子前进：「我们用 monorepo」「写模型走 event-sourcing、读模型投影进 Postgres」「Ordering 和 Billing 只通过领域事件通信」。这种决定，一个成熟仓库好几年也就攒下几十份。

而且每份都极小——ADR-FORMAT.md 明说「一份 ADR 可以只有一段、1–3 句话」。几十份 1–3 句的卡片，加起来不过几页纸。膨胀根本无从谈起。

4. 防线二 · agent 从不整本读（文件名就是索引）

这才是你问的「agent 怎么读」的正解：它不整本读。而且这条读取策略不是碰运气，是白纸黑字写在第 7 课那个「配置层」里的——你自己仓库的 docs/agents/domain.md：

docs/adr/ — read ADRs that touch the area you're about to work in.
— 你的 docs/agents/domain.md（setup 写、所有工程 skill 探码前读）

机制很朴素：文件名 0001-event-sourced-orders.md（编号 + 决策短名）本身就是索引。agent 先列目录（便宜——只是一串文件名）→ 拿当前任务的关键词去比对标题 → 只 open 命中的那几份（昂贵的正文按需加载）。这就是 progressive disclosure（渐进披露）：元数据（文件名）便宜、常扫；正文昂贵、按需取。

这就是第 2 课那条原则的复现

第 2 课的 context hygiene（上下文卫生）/ smart zone（约 120k token 内模型仍锐利的窗口）：永远别把整个 repo 灌进上下文，只灌相关切片。docs/adr/ 正是这条原则的落地——它是随机寻址，不是顺序加载。哪怕有 500 份 ADR，agent 一次也只碰其中三五份。

5. 防线三 · 真到规模，按 bounded context 分片

就算一个仓库大到 ADR 真的多起来，它也从不作为一整堆存在。当仓库根出现 CONTEXT-MAP.md（上下文地图），就说明这是多上下文仓库——ADR 会跟着 bounded context 切开，各回各家：

/
├── CONTEXT-MAP.md
├── docs/adr/                    ← 只放跨系统的全局决策
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/            ← 只属于 ordering 的决策
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/            ← 只属于 billing 的决策

在 billing 里干活的 agent，只读 src/billing/docs/adr/ + root 的全局那几份，永远不碰 ordering 的。CONTEXT-MAP.md 负责路由。那个你担心「会膨胀的大目录」，一开始就按 context 切成了小格，每个 agent 只碰自己那一格。

这是 DDD 落到文件系统

bounded context 是 第 1 课「4 失败模式」里 #2 verbosity（没有共享语言）那本《领域驱动设计》的核心概念。ADR 按 context 分片，就是把领域边界物理化——每个上下文自管自己的架构决策，跨界的才上升到 root。规模越大，这种分片越省心。

6. 那 superseded 的「僵尸 ADR」呢？

被推翻的旧决策，按账本规矩不删——只在它的 Status（状态）前置字段标上 superseded by ADR-NNNN（已被 ADR-NNNN 取代）。你可能担心：这些僵尸不是白占地方？

其实几乎零成本。因为读取是「文件名随机寻址 + area 过滤」：agent 要么按标题就把它划过去，要么真打开这个主题时，Status 那一行立刻把它转指到取代它的新 ADR。历史（我们怎么走到今天、为什么改主意）留住了，却不污染当下这一次阅读。这正是「只增不改」想要的：保住痕迹，又不拖累现在。

检索练习 · 三连

选中即判。答错会揭示正解与解析——错一次记得更牢。

1. docs/adr/「只增不改」，为什么不必然越来越难读？

2. 一个决策要同时满足哪三条，才够格写成 ADR？

3. 仓库大到出现多个 bounded context 时，ADR 怎么放？

推荐一手源

「会不会膨胀」的答案分散在写入端（领域层 skill）和读取端（配置层 doc）两处，都可直接核验：

  • domain-modeling / SKILL.md —— 写入端：单/多上下文的文件结构（含分片树）、「lazy creation（惰性创建）」、以及 Offer ADRs sparingly 的三条件。
  • domain-modeling / ADR-FORMAT.md —— ADR 的格式真相：模板只要 1–3 句、Status: superseded by ADR-NNNN 字段、编号规则，以及「什么才 qualify」的清单。
  • 你自己的 docs/agents/domain.md —— 读取端的活样本：「read ADRs that touch the area you're about to work in」、多上下文再查 src/<context>/docs/adr/、文件不存在就 proceed silently。这正是第 7 课「配置层」在管「怎么读」。
