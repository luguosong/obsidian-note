diagnosing-bugs · 紧反馈回路与六阶段

一张卡钉死：难 bug 别急着猜原因——先造一条能亮红灯的紧回路，后面全是机械动作。配套 第 15 课，适合打印贴墙。

一条主线

Phase 1 就是整条 skill。有一条能对这个 bug 亮红灯的紧回路 → 二分/假设/探针都只是消费它；没有 → 盯着代码看也没用。铁律：「没有能亮红的命令，就不许进 Phase 2」——它专防「读代码 → 猜原因」这个本能。（和 tdd 同源的紧回路纪律，用在 bug 上。）

治 4 失败模式 #3 code-doesn't-work · model-invoked（说「debug this / 报错 / 好慢」就触发）· 探码前读 CONTEXT.md + 该区 ADR。

Phase 1 · 造回路（不成比例地下功夫）

完成判据——报得出一条已跑过一次的命令（贴调用 + 输出），四条全中：

  • ☑ red-capable（能亮红）：驱动真实 bug 路径、断言用户的确切症状——不是「没报错就算过」
  • ☑ deterministic（确定）：每次同判决（非确定 bug：钉住的高复现率）
  • ☑ fast（快）：秒级，不是分钟级
  • ☑ agent-runnable：能无人值守跑（要人则用 HITL 脚本结构化驱动）

十种造法，按优劣排序（能用上面的就别用下面的）：

档手段
1失败测试（在够到 bug 的 seam：unit/集成/e2e）— 首选
2–3curl/HTTP 打 dev server；CLI + fixture diff 已知good快照
4–5headless 浏览器脚本；回放抓下来的真实 trace/payload
6–7一次性 harness（最小子系统 mock 依赖）；property/fuzz（1000 随机输入）
8–9bisection harness（git bisect run）；differential（新旧版本同输入 diff）
10HITL bash 脚本（scripts/hitl-loop.template.sh 的 step/capture）— 兜底

有了一条还要 tighten：更快（缓存 setup）· 信号更利（断言具体症状）· 更确定（钉时间/种 RNG/隔离 fs·网络）。非确定 bug 不追求干净复现，抬复现率到可调试（50% 可调，1% 不可）。

六阶段速览

Phase动作完成/要点
1 回路造紧的、能亮红的回路（整条 skill）一条已跑过的命令 · 四条判据全中
2 复现+最小化跑回路变红；确认是用户的症状非邻居 bug；一次砍一个每个剩下元素都 load-bearing（删任一变绿）
3 假设测之前先列 3–5 条可证伪假设、排序、给用户看「若 X 是因，则改 Y 会消失」；说不出预测＝丢
4 探针一探对一预测、一次一变量；debugger>定向log>绝不 log-all[DEBUG-a4f2] 标签单 grep 清；perf 先测量
5 修+回归先写回归测试再修——但只在有 correct seam 时无 seam＝发现（架构在阻止锁死）→ 举给 Phase 6
6 收尾+复盘清 [DEBUG-]/删原型/对的假设写进 commit；问「什么本可防住」原地闭环 ship；架构问题→交 improve-arch

匝道汇入点：多原地闭环，仅无 seam 时交架构

建回路 + 修 + 回归多数情况
→
原地闭环 ship不汇入主流程
复盘＝架构问题无好 seam/调用者纠缠
→
交 improve-codebase-architecture交架构非 bug · 修完之后

关键：交出去的是那块架构（不是 bug 本身），而且在修完 bug 之后提建议——此刻掌握的信息比开工时多。
