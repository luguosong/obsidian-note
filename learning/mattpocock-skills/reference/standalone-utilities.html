prototype · 一次性代码答一个问题

问题决定形状，第一步选分支（选错＝整个原型白做）：

问题分支 → 产物
「逻辑 / 状态模型对不对？」LOGIC → 终端 app 推状态机过难 case
「该长什么样？」UI → 一条路由几个差异极大的变体切换

歧义且无人问 → 按周围代码默认（后端→LOGIC / 页面→UI）+ 顶部写明假设。

六规矩：① 一次性、标明是原型 ② 一条命令能跑 ③ 默认不持久化（状态放内存）④ 跳过打磨（无测试/抽象）⑤ 摊开状态给你看 ⑥ 捕获＝promotion（决策折进真代码、原型 commit 到 throwaway 分支、主分支只留决策）。

research · 后台查一手源

起后台 agent，你继续干活它一边读（AFK）。三铁律：

  • 只认一手源（官方文档 / 源码 / 规格 / 第一方 API），不吃二手转述，每条论断追回拥有它的源。
  • 写进一份带引用的 Markdown（每条标源）。
  • 按仓库既有约定存；没有就找合理处并说清放哪。

是 RESOURCES「一手源优先·不信参数记忆」的机器化身。与 prototype 分工：research 去读 / prototype 去造。

resolving-merge-conflicts · 合两个意图

冲突 = 两个意图相撞，不是两段文本打架。五步：

  1. 看清状态

    查 git 历史 + 哪些文件冲突

  2. 为每冲突追一手源

    读 commit / PR / issue，懂每边为什么那么改（你合不了你不懂的意图）

  3. 逐 hunk 解

    能保则两意图都保；不兼容选匹配 merge 目标的、记 trade-off。不发明新行为 · 绝不 --abort · 永远解完

  4. 跑项目检查

    typecheck → 测试 → 格式化，修好 merge 弄坏的（「能编译」≠行为正确）

  5. 收尾

    stage + commit；rebase 则续到底

三禁：凭手感挑边 / franken-merge 揉出新行为 / 停在「无冲突标记」就收。
