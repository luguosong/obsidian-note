seam（接缝）· 一个概念，四门 skill 从不同角度接力

和别的卡不同——这张不压一门 skill，而是把 seam（接缝）这一根线，横着串过第 12·18·2·15 课。适合打印贴墙。

一句话定义（Michael Feathers）

seam ＝ 能在别处改变行为、而不必在那处动刀的地方；也就是一个模块的接口所在的位置。「把接缝放在哪」本身是一个设计决策，和「接缝后面放什么」是两回事。

配套一句尺：interface 就是 test surface（测试面）——调用者和测试跨的是同一条缝。要测到「接口之后」，多半是模块形状不对。⚠️ 别叫它 boundary（已被 DDD 的 bounded context 占用）——说 seam 或 interface。

四门 skill × seam：各接一棒

skill（课）对 seam 干什么关键判据 / 措辞
codebase-design
第 12 课		 命名它——给出 seam 的定义与词汇（深/浅模块、leverage/locality） 把接缝放哪是独立设计决策；深模块＝小接口后藏大量行为，测试就贴接口
to-spec
第 18 课		 决定它——主流程里第一次勾出测试接缝并跟你确认 四偏好：现有优先 · 位置最高 · 数量最少（理想一个）· 跟你确认
tdd
第 2 课（implement 内）		 在它上面测——只在 pre-agreed（事先约定）的 seam 上写测试 观察行为、不伸手进内部；未确认的接缝上不写测试
diagnosing-bugs
第 15 课		 要求它 correct——回归测试要有能复现 bug 的正确接缝 太浅＝虚假信心；没有 correct seam 本身＝一个（架构）发现

串成一条线

codebase-design命名（什么/放哪）
→
to-spec决定（勾+确认·首次）
→
tdd在其上测（pre-agreed）
→
diagnosing-bugs要求 correct（否则举架构）

同一个「在哪观察行为」的问题被四门 skill 接力：to-spec 是主流程里的起点；diagnosing-bugs 发现接缝不对时，把那块架构交回 improve-codebase-architecture（用的正是 codebase-design 词汇）——回到第一棒，闭环。

判接缝的两把尺（codebase-design）

  • deletion test（删除测试）：想象把模块删掉——复杂度凭空消失＝纯转发壳（浅，接缝可疑）；复杂度在 N 个调用点重现＝它在挣钱（深，接缝真实）。
  • 一个 adapter＝假想接缝，两个＝真接缝：除非真有东西跨接缝变化，否则别引入接缝。
  • internal seam vs external seam：external＝模块接口那条（调用者 + 测试跨它）；internal＝实现私有、给它自己的测试用。深模块内部可以有很多可换的小件，只是不进接口。
