记忆二分 · 长期记忆 vs 工作记忆

一张卡回答：skill 生态管的四块文件区，其实沿「读多久」分两类记忆——工单层为什么用完即冻、又靠什么兜底。配套 第 9 课，适合打印贴墙。

四块区 → 两类记忆

记忆类型哪些区域维护特征读取时机
长期记忆
（读好几年）		 ① 配置层
② 领域层（CONTEXT.md · docs/adr/）
④ .out-of-scope/		 第 7 课那三种模式：一次性脚手架 / 活的真相 / 只增不改账本 随时被相关 skill 读，跨越很多 feature
工作记忆
（用完冻结）		 ③ 工单层（.scratch/ 或 issues · spec · ticket） 第四种：用后冻结——不属于上面三种长期模式 只在该 feature 在途 / 评审时读

关键澄清：工单层不是第四种长期维护模式；它是唯一的工作记忆——把一份工作从 idea 运到 ship 的临时台面，运到就收台。

工单层生命周期：活跃 → ship → 冻结退役

  1. 活跃在途

    spec.md → 纵切 ticket → 逐片 implement，frontier（阻塞全清的）被一片片消费。

  2. ship

    最后一片纵切过 code-review、合并。这个 feature 的工作结束。

  3. 冻结退役

    GitHub → issue close（不删），冻成历史、和 PR/commit 链在一起；.scratch/ → 目录留原地，一张计划快照。都是「写一次就冻结」，非活文档。
.scratch/<feature-slug>/
├── spec.md                ← to-spec 产出
└── issues/
    ├── 01-<slug>.md        ← 一条纵切片一份文件
    └── 02-<slug>.md        ← blockers-first 编号

为什么敢「用完即弃」——靠「提升（promotion）」兜底

工单敢做成一次性，正因值得长期留的东西，在 ticket 死之前已被抬进长期层。这个动作 = 提升：

在途产生的东西提升到哪个长期层
架构级的「为什么这么定」ADR（领域层，读好几年）
新确立的领域术语CONTEXT.md（活的真相）
干出来的代码本身代码库（实现落地）
被拒的 enhancement.out-of-scope/（只增不改账本）
prototype 的验证结论折进真代码 + issue 留 context pointer

提升的活样本：prototype

它收尾第一句就是提升：「Fold any validated decision into the real code… The main branch keeps only the validated decision.」结论被提升、载体被丢弃——正是工单层的缩影。所以 ticket 是可丢弃的载体：keepers 卸货进长期层后，空车退役即可。

提升 ≠ 归档/备份（那是原样搬运）；提升是「蒸馏 keepers 再抬走」。
