多人协作下文档会不会失真 · 漂移与重新对齐

一张卡回答：别人推一大批提交、不写 ADR / 不用 skills，你的领域层会「失真」吗——失真到底指什么、怎么显形、怎么补。配套 第 10 课，适合打印贴墙。

先把「失真」摆正：改不脏 vs 会掉队

旧 ADR 条目会被改脏吗？——不会。ADR 是只增账本、不可变的时间戳事实，别人改代码改写不了当年那个决策发生过。文档会落后于代码吗？——会，这才是失真的真身。领域层两种介质、各以不同方式掉队：

介质本该是什么别人不同步时怎么漂漂移签名
docs/adr/
（只增账本）		 某时某人「为什么这么定」的历史决策 做了新架构决策，却没写 superseding ADR 漏记 supersede：集合成不完整历史——旧条目仍真、只是过时
CONTEXT.md
（活的真相 / 术语表）		 镜像当前现实的领域术语表 代码里改了概念名，却没同步字典 术语滞后：字典主动说谎（还写 Order，代码早是 Purchase）

一句话：失真 ≠「旧条目被改脏」（ADR 改不脏）；失真 =「文档落后于代码」——ADR 覆盖度缺口 + CONTEXT.md 术语滞后。

为什么不会「悄悄」失真：三道显形闸

关键不在「阻止别人制造漂移」（管不了），而在漂移一旦存在就一定被摆上桌。前两道就写在你自己的 docs/agents/domain.md：

  1. Cross-reference with code（拿文档核对代码）

    domain-modeling 的硬动作：你一说「某处怎么工作」，它就核对代码、发现矛盾当场质问。同事埋下的漂移，在这一步变成一个被追问的问题。

  2. Flag ADR conflicts（与 ADR 冲突就举旗）

    domain.md 明写「显式点出、别静默覆盖」。代码与一条过时 ADR 打架时，agent 举旗：「与 ADR-0005 冲突——但代码似乎已改，这条像过时了。」

  3. Glossary gap 信号（字典里没有 = 信号）

    需要的概念不在字典里就是信号：要么你在造项目不用的词（收手），要么真有缺口（记给 domain-modeling）。同事没进 CONTEXT.md 的新术语，以「缺口」浮上来。

三道闸的共性：把漂移从「悄悄的、我以为文档还准」变成「显形的、被举旗的分歧」——你至少知道这里对不上了。

漂移可回补：重新对齐（reconciliation）

显形之后怎么补——一个拉取式（pull-based）动作，只在你下次动工该区域时发生，非主动全仓扫描：

git log --oneline回溯找热点
→
热点 = 同事那批提交落点读该区 CONTEXT + ADR
→
grill 出摩擦inline 更新领域模型
→
回补 / 刷新补漏记 ADR · 刷 CONTEXT

入口两条：improve-codebase-architecture（Explore 第一步就是走 git log 找热点）；更轻的 grill-with-docs（下次在该区规划新活时，domain-modeling 的 cross-reference 顺手补掉）。

诚实的边界

  • 拉取式、按动工区触发：没人碰的旧文档代价 ≈ 0（不读就不痛）。
  • ADR 是护栏不是镜子：「ADRs record decisions this command should not re-litigate」——记的是不该重翻的决策，不是代码状态的实时镜像。
  • 全队完整性是社会问题：skill 只保证「你经过时漂移会显形并可补」，管不了别人写不写——那一半去社区练判断（见 RESOURCES.md Wisdom 区）。

漂移不是终点，是一个会被下一次经过治好的回路。
