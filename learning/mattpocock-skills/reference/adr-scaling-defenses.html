docs/adr/ 只增不改，为什么不膨胀 · 三重防线

一张卡回答：一份 ADR 长什么样、以及「只增不改」为什么不等于「越读越慢」。配套 第 8 课，适合打印贴墙。

一份 ADR 长什么样

ADR = Architecture Decision Record（架构决策记录）：一份记「某架构决策 + 为什么」的极小 markdown，住在 docs/adr/、顺序编号，模板就一个标题 + 1–3 句（背景 / 决定 / 为什么）。它补的是代码不说的那个 why。

# 订单写模型采用事件溯源

订单写模型走 event sourcing，读模型投影进 Postgres。
因为需要完整的订单变更审计流水；代价是读取侧要额外维护投影。

业界通行实践（Michael Nygard，约 2011），非本 skill 独创；domain-modeling 只是纳进来再加一道更严的「三条件」闸门。

防线一 · 写入有硬闸门 → 长得极慢

ADR 不是决策日志。一个决策三条同时成立才够格写，缺一即跳过：

  1. 难以逆转（hard to reverse）

    以后改主意代价实打实。容易回退的别写。

  2. 不解释会困惑（surprising without context）

    未来读者看代码会问「当初为啥这么干」。不奇怪的没人问。

  3. 是真权衡的结果（real trade-off）

    当时有真实备选，你为具体理由选了这个。没备选就没什么可记。

对比：commit log 每次提交都长、learning-records 每课都长（事件流）；ADR 有闸门，绝大多数决策进不来，只以架构级步子前进——成熟仓库好几年才攒几十份，每份 1–3 句，加起来不过几页纸。

防线二 · agent 从不整本读（文件名即索引）

读取策略白纸黑字写在配置层你自己的 docs/agents/domain.md：「read ADRs that touch the area you're about to work in」。文件名 0001-event-sourced-orders.md（编号 + 决策短名）本身就是索引：

列目录一串文件名 · 便宜
→
比对标题拿当前任务关键词
→
只 open 命中正文按需 · 昂贵

这是 progressive disclosure（渐进披露），也是第 2 课 context hygiene / smart zone 的落地——随机寻址，不是顺序加载。哪怕 500 份 ADR，一次也只碰三五份。

防线三 · 真到规模，按 bounded context 分片

仓库根出现 CONTEXT-MAP.md = 多上下文仓库，ADR 跟着 bounded context 切开、各回各家：

/
├── CONTEXT-MAP.md
├── docs/adr/                 ← 只放跨系统全局决策
└── src/
    ├── ordering/docs/adr/    ← 只属于 ordering
    └── billing/docs/adr/     ← 只属于 billing

在 billing 干活的 agent 只读 src/billing/docs/adr/ + root 全局那几份，永不碰 ordering。CONTEXT-MAP.md 负责路由——那个「会膨胀的大目录」一开始就按 context 切成小格。这是 DDD 领域边界物理化。

superseded「僵尸 ADR」= 近零成本

被推翻的旧决策不删，只在 Status 标 superseded by ADR-NNNN。因读取是「文件名随机寻址 + area 过滤」：agent 要么按标题划过，要么打开时 Status 那行立刻把它转指到新 ADR。历史留住，又不污染当下阅读。

一句话：写入被闸门卡到极慢 + 读取从不整本 + 规模化按 context 分片——三重防线让「只增不改」保住历史却不牺牲可读性。
