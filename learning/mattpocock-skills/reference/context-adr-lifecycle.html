CONTEXT.md 与 ADR：什么时候产生、什么时候更新

一张卡钉死一件事——何时新建这两个文件、何时动它们。配套 第 8 · 16 课，适合打印贴墙。前提一句话先说死：读 CONTEXT.md 取词是任何 skill 的一行习惯（被动消费），不是本卡讲的纪律——本卡讲的是 domain-modeling 在主动改模型时写它们的规矩。

0. 先画线：读 ≠ 写

被动消费（不触发本卡）主动建模（触发本卡全部规则）
你读 CONTEXT.md 让命名对齐术语——tdd 写测试前读、diagnosing-bugs 探码前读、to-spec 引用已有措辞。任何 skill 的一行习惯。 你正在改变模型：逼出一个词的精确定义、拍下一个架构决策、发现代码和说法打架。
This skill is for when you're changing the model, not just consuming it.
— domain-modeling / SKILL.md

下面所有「产生 / 更新」规则，只在右栏（主动建模）发生时才适用。左栏一行习惯，不产生也不更新这两个文件。

1. 总纲：三种动作，三条规则

两件产物加起来只有三种文件动作，每条一条铁律：

动作作用于规则触发时机（一句话）
create · 新建文件 两者 lazy 惰性 第一次有东西可写才建：第一个术语 resolved 时建 CONTEXT.md；第一份够格 ADR 来时建 docs/adr/。没东西就永远不建。
inline update · 当场改 CONTEXT.md 不攒批 一个术语刚 resolved（拍板）就当场写进去，don't batch — capture as they happen。
append · 追加不改 ADR sparing + 只增 三条件全中才追加；写完不改旧文，推翻＝新建一份＋旧的标 superseded。

为什么 CONTEXT 用「当场改」、ADR 用「只追加」

CONTEXT.md 是活的真相——术语含义会随理解变精确，所以 inline 更新；ADR 是只增账本——决策的历史本身有价值，所以旧决策不抹，只标被取代。两种文件，两种相反的更新哲学。

2. CONTEXT.md：产生与更新

  1. 产生 · lazy

    根 CONTEXT.md 在第一个术语被 resolved（拍下精确定义）时才建。在此之前没文件、不预建空壳。

  2. 更新 · inline，逐个当场写

    一个术语一结晶就立刻写进同一次会话，不攒到一批再写。这些词从哪来——domain-modeling 的四手法：challenge（用户词与字典冲突）/ sharpen（模糊词磨利）/ scenario（场景压测逼出边界）产出术语条目；cross-reference（拿代码核对说法）发现说法与代码打架时回补对齐。

装什么 / 不装什么（写法纪律）：只装本项目特有的领域术语，定义 tight（1–2 句、说它是什么不说它做什么），opinionated（多词同义挑最佳、其余列 _Avoid_）。

该写进 CONTEXT.md ✅不该写 ❌
本项目特有、刚被四手法逼出精确定义的领域词 通用编程概念（超时、错误类型）——即便项目在用
多词同义时挑定的规范词 + _Avoid_ 易混词 模块路径 / 函数签名 / 实现细节（那是代码）
选这个词背后的架构权衡理由（那是 ADR）

3. ADR：产生与更新

  1. 产生 · sparing，三条件同时全中才 offer

    一个决策三条全成立才够格写 ADR，缺一即跳过：
    • hard to reverse（难以逆转）——以后改主意代价实打实；容易回退的别写。
    • surprising without context（不解释会困惑）——未来读者看代码会问「为啥这么干」；不奇怪的没人问。
    • real trade-off（真权衡）——当时有真实备选，你为具体理由选了这个；没备选就没什么可记。
    第一个够格决策来时才 lazy 建 docs/adr/。

  2. 够格清单 · 什么样的决策值得写

    架构形态 · context 之间的集成模式 · 带 lock-in 的技术选型 · 边界与范围决策 · 刻意偏离显眼路径 · 代码里看不见的约束 · 非显然的否决备选（被否决这件事本身不明显时才记）。

  3. 更新 · append-only，不改旧文

    决策被推翻 不删不改原 ADR，而是新建一份，旧的在 Status 行标 superseded by ADR-NNNN。Status 取值：proposed | accepted | deprecated | superseded by ADR-NNNN。

模板极小——一个标题 + 1–3 句（背景 / 决定 / 为什么）。它补的是代码不说的那个 why。会不会膨胀见 ADR 三重防线卡。

4. 多上下文：何时拆 CONTEXT-MAP.md

仓库根出现 CONTEXT-MAP.md = 这是多上下文仓库。两件事跟着发生：

  • CONTEXT-MAP.md 路由到各 bounded context 各自的 CONTEXT.md，并含一个 Relationships 段，记录 context 之间如何交互（例如哪个发事件、哪个消费）。
  • ADR 跟着 context 切：根 docs/adr/ 只放跨系统全局决策，各 context 的 ADR 进 src/<context>/docs/adr/。在 billing 干活的 agent 不碰 ordering 的 ADR。

何时拆＝领域本身长出多个 bounded context（不同统一语言、不同团队节奏），不是按文件数凑。

5. 一句话口诀

没东西写就不建（lazy）；词一拍板当场进 CONTEXT（inline）；决策三条件全中才进 ADR（sparing）；ADR 只增、推翻新建不删旧的（superseded）。
