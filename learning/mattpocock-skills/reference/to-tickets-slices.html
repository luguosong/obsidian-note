to-tickets · tracer-bullet 纵切片与 expand–contract

一张卡钉死：怎么把 spec 切成又窄又完整的纵切片、怎么串依赖沿 frontier 推、以及唯一例外 wide refactor 怎么办。配套 第 19 课，适合打印贴墙。

一条主线：纵切，不是横切

每片 = 一条又窄又完整、穿透所有层（schema→API→UI→test）的竖切，自己就能 demo/验证。不是「先做完所有 schema、再做所有 API」的横切（那正是 tdd 反模式 horizontal slicing）。切错方向，后面每步都歪。

主流程第三步：grill-with-docs → to-spec → to-tickets → implement。它只做「切」这一格。

纵切四规矩

  • ☑ 又窄又完整、穿透每一层（schema→API→UI→test 竖着打通）
  • ☑ 自己就能 demo / 验证（做完是一个端到端行为，不是拼不起来的零件）
  • ☑ 装得进一个 fresh context 窗口（一片正好交一次 implement）
  • ☑ prefactor 先行（"make the change easy, then make the easy change"）

产出即工单层（工作记忆）：frontier 被一片片消费、ship 后冻结退役。一次一片 + 片间清空 = context hygiene 落地。不 close / 改任何 parent issue。

唯一例外：wide refactor 走 expand–contract

wide refactor = 一次机械变更（改列名 / 换共享符号类型），爆炸半径横扫全仓、一改断上千调用点，没有纵切能 land green。硬塞纵切会全红 → 改走三段：

expand 扩新形态与旧并存
什么都不破
→
migrate 迁按爆炸半径分批
每批阻塞于 expand
旧形态在→CI 保绿
→
contract 缩删旧形态
阻塞于所有迁移批

连分批都无法各自保绿时：保留序列，但共享一条 integration branch，全部阻塞于最后的 integrate-and-verify，绿色只在那里兑现。
