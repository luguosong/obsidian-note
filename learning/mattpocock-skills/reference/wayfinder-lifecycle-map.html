wayfinder 执行生命周期 · 工件落点

一张卡回答：wayfinder 从起手到 ship，每一步的产物落在哪种介质、动不动你的仓库文件树。配套 第 14 课，适合打印贴墙。

一条主线：工件介质二分

读任何一步「产生什么」，先分它落在哪种介质——tracker 上的 issue（map / 票 / spec / ticket）还是 git 里的文件（源码 / CONTEXT.md / .scratch/）。wayfinder 刻意几乎只产前者：全程在 issue 上打转，真·文件树的改动被推到最右的 implement 才发生。这就是 plan, don't do 的物证。

介质位移：tracker 决策 → spec/ticket issues → 已提交代码。真·文件只在最右一格落地。

三条铁律 + 判据

  • 介质随 tracker 而变（tracker-specific）：「wayfinder 产生哪些文件」无唯一答案。GitHub tracker（你的仓库）→ map/票是 issue、仓库零文件；local-markdown tracker → 才落成 .scratch/*.md。
  • 真·文件在 implement 才落地：整条弧上，源码/测试文件第一次也是唯一一次被提交到分支，是 implement 驱动 /tdd 那步。此前全在 issue（+ domain 惰性文件 + throwaway 分支）里打转。
  • 雾散 → 移交，不开建：默认汇入 to-spec（把 linked decisions 收拢成可构建 plan）→ to-tickets → implement。只有 effort 其实很小时才可跳过 to-spec 直连 implement（代价：丢掉「收拢」、丢票里细节）。

一句话闭合：wayfinder 先「决定」（issue）→ to-spec/to-tickets 把决定变「构建片」（issue）→ implement 才「建」（提交文件）。
