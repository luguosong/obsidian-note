安装原理深入：irm | iex 与 npm 的区别

第 1 课你敲了 irm https://claude.ai/install.ps1 | iex 就装好了，但这行命令到底做了什么？ 它和 npm install -g 装的不是同一个东西。这节课把官方安装脚本逐行拆开—— 看懂它下载什么、怎么校验、装到哪，理解「原生二进制」与「npm 包」两条路线的本质分野。

一句话收获：irm | iex = 下载脚本文本并当场执行；这段脚本下载的是一个独立原生二进制（不需要 Node），并用 SHA256 校验后自安装——而 npm 装的是一个需要 Node 运行的 JS 包。

1. 先拆这行命令：irm | iex 是什么

这行命令由两个 PowerShell cmdlet 加一个管道组成，两个都是别名：

写法全名作用
irmInvoke-RestMethod向 URL 发 HTTP 请求，把响应正文当字符串返回（这里返回的就是那段 .ps1 脚本文本）
|管道把左边返回的脚本文本，交给右边
iexInvoke-Expression把收到的字符串当 PowerShell 代码执行

所以整行的含义是：「从网上抓一段脚本，立刻在当前 PowerShell 会话里运行它」。它就是 Windows 版的 curl -sSL https://... | bash——同一种「一行流安装」模式，换了外壳。

关键认知：没有「审阅」这一步

irm | iex 抓到脚本后直接执行，你没有机会先读一眼。你信任的是 claude.ai 的 HTTPS 证书 + 服务器没被攻陷。想先审阅，就把两步拆开（见第 4 节）。

2. 脚本内部：七步流水线

逐步对照脚本原文看：

① 环境闸门：拒绝 32 位

if (-not [Environment]::Is64BitProcess) {
    Write-Error "Claude Code does not support 32-bit Windows."
    exit 1
}

第一件事就是把不支持的环境挡在门外——快速失败，不做无用功。

② 认清架构：ARM64 还是 x64

if ($env:PROCESSOR_ARCHITECTURE -eq "ARM64") {
    $platform = "win32-arm64"
} else {
    $platform = "win32-x64"
}

决定待会儿要下载哪个平台的二进制——ARM 机器拿原生 ARM64 版，不跑模拟。

③ 查最新版本号

$version = Invoke-RestMethod -Uri "$DOWNLOAD_BASE_URL/latest"

向发布服务器问「最新版是几」，拿到一个形如 2.1.224 的版本号。脚本还会校验返回值确实像版本号（防止拿到一个 HTML 错误页）。

④ 取 manifest，拿到「正确答案」SHA256

$manifest  = Invoke-RestMethod -Uri "$DOWNLOAD_BASE_URL/$version/manifest.json"
$checksum  = $manifest.platforms.$platform.checksum

下载该版本的清单文件，从里面读出本平台二进制应有的 SHA256 校验和。这是稍后验货的「标准答案」。

⑤ 下载二进制

$binaryPath = "$DOWNLOAD_DIR\claude-$version-$platform.exe"
Invoke-WebRequest -Uri "$DOWNLOAD_BASE_URL/$version/$platform/claude.exe" -OutFile $binaryPath

把真正的 claude.exe 下载到 ~/.claude/downloads。注意：这是一个编译好的原生 Windows 可执行文件，不是 JS 脚本。

⑥ 验货：SHA256 必须匹配

$actualChecksum = (Get-FileHash -Path $binaryPath -Algorithm SHA256).Hash.ToLower()
if ($actualChecksum -ne $checksum) {
    Write-Error "Checksum verification failed"
    Remove-Item -Force $binaryPath
    exit 1
}

对下载的文件算一遍 SHA256，和 manifest 里的「标准答案」比。不一致就删文件、报错、退出——这一步保证你运行的二进制没在传输途中被篡改或损坏。

⑦ 自安装 + 清理

& $binaryPath install $Target      # 让二进制自己配置启动器和 shell 集成
# ...
Remove-Item -Force $binaryPath      # 装完删掉临时下载的 exe

脚本不自己搬文件，而是调用刚下载的二进制的 install 子命令，让它自己完成落地（配置启动器、写 PATH、shell 集成），最后把临时下载的 exe 删掉。

版本可以钉死

脚本首行的参数 $Target 接受 latest（默认）、stable 或具体版本号 2.1.224。一行流默认装 latest；想钉版本，就把脚本存下来再带参数运行（见下一课的自动化场景）。

3. 核心区别：原生二进制 vs npm 包

irm | iex 走的是原生安装路线，npm install -g @anthropic-ai/claude-code 走的是 Node 包路线。它们最终都给你一个 claude 命令，但「装的是什么」完全不同：

维度原生安装（irm | iex）npm 安装（npm i -g）
装的是什么编译好的原生 claude.exe，自带运行时一个 JS 包（@anthropic-ai/claude-code）
依赖 Node.js?不需要——机器上没装 Node 也能跑需要，且要 Node ≥ 22
完整性校验脚本内置 SHA256 比对靠 npm registry 的 integrity 哈希
安装位置~/.claude/ 下（启动器 + PATH）全局 node_modules（如 %APPDATA%\npm）
升级方式claude update（二进制自更新）npm update -g @anthropic-ai/claude-code
适合谁只想用 Claude Code，不想碰 Node 工具链已有 Node 环境、想统一用包管理器管理

一句话记住

原生安装给你一个「什么都不依赖、拆箱即用」的独立程序；npm 安装把 Claude Code 当成你 Node 生态里的一个全局包来管。前者省心，后者好统一管理。

4. 安全视角：两层信任模型

「一行流安装」常被诟病不安全，但这个脚本其实有两层不同强度的信任，值得看清：

环节靠什么保证强度
抓取并执行 install.ps1 本身只有 HTTPS（TLS 证书 + 服务器可信）较弱：你没审阅就执行了
下载的 claude.exeHTTPS 加 manifest 里的 SHA256 比对较强：篡改会被校验拦下

换句话说：二进制的完整性有密码学校验兜底，但脚本第一跳只靠 TLS。如果你想更谨慎（企业环境、审计要求），把两步拆开、先读再跑：

# 先下载脚本到本地
irm https://claude.ai/install.ps1 -OutFile install.ps1

# 用编辑器或命令看一眼内容，确认无误
Get-Content install.ps1

# 确认后再执行
.\install.ps1

这不是 Claude Code 独有的取舍

curl | bash / irm | iex 是整个行业的通用安装模式（Homebrew、Rust、Deno 都用）。方便与「先审阅」天然互斥——理解这个取舍，按你的安全要求选择拆不拆开即可。
