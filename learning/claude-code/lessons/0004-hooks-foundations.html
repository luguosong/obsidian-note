Hooks 基础：确定性的生命周期自动化

你在 CLAUDE.md 里写「改完代码必须跑一遍 lint」， 但 Claude 有时就是忘了——因为那只是一句建议，模型可以不听。 Hook 不一样：它是一段在生命周期固定节点必然运行的代码。 这节课把 hook 的运行机制拆开——何时触发（生命周期）、怎么接线（三层配置）、 怎么裁决（stdin/stdout 协议）——建立能自己写护栏、审计、自动格式化的底层认知。

一句话收获：hook = 在 Claude Code 生命周期的某个事件上，用 matcher 过滤后运行你的处理器； Claude Code 通过 stdin 喂给它一段 JSON 上下文，处理器再用退出码或回吐的 JSON 告诉 Claude Code「放行、拦截、还是往上下文里塞点料」。这是确定性的控制，不是求模型配合。

1. 为什么要用 hook：建议 vs 保证

Claude Code 有两种「让它按规矩办事」的路子，强度天差地别：

CLAUDE.md / 提示词Hook
本质喂给模型的一段文字建议由 Claude Code 运行时执行的代码
可靠性概率性——模型可能忽略、忘记、误解确定性——只要事件触发就必然运行
能否强制不能真正阻止一个动作能——可直接拦下一次工具调用
适合风格偏好、背景知识、软约定硬规则：护栏、审计、自动格式化

官方文档把 hook 定义为「在 Claude Code 生命周期特定节点自动执行的用户自定义 shell 命令、HTTP 端点或 LLM 提示」[docs: Hooks reference]。关键词是自动与确定——它把「希望 Claude 做 X」变成「X 一定会发生」。

一个判断标准

「这条规则被违反一次，我能接受吗？」——能接受（如命名风格）→ 写进 CLAUDE.md；不能接受（如「禁止 rm -rf」「密钥不许进日志」「提交前必须过测试」）→ 写成 hook。

2. 生命周期：hook 在「何时」触发

Claude Code 一次会话里有很多可挂载的事件。它们按触发频率分成三档节奏（cadence）——先记住节奏，再记具体事件名，就不会乱：

节奏典型事件一句话
每会话一次SessionStart / SessionEnd会话开始 / 结束时各触发一次
每轮一次UserPromptSubmit / Stop你每提交一次提问、Claude 每答完一轮
每次工具调用PreToolUse / PostToolUseagentic loop 里每调一次工具，前后各一次

这只是最常用的 6 个。实际事件目录有 约 30 个——还包括 SubagentStart/Stop（子代理）、PreCompact（压缩上下文前）、Notification（通知）、PermissionRequest（权限裁决）、FileChanged（文件变动）等[docs: Hook events]。先吃透这 6 个骨架事件，其余按需查表即可。

3. 配置骨架：三层嵌套

hook 写在 JSON 设置文件里，结构永远是三层嵌套[docs: Configuration]：

  1. 事件（如 PreToolUse）—— 挂在哪个生命周期节点
  2. matcher 组（如 "Bash"）—— 过滤「什么时候才真的触发」
  3. 处理器 handler（如 type:"command" + 一条命令）—— 匹配后跑什么
{
  "hooks": {
    "PreToolUse": [                         // ① 事件
      {
        "matcher": "Bash",                  // ② matcher：只对 Bash 工具
        "hooks": [
          {
            "type": "command",              // ③ 处理器：跑一条命令
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
          }
        ]
      }
    ]
  }
}

matcher 怎么匹配

matcher 的值决定匹配方式[docs: Matcher patterns]：

写法含义
"*" / "" / 省略匹配该事件的每一次触发
"Bash"精确匹配单个工具名
"Edit|Write"匹配 Edit 或 Write（`|` 分隔多个）
"mcp__memory__.*"正则：某个 MCP 服务器的全部工具

注意：只有工具类事件（PreToolUse/PostToolUse 等）按工具名匹配；SessionStart 按「怎么启动的」匹配、UserPromptSubmit 干脆不支持 matcher（每次都触发）。matcher 匹配的字段各事件不同。

写在哪 = 作用范围

位置范围能否随仓库共享
~/.claude/settings.json你的所有项目否（本机私有）
.claude/settings.json单个项目能，可提交进 repo
.claude/settings.local.json单个项目否（默认 gitignore）

把团队护栏放进 .claude/settings.json 提交，全组自动生效；个人实验放 settings.local.json，不污染仓库[docs: Hook locations]。

Windows 用户：让 hook 跑 PowerShell

命令处理器默认用系统 shell。在 Windows 上给处理器加 "shell": "powershell"，即可用 PowerShell 跑（自动优先 pwsh.exe，回退 powershell.exe）。引用项目根用 $env:CLAUDE_PROJECT_DIR，别写裸的 $CLAUDE_PROJECT_DIR——PowerShell 会当成未定义变量解析成 $null[docs: Windows PowerShell tool]。

{
  "type": "command",
  "shell": "powershell",
  "command": "& \"$env:CLAUDE_PROJECT_DIR\\.claude\\hooks\\check.ps1\""
}

4. 通信协议：stdin 进，退出码 / JSON 出

这是 hook 最「底层」也最该吃透的一环。Claude Code 与你的脚本之间是一场结构化对话[docs: Hook input and output]：

① 输入：stdin 上的 JSON

脚本从 stdin 读到一段 JSON，含公共字段（session_id、cwd、permission_mode、hook_event_name…）加事件专属字段。以一次拦 Bash 的 PreToolUse 为例：

{
  "session_id": "abc123",
  "cwd": "/home/user/my-project",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "npm test", "description": "Run test suite" },
  "tool_use_id": "toolu_01ABC..."
}

② 输出通道 A：退出码

最简单的回话方式就是退出码[docs: Exit code output]：

退出码含义
0成功放行。stdout 一般只进调试日志（例外：UserPromptSubmit/SessionStart 的纯文本 stdout 会被当作上下文塞给 Claude）
2阻断。PreToolUse→拦下工具调用；UserPromptSubmit→丢弃提问；Stop→不许停、继续对话。stderr 作为阻断原因
其它非阻断错误：动作照常进行，转录里留一条 hook 报错提示

⚠️ 想拦截就必须 exit 2，不是 exit 1

Unix 习惯用 1 表示失败，但 Claude Code 只认 2 作为阻断信号。裸用 exit 1 会被当成「非阻断错误」——动作照样放行。策略护栏务必用 exit 2[docs: Exit code 2]。

③ 输出通道 B：stdout 上的 JSON（更强的控制）

退出码只能「拦/不拦」。想要富控制——指定放行/拒绝/升级问用户、往上下文注入信息、甚至改写工具参数——就往 stdout 打印一段 JSON。Claude Code 在任何退出码下都会读它[docs: JSON output]。不同事件用不同的决策字段：

事件决策字段作用
PreToolUsehookSpecificOutput.permissionDecisionallow/deny/ask——放行、拒绝、或升级给用户确认
PostToolUse、Stop 等顶层 decision: "block" + reason阻断并把 reason 反馈给 Claude
多数事件hookSpecificOutput.additionalContext把一段文字注入 Claude 的上下文窗口

这就是第 2 节图里那两个金色闸门（PreToolUse/Stop）的能力来源。一个「禁止 rm -rf」的 PreToolUse 处理器长这样：

#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')          # 从 stdin JSON 取命令

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",                # 拒绝这次调用
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0                                          # 无决策：走正常权限流程
fi

（这些 Bash 例子用 jq 解析 JSON，需先装好 jq 并在 PATH 里。）

5. 决策速查：谁能拦、谁只能听

不是每个事件都能「拦截」。按能力分三类，写 hook 前先对号入座[docs: Decision control]：

能力代表事件能做什么
能拦截 / 改写PreToolUse、UserPromptSubmit、Stop拒绝动作、改写工具参数、拦住 Claude 别停
只能注入上下文SessionStart、PostToolUse往上下文塞信息（分支名、CI 结果、项目规则），不能拦
纯副作用SessionEnd、Notification只用来记日志、清理、发通知，无决策权

所以「自动 lint」用 PostToolUse（改完文件后跑，把结果注入上下文让 Claude 自己修）；「禁危险命令」用 PreToolUse（执行前拦）；「审计日志」挂 SessionEnd 或任意事件（纯记录）——选事件的依据，就是你需要哪一档能力。

6. 安全：hook 是拿你权限跑的代码

务必先审再用

命令 hook 以你的完整用户权限执行 shell 命令，能读写/删除你账号能碰的任何文件。把 hook 加进配置前，务必读懂并测试每一条命令[docs: Security considerations]。

两条最该记住的实践：

  • 工作区信任门槛：交互式会话里，Claude Code 会等你对该目录点了「信任」才运行任何设置文件里的 hook；但 claude -p（headless）不弹信任对话框——克隆别人仓库跑 -p 前，先审它的 .claude/，或用 --settings '{"disableAllHooks": true}' 关掉。
  • 脚本卫生：变量一律加引号 "$VAR"、防路径穿越（查 ..）、用绝对路径、避开 .env/.git//密钥等敏感文件。
