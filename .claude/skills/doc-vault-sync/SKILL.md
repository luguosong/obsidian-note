# Vault 链路与外观同步

把**分类目录**里脱链的东西重新接回 MOC 树，并给新分类目录补上图标和颜色。本 skill 是**定期维护工具**：用户日常新建笔记 / 目录时不会顺手维护 MOC 链接和外观，攒一阵子跑一次本 skill 批量同步。

> 为什么有这条 skill：用户的 vault 用「目录即分类 + 文件夹笔记 MOC」组织（见项目 CLAUDE.md）。每新建一篇笔记或一个分类目录，理论上都要手动在对应 MOC 里加 wikilink、在 Notebook Navigator 里配图标颜色——这很繁琐，用户懒得每次做。于是笔记越积越多，MOC 链接脱节、新目录没图标颜色。本 skill 负责定期把这些「欠的维护」一次性补齐。

## 两条铁律（凌驾一切，违反即事故）

**铁律一：MOC 链接只增不删——绝不删除任何已有 wikilink。**

MOC（文件夹笔记）里已有的每一个 `[[链接]]` 都不许删，哪怕它指向目录外的笔记（那是用户手动引入的「相关资源」等引用，skill 不干预）。skill 只做两件事：**补缺失的链接**、**重排链接顺序**。删除是禁止动作。

> 为什么：用户会在 MOC 里手动引入其它位置的笔记（例如在 `Obsidian.md` 里写 `## 相关资源` 段引用 `[[llm-wiki]]`）。这些是用户有意识的整理，skill 若以「该笔记不在此目录」为由删掉，就是毁掉用户的劳动。判定的唯一依据是「该有的链接是否缺失」，从不依据「已有的链接是否多余」。

**铁律二：已设的图标 / 颜色不动。**

`data.json` 的 `folderIcons` / `folderColors` 里**已存在**的分类目录，一律跳过——不覆盖用户或上次跑 skill 设定的值。只为**缺失**的目录补图标 / 颜色。

> 为什么：图标颜色是用户主观选择的结果（尤其品牌色：Java 橙、Docker 青等）。自动覆盖会抹掉这些判断。「只补未设」是最安全的策略；已有的想改，用户自己改。

## 作用域：哪些目录要处理

**处理的（分类目录）**：
- `01-编程笔记/` 下的**所有层级**子目录（主题目录及其深层子目录）
- 顶层学科分区 `NN-名称/`（如 `02-数学/`、`03-英语/` …）及其子目录

**排除（绝不处理）**：`code/`、`learning/`、`网页裁剪/`、`附件/`、`模版/`、`数据库/`、`Excalidraw/`、`未分类笔记/`、`待办任务/`、`docs/`、`.obsidian/`，以及上述目录的任何子目录。

> 判定一根线：目录是否在 `01-编程笔记/` 或 `NN-名称/`（编号学科分区）之下。是→处理；否→排除。

## 工作流：dry-run 先行，确认后才动手

本 skill **分两阶段**：先 dry-run 扫描出完整清单（不改任何文件），交给用户确认，用户点头后才执行修改。绝不直接改。

---

### Phase 0：扫描，生成 dry-run 清单（只读，不改）

遍历作用域内每个分类目录 `D`，收集以下信息，最后汇总成一份清单输出给用户：

**MOC 部分**（对每个 `D`）：
1. 找 `D` 的文件夹笔记 MOC = `D` 路径下与目录同名的 `.md`（例 `01-编程笔记/Java/Java.md`）。不存在则记为「需新建占位 MOC」（见下文「空目录占位 MOC」）。
2. 算出**该被链接的集合** `S`：
   - `D` 下的**直接子笔记**（`*.md`，排除 MOC 自身）→ 每篇贡献一个 wikilink（用文件名，去 `.md`）
   - `D` 的**直接子目录** `C` 中，存在 MOC 的（`C/C.md` 在）→ 贡献一个指向子 MOC 的 wikilink `[[C目录名]]`
3. 读 MOC 现有所有 `[[...]]` 链接 → 集合 `E`。
4. **待补** = `S − E`（该有却没链接的 = 孤立笔记 + 漏链的子 MOC）。
5. 记录：`D`、待补的链接列表、是否需重排（见 Phase 1 重排规则）。

**图标 / 颜色部分**（对每个 `D`）：
1. 查 `data.json` 的 `folderIcons` / `folderColors` 是否已有 `D` 的全路径键。
2. 缺图标 → 按语义候选一个 lucide 图标（见「图标规则」）。
3. 缺颜色 → 走颜色算法（见 `references/color-algorithm.md`），算出一个与真实相邻目录不重色的 Tailwind 色。
4. 记录建议值。

**重名告警**：若 `D` 下某笔记的文件名在 vault 内有多个同名文件，`[[文件名]]` 会歧义——标记为告警项，让用户确认用 `[[路径/文件名]]` 还是别的。

把全部结果按「dry-run 清单格式」（见下文）输出，**停下来等用户确认**。

---

### Phase 1：MOC 补漏 + 重排（用户确认后执行）

对清单里每个待处理的 `D`：

1. **补**：把「待补」的 wikilink 加进 MOC 的**主索引列表**。
   - 「主索引列表」= MOC 里**第一个**连续的 `- [[...]]` 列表块（通常在一级标题下、任何 `## 二级标题` 之前）。
   - 若 MOC 是空占位（只有 `# 标题` 没有列表），则在标题下新建该列表。
   - **绝不**把新链接加进 `## 相关资源` 等后续段落——那些是用户手动维护的，不碰。

2. **重排**：把主索引列表里的链接按「重排规则」排序后写回。**只重排主索引列表这一段**，其它段（`## 相关资源` 等）原样保留。

3. **不删**：主索引列表里原有的、但不在 `S` 里的链接（例如用户手动塞进主索引的外部引用），**保留不动**（参与重排但不删除）。

**重排规则**（决定主索引列表里链接的顺序）：
- 读每个被链笔记 / 子 MOC 的 frontmatter `排序` 字段（数字）。
- **有 `排序` 值的**按值升序排在前。
- **无 `排序` 值的**按文件名字母序排在后面（中文用拼音序，即 JS `localeCompare('zh')`）。
- 稳定排序：同 `排序` 值或同字母序的，保持原相对顺序。

> 为什么可以重排：用户明确「可以重排顺序」。重排让 MOC 主索引保持整齐（重要笔记用 `排序` 字段置顶，其余字母序），避免新链接堆在末尾越积越乱。但重排仅限主索引段、且绝不删链接——整齐以不丢信息为前提。

---

### Phase 2：图标 / 颜色补全（用户确认后执行）

按清单建议，把缺图标的目录加进 `folderIcons`、缺颜色的加进 `folderColors`（键为目录全路径，如 `01-编程笔记/Java`）。**已有的一律不动。**

改的是 `.obsidian/plugins/notebook-navigator/data.json` 的 `folderIcons` / `folderColors` 两个对象。改完用 `node -e "JSON.parse(...)"` 校验 JSON 合法。改完提示用户重载 Notebook Navigator 插件生效。

---

### Phase 3：同步 CLAUDE.md（空目录占位 MOC 约定）

本 skill 会给空分类目录建占位 MOC（见下文），这与项目 CLAUDE.md 原本的「0-1 篇不建空 MOC」约定相反——该约定已过时。**每次跑 skill 若发现 CLAUDE.md 里仍残留「0-1 篇不建空 MOC」的表述，同步把它改成「空分类目录建占位 MOC」**，保持文档与 skill 行为一致。

> 为什么：文档和实际行为不一致会骗人（你或别的 agent 读 CLAUDE.md 会被误导）。skill 的行为是新的约定，文档要跟上。

## 空目录占位 MOC

作用域内的**空分类目录**（0 篇笔记、无 MOC）也要建一张占位 MOC（与目录同名的 `.md`），作为 Notebook Navigator 的「点目录即打开」入口。占位 MOC 内容：

```markdown
---
描述: <一句话说明该分类覆盖的主题>
排序:
分组:
创建时间: <YYYY年MM月DD日，当天>
---
# <目录名>

<一句话主题说明>。笔记待整理迁入后在此汇总。
```

- frontmatter 用 `模版/普通笔记模版.md` 的基础字段（`描述`/`排序`/`分组`/`创建时间`），**不要删基础字段**。
- `描述` 填一句话该分类的主题（凭目录名语义判断，如 `密码学` →「国密算法（SM2/SM3/SM4）、PKI（CA·RA）体系与密码学基础」）。
- 之后该目录有笔记了，再跑 skill 时占位 MOC 会被正常补漏 + 重排（标题、frontmatter 保留）。

> 为什么空目录也建：用户要求每个分类目录点开都有入口页（Notebook Navigator folder notes），即使空目录也要有占位，方便后续填充。

## 图标规则

为缺图标的分类目录选 lucide 图标：

1. **查种子映射表**（下文）：目录名 / 主题命中 → 直接用映射的图标。
2. **未命中**：按目录名的**语义**选一个 lucide 图标（例：`Rust` → 系统/语言类，可选 `gears>` 或 `leaf`；`Kafka` → 消息流，可选 `messages-square`）。
3. **校验合法性**：所选图标名必须是 [lucide.dev](https://lucide.dev/icons) 上存在的；拿不准就 `WebFetch` 查 lucide 图标库确认。非法或无把握 → 留空（不设图标）并在清单里告警，不要瞎编一个不存在的图标名。
4. 图标也可用其它已启用图标库（data.json `externalIconProviders` 开了 `bootstrap-icons`/`simple-icons` 等），格式 `库前缀:图标名`（如 `bootstrap-icons:windows`）。

## 颜色规则（概述）

为缺颜色的分类目录配色，原则是**相邻不重色**（相邻目录色相差异大，一眼可区分）。**相邻关系按 Notebook Navigator 的真实显示顺序判定**，不是按字母序猜——因为中文目录的显示顺序是 Chromium 的 `localeCompare`（拼音变体），与字母序 / Unicode 序都不同，猜会配错。

具体算法（DOM 读取、相邻判定、选色）见 **`references/color-algorithm.md`**——执行 Phase 0 / Phase 2 的颜色部分前先读它。

关键约束：
- **Obsidian 必须运行 + `obsidian` CLI 可用**（`obsidian eval code="app.vault.getName()"` 能返回 vault 名）。否则**降级**：跳过配色（只做 MOC 和图标），在清单里告警「配色需 Obsidian 运行，本次跳过」。
- 调色板用 Tailwind 500 色阶（`#ef4444` 红、`#f97316` 橙、`#f59e0b` 琥珀、`#84cc16` 黄绿、`#22c55e` 绿、`#10b981` 翠、`#14b8a6` 青、`#06b6d4` 天青、`#0ea5e9` 天蓝、`#3b82f6` 蓝、`#6366f1` 靛、`#8b5cf6` 紫、`#a855f7` 紫2、`#d946ef` 品红、`#ec4899` 粉、`#f43f5e` 玫红）。
- 新目录选一个与**真实前后的兄弟目录**色相差 ≥ 90°（理想 120°+）的色。同时避开父目录的颜色。
- 已设的颜色（`folderColors` 已有键）**当作固定约束**，新色要避开它们。

## 仓库约定（执行时遵守）

- MOC / 笔记的 frontmatter 用 `模版/普通笔记模版.md` 基础字段（`描述`/`排序`/`分组`/`创建时间`），中文格式，创建时间用当天 `YYYY年MM月DD日`。
- wikilink 用 `[[笔记名]]`（文件名去 `.md`，不带路径）；重名时才用 `[[路径/笔记名]]`。
- 一级标题 `# 目录名` 与 MOC 文件名一致。
- `data.json` 改完务必 `node -e "JSON.parse(require('fs').readFileSync('.obsidian/plugins/notebook-navigator/data.json','utf8'))"` 校验。
- 提示用户改完重载 Notebook Navigator 插件生效。
- 不碰 `.obsidian/workspace.json`，不碰排除目录，不提交 git（除非用户要）。
